# Making a release

How a release archive is built, checked and published, and what to do before the repository's GitHub Actions are switched on. Publishing is always done by hand: nothing in this repository pushes, tags or publishes by itself.

## 1. Build, test, package

```powershell
git submodule update --init --recursive
pwsh -File tools\build-locked.ps1 -Rebuild
pwsh -File tools\test.ps1                                   # 0 failed
pwsh -File tools\footprint.ps1                              # record the numbers
pwsh -File tools\package.ps1 -Target <package folder>       # build output + ini fragments merged into OptiScaler.ini
pwsh -File tools\package-release.ps1 -Package <package folder> -Version ffxiv-<yyyy.mm.dd>-<upstream sha8>[-rcN]
```

`tools\package.ps1` copies the build output to the target folder and merges the fragments in `OptiScaler\ext\ini\` into the shipped `OptiScaler.ini`. `tools\package-release.ps1` turns that folder into `dist\OptiScaler-FFXIV-<Version>.zip`. It never writes to the package folder (it hashes the folder before and after to prove it), writes a `.gitignore` containing `*` into `dist\` so an archive cannot be committed by accident, and finishes by extracting the archive to a scratch folder and re-checking every hash.

Exit codes of `package-release.ps1`: 0 ok, 2 bad arguments or a missing required file, 3 a file it cannot classify or a licence file that is missing, 4 verification failed, 5 a packed binary contains a user profile path.

Exit 5 is the privacy scan: before anything is written, every packed `.dll`, `.exe` and `.addon*` is searched (ASCII and UTF-16LE) for a drive letter followed by `:\Users\`, which a build can leave in the PE debug directory or in assertion strings and which would publish the Windows user name of the build machine. The message names the file and the string. There is no switch to skip it: rebuild so that the path is not embedded (the forwarder links with `/PDBALTPATH:%_PDB%`, which keeps only the `.pdb` file name). A match inside a third-party library under `OptiScaler\` (FidelityFX, XeSS, Direct3D 12 core) is reported as a warning with the string and the file is packed, because it can only be the vendor's build path; read the warning once. Files under `Licenses\` are classified like every other file (a blocked name there is left out and reported) and scanned too.

## 2. What goes into the archive

The archive has the layout of the game folder (the folder that contains `ffxiv_dx11.exe`):

| In the archive | Source |
|---|---|
| `winmm.dll` | the build's `OptiScaler.dll`, renamed (the game loads it by that name) |
| `OptiScaler.ini` | the merged template |
| `nvngx.dll_dlssnr.dll` | the fork's NR forwarder (the name is a contract with NVIDIA's model, see [SEAMS.md](SEAMS.md) section 5) |
| `OptiScaler\...` | third-party libraries the build copies: `D3D12_OptiScaler\D3D12Core.dll`, `amd_fidelityfx_*.dll`, `libxess.dll`, `libxess_dx11.dll`, `libxess_fg.dll`, `libxell.dll` |
| `Licenses\...` | the build's licence and notice files (DirectX, FidelityFX, XeSS, RenoDX licence, attribution and notice, ReShade headers attribution), plus the GPL-3.0 text and [ATTRIBUTION.md](ATTRIBUTION.md) (which carries the credit for SirenBrink's fork) |
| `INSTALL.txt`, `NOTICE.txt`, `SHA256SUMS.txt` | generated by the script (install steps and bring-your-own list; credits and the source pointer; hashes of everything else in `sha256sum -c` format) |

Left out on purpose: `.pdb`, `.exp`, `.lib` (use `-IncludeSymbols` to ship the `.pdb`) and upstream's `setup_windows.bat`, `setup_linux.sh` and the "extract all files" marker (the fork's install is a plain copy).

**Never packed, even if they are in the package folder:** NVIDIA's runtime and model files (`nvngx_dlss*.dll`, `nvngx_dlssnr.dll`, `nvngx.dll`, `nvapi*.dll`), Streamline plugins (`sl.*`), anything that looks like a model (`*.onnx`, `*.engine`, ...), and the Ampere companion runtime (`dlssg_sm86*`). They are listed in the report and in `INSTALL.txt` under "bring your own". The script knows them by name; extend `$blockPatterns` if a new one appears.

**Anything it does not recognise stops it (exit 3).** Decide whether the new file is a third-party binary (add it to `$thirdParty` with its licence file) or must never ship (add it to `$blockPatterns`).

### Checks to do before publishing

- A test run against the package folder of a development build (the one played shortly before the first release candidate) produced 23 files plus `SHA256SUMS.txt`, 126 MB. That folder held no NVIDIA or Streamline file, so nothing had to be excluded; the same run was repeated on a synthetic folder with such files and the script left them out.
- **`libxell.dll`**: the only licence file the build ships for it is `XeSS_LICENSE.txt`, which does not name it. The script leaves it out by default (`-Exclude` defaults to `libxell.dll`; the XeFG output and XeLL low latency then need the user to supply it). Pass `-Exclude @()` only after confirming with Intel's licence for the XeSS SDK that it covers the Xe low latency library.
- Everything under `OptiScaler\` is redistributed on the same terms as upstream OptiScaler's own releases; check upstream's current practice if its list of bundled libraries changes.
- Read `INSTALL.txt` and `NOTICE.txt` in the extracted archive once.
- Run the smoke test in [SYNC-RUNBOOK.md](SYNC-RUNBOOK.md) section 9 with the archive extracted over a clean copy of the game folder.
- Check that the release status paragraph and the table in [STATUS.md](STATUS.md) and the status section of [.github/README.md](../.github/README.md) match the release (tag names, tested features, supported game build).

## 3. Tag and publish (by hand)

```powershell
git tag -a ffxiv-<yyyy.mm.dd>-<upstream sha8>[-rcN] -m "<summary>"
git push origin ffxiv-<yyyy.mm.dd>-<upstream sha8>[-rcN]
gh release create ffxiv-<...> dist\OptiScaler-FFXIV-ffxiv-<...>.zip --prerelease --title "v<version>" --notes-file <notes>
```

Use `--prerelease` for `-rcN` tags. The release notes should say which features are tested (copy the table from [STATUS.md](STATUS.md)), the upstream sha the build is based on, the supported FFXIV build (the `TimeDateStamp` in `ext/ffxiv/GameBuild.h`), the archive's SHA-256, and that the archive does not include NVIDIA files. Convention for the tag: [SYNC-RUNBOOK.md](SYNC-RUNBOOK.md) section 10. The release name is the version number below.

### Release numbering

Each GitHub release is named with a version number (`--title "v<version>"`). The git tag keeps the date form `ffxiv-<yyyy.mm.dd>-<upstream sha8>[-rcN]`, because `tools\package-release.ps1` and the build's version string rely on the `ffxiv-` prefix.

The project is at 0.x, the initial development range of semantic versioning.

- Minor (0.Y.0): a new feature, or a change in behaviour that may need a settings change.
- Patch (0.Y.Z): fixes only.
- `-rcN`: a candidate that has not been through the wider play-test yet.
- 1.0.0 is reserved for the day the author calls the project stable.

| Version | Tag | Date | Upstream base |
|---|---|---|---|
| v0.1.0 | `ffxiv-2026.10.23-d9b62110` | 2026-10-23 | `d9b62110` |
| v0.2.0 | `ffxiv-2026.10.25-d9b62110-rc1` | 2026-10-25 | `d9b62110` |

The v0.2.0 row keeps the `-rc1` tag: it was published as a candidate and promoted to a normal release unchanged, so the tag and archive names were left alone. Add a row for every release. [STATUS.md](STATUS.md) and the status section of the README name the current release by version first and by tag second.

## 4. Rolling back a release

`gh release delete <tag> --yes` removes the release; `git push origin :refs/tags/<tag>` and `git tag -d <tag>` remove the tag. People who installed the archive restore the backup they made (install step 1) or follow the uninstall text in `INSTALL.txt`.

## 5. GitHub Actions: inactive drafts and how to switch them on

The repository has Actions switched off. Two workflow drafts are committed but inert:

| File | What it does |
|---|---|
| `.github/workflows/ffxiv-ci.yml` | On push and pull request to `main`: checks out with submodules, builds with `tools\build.ps1`, runs `tools\test.ps1`, prints the footprint, uploads the packaged build as an artifact. |
| `.github/workflows/ffxiv-upstream-watch.yml` | Weekly and on demand: compares upstream `master` with the sha in [UPSTREAM-BASE](UPSTREAM-BASE) and opens or updates one issue, "Upstream moved: N commits". |

The names start with `ffxiv-` because the repository contract reserves that prefix for fork workflows ([SEAMS.md](SEAMS.md) section 1) and `tools\footprint.ps1` ignores exactly that pattern.

**The catch.** The repository also contains upstream's six workflows in `.github/workflows/`. Switching Actions on makes all of them eligible to run: `build.yml` ("Scheduled Build", has a cron schedule), `clang-format.yml` ("clang-format Check", runs on every push and pull request), `just_build.yml` ("Build"), `just_build_no_signature.yml` ("Build (No Signing)"), `release_debug.yml` ("Build ReleaseDebug") and `test.yml` ("Test") (the last four on manual dispatch). They are upstream's and not meant for this fork, so disable each one **before the first push after Actions are enabled**, and ideally before anything can trigger them. Disabling is per workflow, survives later syncs as long as the files keep their names, and is reversible.

Check the current state first (read-only):

```powershell
gh api repos/<owner>/<repo>/actions/permissions          # {"enabled":false,...} today
gh workflow list --all --repo <owner>/<repo>             # the six upstream workflows, all "active"
```

Procedure (all of these write to the repository settings; run them yourself):

```powershell
$repo = '<owner>/<repo>'
# 1. Try to disable the six first, while Actions are still off. (Untested whether GitHub accepts this while Actions are disabled.
#    If it refuses, continue with step 2 and run this block again immediately afterwards, before any push.)
foreach ($w in 'build.yml','clang-format.yml','just_build.yml','just_build_no_signature.yml','release_debug.yml','test.yml') {
    gh workflow disable $w --repo $repo
}
# 2. Enable Actions, restricted to GitHub's own actions (the drafts use actions/checkout and actions/upload-artifact only).
gh api -X PUT repos/$repo/actions/permissions -F enabled=true -f allowed_actions=selected
gh api -X PUT repos/$repo/actions/permissions/selected-actions -F github_owned_allowed=true -F verified_allowed=false
# 3. Make the default token read-only (the upstream-watch draft asks for issues: write itself).
gh api -X PUT repos/$repo/actions/permissions/workflow -f default_workflow_permissions=read
# 4. Disable the six again if step 1 was refused, then confirm:
foreach ($w in 'build.yml','clang-format.yml','just_build.yml','just_build_no_signature.yml','release_debug.yml','test.yml') { gh workflow disable $w --repo $repo }
gh workflow list --all --repo $repo      # the six must read disabled_manually; the two ffxiv-* drafts active
```

Only then push anything that touches `.github/` or any branch. To switch everything off again: `gh api -X PUT repos/$repo/actions/permissions -F enabled=false`.

Notes on the drafts:

- `ffxiv-ci.yml` needs a Windows runner with Visual Studio 2022 (`windows-2022`) and builds the whole solution; expect a long run. It uses `tools\build.ps1`, which locates MSBuild through `OPTISCALER_MSBUILD`, a default path or `vswhere`. The WARP tests need no GPU. It fetches upstream into `refs/remotes/upstream/master` so `tools\footprint.ps1` can run.
- `ffxiv-upstream-watch.yml` reads [UPSTREAM-BASE](UPSTREAM-BASE) (the first line that is not a comment), asks the GitHub API for upstream `master` and the number of commits between the two, and creates or edits a single open issue titled "Upstream moved: N commits". It does nothing else. Keep `UPSTREAM-BASE` current as part of every sync.
- The YAML syntax was checked with a small purpose-built reader because no YAML library was available when the drafts were written; the first run on GitHub is the real test. Run `ffxiv-upstream-watch` manually (`gh workflow run ffxiv-upstream-watch.yml`) once before relying on its schedule.
