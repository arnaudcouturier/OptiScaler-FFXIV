# Game jitter: probe, correction and source in full

Material moved out of [FEATURES.md](../FEATURES.md#game-jitter-ffxiv) on 2026-10-23; the paragraphs are copied unchanged; internal names are renamed or removed. In the JitterSource paragraph the heading phrase "not yet validated in game" is replaced by the corrected status; the rest of that paragraph already stated the in-game result.

**What and why.** The game renders its scene with a jitter translation it scales itself and tells the upscaler the unscaled pixel jitter; they agree only when the game's scale s is 2. `[FFXIV] JitterProbe` (false) reads the game's camera jitter object (read only, guarded, matched game build only) and writes one log line about every 10 seconds, and early when the render size or preset changes: `Game jitter: counter N, reported jx/jy ..., ndc ..., render WxH (source), applied ax/ay ..., ratio rx/ry ..., signs ok, implied s = 2.000/2.000 (consistent), NGX saw the same values; NGX subrect ..., Width/Height ..., PerfQualityValue ...; last forced-quality answer ...`. `s = 2` on both axes means the game applies what it reports; another value means the upscaler is told a different jitter than the one in the picture; `signs MISMATCH` means an axis has the opposite sign. A failed check logs one line per episode (`Game jitter: not read, guard failed: ...`) and does nothing else. **Measured in game** (the released build, DLSS preset M): the picture moves by only 60% of the jitter the game tells DLSS about, `ratio rx/ry 0.600/0.600` in every sample, at DLAA and at Performance alike. Transformer presets (L, M) depend on accurate jitter more than the CNN preset K, which fits the reports that L and M look jittery. Quality (1.5x) and Balanced are not measured yet.

**Correction (experimental): calibrate and scale.** `[FFXIV] JitterCorrection` (false; also a checkbox, with the probe key, in the menu card "Game jitter (FFXIV)" in the FFXIV tab, after the FFXIV HDR10 card: it applies at once and is stored in the ini when the settings are saved). It learns the ratio applied/reported from snapshots of the game's jitter object and then multiplies the `Jitter.Offset.X/Y` pair of every DLSS evaluate by it, so the upscaler is told the jitter that is in the picture. The ratio is a property of one snapshot (its own jitter and NDC pair), so a snapshot does not have to belong to the evaluate in hand; this is why it works whether or not the game thread and the render thread are a frame apart. An earlier version replaced the pair only after proving, for every evaluate, that the object belonged to it; in the author's session that proof held for 11% of 9418 evaluates and the correction flapped between corrected and uncorrected frames, which is why it was replaced by this design. How it works: (1) a snapshot is accepted when the object was read cleanly, the render size is known from the game's Width/Height, both axes have enough jitter to give a ratio (at least 1/64 pixel), the signs agree, the applied jitter is at most 1 pixel and the object's frame counter is higher than at the previous snapshot (the same camera step counts once; a counter that goes down, such as a re-created camera, re-bases). (2) Five accepted snapshots in a row that agree within 2% (and whose two axes agree with each other) adopt their mean as the ratio: `Jitter correction: calibrated ratio 0.600/0.600 from 5 snapshots for render 1920x1080, output 3840x2160, quality 0; scaling the reported jitter`. Until then the game's values pass through. (3) A ratio within 2% of 1 means the game already hands DLSS what it applies: nothing is applied (`the game already hands DLSS the jitter it applies`). A ratio above 1.02 or below 0.25 is refused with one line and nothing is applied. (4) The adopted ratio keeps being checked against every accepted snapshot; isolated contradictions (a torn or off-frame snapshot) are counted and change nothing, five contradictions in a row that agree with each other replace the ratio (`ratio changed after 5 contradicting snapshots: was ..., now ...`). A failed read of the object never changes an adopted ratio; when no snapshot has been accepted for 10 seconds the ratio keeps being applied and the log says `verification stale` once, and `jitter snapshots are arriving again` when they return. (5) The calibration belongs to one configuration (render size, output size, quality, the forced-quality answer): a different one drops the ratio and learning starts again (`configuration changed to ...; calibration dropped, learning again`). (6) Every evaluate whose NGX pair is present, finite and not above 0.55 pixel is scaled: X first, then Y, with the pair read before any write; anything else passes the game's values through and is logged once per episode (`jitter pair not usable`). The first scaled pair of a calibration logs what the parameter block holds afterwards (`parameter block read back: (x,y)`). A consistent game is never touched. Both keys cost two config reads and a branch while off. Default off; to be validated in game, with frame generation off first.

**What the scaled pair reaches, and how to test it.** The correction writes once, into the parameter block of the evaluate in progress, and nothing puts the pair back afterwards (restoring it would hand the upscaler one value and frame generation another, because frame generation reads the block after the upscaler's evaluate). So everything that reads the block after the write sees the scaled pair: the DLSS super resolution, frame generation (also its guide-delay mode, which replays the corrected value together with that frame's guides), the DLSS-NR path (it copies from the same block), the `Jitter Count` value in the menu (it counts the applied pairs), and the FSR and XeSS backends if one of them is selected. A comparison of "correction on" against "correction off" with frame generation active therefore changes the upscaler and frame generation together. Test with frame generation (and NR) off first, then with frame generation on. The status line says whether frame generation is active.

**The stale block, and the status line.** Multiplying is not harmless the way writing an absolute value was: if the game does not set `Jitter.Offset` again before the next evaluate (or the engine runs twice for one evaluate), the block still holds our own result and scaling it again would shrink the jitter every time. So the engine remembers the pair it wrote last, exactly as passed to the block, and an evaluate whose pair equals it bit for bit on both axes is not scaled again; it is counted as `already scaled (block not refreshed)`. The count is also the in-game answer to the open question whether the game sets `Jitter.Offset` at every evaluate: a count near zero means it does, a count near the number of evaluates means it does not. The engine therefore remembers, next to the pair it wrote, the game's own RAW pair that it was derived from. When the pair read equals the written pair bit for bit on both axes, the block was not refreshed and the raw pair is the remembered one (never the pair read); the wanted pair is re-derived from it every time: raw times the current ratio, or the raw pair itself when nothing is to be applied (still learning, a consistent or refused game, a manual scale of 1.0 or 0, a new configuration that starts the learning again). A wanted pair that equals the written one is not written again (counted `already scaled`); a different one is written (counted `scaled`, or under `learning` / `left alone` when the raw pair is put back). So a ratio change, a configuration change or a slider drag on a block the game does not refresh never compounds (raw 0.3 at ratio 0.6 then 0.8 gives 0.24, not 0.144), and a state that applies nothing leaves the game's own pair in the block. A pair the game has refreshed is simply the new raw pair. The remembered pair is forgotten only when the game refreshed the block and when the correction is switched off; after a write that failed half way it holds what the block is believed to hold (what it held before when the first value could be put back, the mixed pair with the true raw pair when it could not, so the next evaluate repairs it). Two coincidences are possible and harmless: a raw pair of exactly (0, 0) is counted as `already scaled` although the game refreshed it (0 times any ratio is 0, so the write would change nothing), and a genuinely new raw pair that is bitwise equal to the pair written last would be treated as not refreshed for one evaluate (practically impossible: the game's jitter sequence does not repeat). The status line reads `Jitter correction: on; totals since the start of the session: N evaluates seen, N scaled, N passed through while learning, N passed through because the jitter pair was not usable, N already scaled (block not refreshed), N left alone (nothing to apply); state: calibrated ratio 0.600 for render 1920x1080, output 3840x2160, quality 0; snapshots: N accepted, N disagreed with the ratio, N ratio changes, N restarts after a configuration change; verification fresh|stale; frame generation active yes (input Upscaler)|no (input NoFG)|unknown`; the state is `learning`, `calibrated ratio R`, `consistent (ratio R), nothing applied` or `refused (ratio R), nothing applied`, each with its configuration, or `dropped after a configuration change, learning again`. It comes about every 10 seconds for the first 60 lines and once a minute after that, and every line holds the totals since the start (subtract two lines for a window). What to look for in a good session: a `calibrated ratio` line within a second or two, then `scaled` close to the number of evaluates, `disagreed` and `ratio changes` near zero. Only the input named `Upscaler` reads the scaled pair from the parameter block; with another frame-generation input (`DLSSG`, `NvngxFG`, `FSRFG` ...) the field can say `yes` while the pair never reaches frame generation.

**Manual scale for experiments.** `[FFXIV] JitterScaleOverride` (0 = off, "auto" means 0; also a slider "Manual jitter scale (0 = learn it)" in the same menu card, greyed out while the correction switch is off; it moves in steps of 0.05 so it can land on exactly 0.6 or 0.8, and anything below 0.25 snaps to 0 = off) is an experiment key and may be removed once the correction has been validated. A value from 0.25 to 1.0, used while `JitterCorrection` is true, takes precedence over the calibration: nothing is learned and every evaluate is scaled by the value through the same path as above (reads before the write, X then Y, the 0.55 pixel limit, the stale-block guard, the put-back). The values to try, one after the other with the same scene: `1.0` (nothing is changed, the baseline), `0.8`, `0.6` (what the probe measured) and `0.5`. If the calibrated build looks the same as the baseline, comparing these tells "the 0.6 theory is wrong" from "the correction works" without another build. 0 is off and is never applied as a scale; a value that is not a number, negative, below 0.25 or above 1.0 is ignored (the calibration goes on) and logged once (`manual scale value ... ignored (valid values are 0.25 to 1.0, 0 turns it off)`). A value within 2% of 1.0 writes nothing. Switching it on drops the calibration state, switching it off starts learning from scratch; a change of the value is applied to the game's raw pair, so it never compounds on a block the game does not refresh, and 1.0 or 0 puts the raw pair back; each change of the value logs `manual scale 0.800 in use, calibration off` once, and the status line then reads `state: manual scale 0.800 (calibration off)` with the same counters.

**Limits.** (1) A second, differently sized DLSS evaluate in the same frame flips the configuration at every evaluate, so the correction never finishes learning (inert, the game's values pass through; the `configuration changed` lines are capped at 32). (2) The ratio is only as good as the formula `ax = ndcX * renderW / 2, ay = -ndcY * renderH / 2` that comes from reading the game's code; the constant 0.600 at two different render widths argues that the render-size part is right, and the manual scale is the cheap test of the rest. (3) Quality (1.5x) and Balanced are not measured. (4) With both keys off a pause keeps an adopted ratio (the zero-cost default); switch the correction off and on to start learning again. (5) A pair that arrives with a jitter above 0.55 pixel, or without one, is not scaled.

**Cost and log budget.** With the probe alone, the clock decides between samples: nothing is read in the first 2 seconds after a sample; after that the parameters (nine lookups) are read on every 16th evaluate to notice a changed render size or preset, for as long as the session lasts, and again at each 10-second sample. With the correction on, every evaluate reads the parameters and the object (one pass of reads). At most 360 sample lines are written per session (then one line says so); failure episodes, unusable pairs, the first scaled pairs and each kind of calibration event are capped at 32 lines each, and the count of episodes that did not get a line is reported when it changes (`Game jitter: log line budget used up, episodes not logged so far: N probe failures, N pass-throughs, N replacements, N abandoned steps, N calibration events`; `pass-throughs` are unusable pairs and `replacements` are first scaled pairs; the first 60 reports as they change, then at most one a minute, always with the totals). The status line is thinned the same way instead of being cut off. A step that throws is abandoned (the rest of that evaluate is skipped, the learning run in progress is dropped but an adopted ratio is kept) and logged once per episode (`Game jitter: step abandoned after an exception: ...`); the same place failing again and again is one episode, even when the evaluates between two sample ticks complete, and the episodes beyond the 32-line budget are counted in the report as `N abandoned steps`. A pair whose second value could not be written is put back to the game's own first value (best effort), so the upscaler is not handed a mixed pair for that evaluate. Switching the correction key off while the probe stays on drops the whole calibration; learning starts again when it is switched back on.

**Jitter at the source (`[FFXIV] JitterSource`, experimental, default off; the lattice was tested in game, see the Status in FEATURES.md).** In DLSS mode the game draws the scene with only a fraction of the sub-pixel jitter its generator produces (the native strength, measured 0.6, so +-0.3 px instead of +-0.5 px) and calls the generator with an unbounded phase count, so the pattern never repeats. `JitterCorrection` can only change what the upscaler is told; it cannot recover sub-pixel samples that were never drawn. With `JitterSource=true` the fork changes what is drawn: a hook on the game's jitter generator (called by the camera update) divides its output by the game's own native strength, so the game's multiplication leaves the full +-0.5 px lattice, and replaces the unbounded phase count by NVIDIA's `ceil(8 * output pixel area / render pixel area)` (8 at DLAA, 18 Quality, 24 Balanced, 32 Performance, 72 Ultra Performance), recomputed on every call, so a quality or size change follows at once. The hook only touches the WORLD camera's jitter object (the one the world-scene NGX packet is built from, learned from a second hook on the camera getter); any other object that reaches the same call site is left alone and logged. At the DX11 evaluate boundary (the same place `JitterCorrection` writes) `Jitter.Offset.X/Y` of that frame are replaced by the offset that was drawn (`x = ndcX * width / 2`, `y = -ndcY * height / 2` of the same frame, paired with the packet by its raw value, render size and age). Super resolution, frame generation (also the guide-delay replay) and the Jitter Count readout read the same block, so they all get the drawn value. The motion-vector jitter compensation and every other buffer the game derives from the jittered projection follow automatically because the change is made before the game builds them. `JitterCorrection` stands down for every evaluate the fix tells; when the fix is off or has fallen back it works exactly as before. Fail-open means today's behaviour: any mismatch of the executable (identity and the instruction-guard blocks), a failed hook install, the key off, or a generator that is not being normalised for a second (not in DLSS mode, native strength out of range, world camera not learned or never seen at the call site) switches the generator hook and the told-offset write off together. A verification runs on every frame whose generator record is known: the drawn offset is compared with the generator's own Halton value (tolerance 0.005 px); 90 consecutive frames outside, or 90 consecutive evaluates that match no camera sample, make the fix fall back for the session (switching the key off and on again tries once more). A frame that matches no camera sample is told the generator's recorded value for that raw pair when there is one and otherwise left to `JitterCorrection`; only three evaluates within a second with no record and a value above 0.55 px (more than the scaling accepts) fall back at once. The character preview keeps its own 32-phase path. Log lines: `Jitter source: hooks installed (...)`, `Jitter source: active (strength 0.600, phases 32 for render 1920x1080 output 3840x2160)`, `Jitter source: verified N frames, drawn offset equals the generator's value (max deviation ... px, outside 0.005 px: 0), ...; told offsets over N frames: x a..b px, y c..d px, D distinct pairs (phase count P)` (it says `differs ... in N frames` when any frame was outside), `Jitter source: phases A -> B (...)` on a quality change, `Jitter source: the generator's camera call site was reached with N distinct jitter object(s): ...`, `Jitter source: inactive (<reason>)`, `Jitter source: fell back to the old behaviour, ...`. With the key off no hook is installed and the cost is three config flag loads, one relaxed atomic load and a branch. Experimental, opt-in, default off: the arithmetic and the executable anchors were checked against the October 20 executable (SHA-256 46A52AB1...); in game the log showed the full +-0.49 px lattice with 32 distinct phases at Performance and 0 frames outside tolerance, and the author reported motion 'less jumpy' with it on while `[HudLess] Mode = ui_free` was active. It is not what removed the faint micro-stutter seen with frame generation in that session: that came from the `ui_free` fallback (see HUD-less frame generation) and was gone with `recomposition` whether the key was on or off (with the DLSS-G preset on Auto or B).
