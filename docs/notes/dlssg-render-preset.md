# DLSS-G render preset: full description

Material moved out of [FEATURES.md](../FEATURES.md#dlss-g-render-preset-a-b-c-switchable-while-the-game-runs) on 2026-10-23; the paragraphs are copied from it with only internal names renamed or removed and the in-game status corrections of 2026-10-23.

**DLSS-G render preset (A, B, C), switchable while the game runs.** Chooses the render preset of NVIDIA's frame generation runtime (`nvngx_dlssg.dll`): Auto (the driver and the runtime decide), Preset A, B or C. The request is answered inside the process only: at start-up the driver-settings query of the runtime for the preset (setting id 0x10E41DF1) is answered with the preset number (a "setting not found" reply too), and no NVIDIA profile is written. That is the only id answered. The separate DLSS override id (0x10E41E03, NVIDIA's "DLSS override" switch) is never answered, because answering it "on" made NGX load NVIDIA's own copy of the runtime from its model store (`C:\ProgramData\NVIDIA\NGX\models\dlssg\...`, log `Built with APP_NAME = nvapp_override`) instead of the patched `OptiScaler/nvngx_dlssg.dll`: no multi-frame unlock (`max generated frames 1`) and about a third fewer frames per second (frame rates as the author measured them on one RTX 4090 setup, not from the logs); with only the preset id answered the local runtime loads (`APP_NAME = endpoint`, `max generated frames 5`) and logs `Applying settings for render preset N.` (checked in game on 2026-10-22 with `RenderPreset = 3`, about 74 fps on that setup). A user whose own NVIDIA profile, or the NVIDIA app's "DLSS override" setting, turns the override on may get NVIDIA's copy of the runtime regardless of this tool: that is inferred from the run in which this tool answered the override id itself, no log with a real profile value exists. The menu shows a warning line and the log gets one WARN line when NGX's init line for frame generation shows that copy (`Built with APP_NAME = nvapp_override`); it states what the log shows, not why. The preset is applied by that copy too (`Applying settings for render preset N.` was seen with it), without the unlock. Changing it in the menu while the game runs switches frame generation off, waits, releases the DLSS-G resources on a later frame (at least 3 frames and 100 ms after the switch-off, never in the same frame), lets the runtime build its next endpoint under the new request and resumes with fresh history. The installed runtime caches its settings, so the live change hooks three of its functions in memory (the cached-settings reader, the endpoint create function and the configuration copy function). This happens once, at the first live change, after the frame generation switch-off and the release, with only the calling thread enlisted (no other thread is suspended), and only after structural checks of the module's code passed: every pattern unique, every target a function start, the endpoint create function is decoded instruction by instruction and its context argument is followed from the function entry to the settings read (kept in any callee-saved register or frame slot, no fixed register is assumed; nothing may write that place in between and nothing may jump into that stretch), the shared configuration and the two copy sites are checked, the create function's argument count and status constant are read from the decoded code, and stack-frame sizes are read from the code so 310.8 and 310.9 builds both pass. The file hash is logged but is not the gate; only 310.8 and 310.9 runtimes are accepted. Any failed check or release keeps the old request and the menu says "restart needed"; nothing is hooked while the key stays on Auto, and a session that started on a preset can go back to Auto live only if the driver's own answer was seen first. Preset A and Preset C turn off the runtime's own UI recomposition and Preset B turns it on; Auto leaves it to the application (read in the binary of nvngx_dlssg 310.9.16, sha256 8d59d49b..., `EndpointConfiguration::ApplyRenderPreset`; Preset C also turns FG Lite on). So the UI recomposition is requested only when `[HudLess] Mode = recomposition` and the active preset is Auto or B: one pure rule (`ext/fg/dlssg/UiRecompositionRule.h`) decides it from the active preset at every DLSS-G option call, the first one included, so DLSS-G is created with the final value and is never recreated because of it (the runtime's confirmation only feeds the menu readout, never the decision). With A or C the option is not requested; the log says so once (`Preset C turns NVIDIA's UI recomposition off on this runtime, so the HUD is interpolated; use Auto or B for recomposition, or ui_free with C`), the menu shows the same sentence next to the HUD-less mode and next to the preset selector, and the HUD-less engine stops capturing and reports `PausedByPreset`. Nothing is blocked, and the `ui_free` mode is not affected. The rule is the same on every runtime build: a runtime that ignores Preset C (310.9.1.0) loses the recomposition with C too. The menu shows whether the runtime asked the driver for the setting, the last NVIDIA preset log line verbatim (with a "confirmed" mark when its format is known) and what the runtime reports back (`requested`, and `applied` or `effective` depending on the build); it recognises the 310.9.16 wording (`Applying settings for render preset N.`, `ReportOverrideStates: render preset (requested=N, effective=N)`, `Ignoring unsupported render preset ID N.`) as well as the 310.9.1.0 wording, and it shows a private driver flag that forces part of the preset off (UI recomposition or FG Lite) as an override while the preset itself is still applied; when two lines disagree the later one wins (NGX's `Applied: No` does not outrank a later report that says the requested preset is in force; only `Applied: Yes` has been seen in a real log, so what `Applied: No` means is unverified); it says "In use" only when the runtime confirmed the preset, and a single `Applying settings for render preset N.` line is enough for that (the 310.9.16 runtime prints no `ReportOverrideStates` and no `Override Reported` line on a normal start with the preset id answered alone; their absence is not shown as a failure). The selector stays visible; when the chosen preset and the one in use differ the menu says `Chosen: X, in use: Y` with the reason (the change is made when frame generation runs next, or restart needed with the reason of the failed step, shown only while the chosen preset is the one that failed; the restart note says what stays until the next start, with "not confirmed" where the runtime did not confirm it, and that the ini value applies then), and with the control off it says `Chosen: X, not in use:` and the reason (Auto reads as the reason alone). "Chosen" is the selector's value, which is the saved one after Save Settings. The readout comes from a log relay on the Streamline log lines: with `[Log] LogLevel` at warn or higher, or with `LogAsync`, it stays empty and the menu says so. Disabled, with the reason shown, for the RTX 20/30 runtime, a replacement runtime and any output other than DLSS-G. Config: `[DLSSG] RenderPreset` (0 Auto, 1 A, 2 B, 3 C; the ini value applies at the next start either way). Status: the code checks pass on the real 310.9.16, 310.9.1.0 and 310.8.0 runtimes (local recipe `tests/ext/fg/fg_preset_guards_dll.cpp`, run with `tools\test.ps1 -Local`); tested on the 310.9.16 runtime (RTX 4090): boot on Auto and on Preset C; live Auto/B/C switches without a refusal (B on 2026-10-22, C on the released build); Preset A seen only on an earlier build; a start with `RenderPreset = 3` loads the local runtime (`max generated frames 5`) and applies Preset C; the live change Auto to Preset C from the menu was also seen working (2026-10-21, `max generated frames 5`, about 74 fps as the author measured it on one RTX 4090 setup). Known limits: the 310.9.1.0 runtime acts on A (1) and B (2) only (C is ignored there: the menu says so and nothing is paused), while 310.9.16 acts on all three (A and C turn the runtime's UI recomposition off, B turns it on, C also turns its FG Lite setting on: read from the runtime's code and the preset number, not stated by its log); "confirmed" rests on the lines the runtime prints when it creates an endpoint, so after a live switch the real UI recomposition and FG Lite behaviour are an in-game check; whether releasing the DLSS-G resources in a live scene is safe is an in-game question (the wait is 3 frames and 100 ms, not a proven GPU drain). Code: `ext/fg/dlssg/Preset*.h|.cpp` (`PresetX64.h` is the instruction decoder of the guards), `ext/fg/MenuFgPreset.cpp`. Seams: fg `PresetSwitchTick`; the driver-settings hook calls `ext::fg::preset::OnDrsGetSetting` (upstream: `nvapi/NvApiHooks.cpp` +2 lines, `framegen/dlssg/DLSSG_Dx12.cpp` +2 lines). Menu: section "DLSS-G render preset" of the `fg_unlocks` card. Check on a new runtime: `tests/ext/fg/fg_preset_guards_dll.cpp` (local recipe, runs with `tools\test.ps1 -Local` when `OPTISCALER_DLSSG_DLL` names the DLL).

**HUD-less recomposition and the DLSS-G preset.** NVIDIA's runtime decides what its preset does with the UI recomposition (nvngx_dlssg 310.9.16, `ApplyRenderPreset`, verified in the binary): Auto untouched, Preset A recomposition off and FG Lite off, Preset B recomposition on and FG Lite off, Preset C recomposition off and FG Lite on. Until 2026-10-22 the fork created DLSS-G with the recomposition requested and then paused it about 0.09 s later when the runtime confirmed the preset; Streamline then logged `UserInterfaceRecomposition flag changed from create-time value 1 to 0, feature needs to be recreated`, and after that recreation the author's screen showed about 59 of about 132 presents per second as distinct pictures (measured with a desktop-duplication counter), although the log said 2.00 presents per frame: frame generation felt like it was not working. The rule above removes the recreation. Recommended pairings: `recomposition` with preset Auto or B; preset A or C only with HUD-less off or `ui_free` (`ui_free` is experimental, see the Status paragraph). The preset selector is not tied to HUD-less: it is unavailable only for the RTX 20/30 runtime, a replacement runtime or an output other than DLSS-G, and Preset C without HUD-less is a valid configuration (the UI is interpolated). The local recipe `fg_preset_guards_dll` checks the preset stores of `ApplyRenderPreset` and the preset-to-store mapping on a runtime, so a future runtime that changes the table fails the recipe instead of mis-pairing silently.
