# Window mode: design, rules, log lines and open points in full

Material moved out of [FEATURES.md](../FEATURES.md#window-mode) on 2026-10-23; the paragraphs are copied from it with only internal names renamed or removed and the in-game status corrections of 2026-10-23. The menu card position is corrected to the FFXIV tab, first card, as in the layout table.

**What it is for.** FFXIV runs borderless when `[XeFG] ForceBorderless = true` (a setting the fork does not turn on by itself). In that mode upstream's hook swallows the game's request to change the window mode and restyles the window itself. Two problems come from that, both seen in logs: after leaving the pseudo fullscreen the window keeps a thin edge (the client area becomes 3836x2156 inside a 3840x2160 window), and one window-mode switch made while DLSS-G was running stalled Streamline's frame pacer, which logged "Potential dead-lock in Present - please make sure DLSS-G is disabled when making any modifications to the window" and ended with the GPU device removed.

**Status.** Opt-in, off by default; tested (RTX 4090) on 2026-10-19: border fix and two held-back mode switches with DLSS-G on; the open points listed below were not exercised. The rules and the decision flows have unit tests on fakes (frame generation, window, clock and swapchain are replaced by test doubles) and the window calls are tested on a real hidden window; the game itself decides whether it tolerates a held-back window-mode call (see "Open points" below).

**Config.** `[Window] Mode`: `off` (default: nothing runs and nothing is logged), `probe` (log only), `on` (probe, border fix and deferred mode switch). Applies after a game restart; any other value counts as `off`. The same setting is a drop-down in the menu card "Window mode (FFXIV)" (FFXIV tab, first card): the choice is stored for the next start and the card shows the mode that is active in this session. With `off` the module costs one atomic load and one branch at each of its five entry points (bridge resize, bridge destruction, Present entry, Present exit, ReShade event), and the ReShade event is not even subscribed.

**Probe.** With `probe` or `on`, one line starting with `Window:` is written (a) after every successful resize of the bridge swapchain and (b) for every window-mode call (`IDXGISwapChain::SetFullscreenState`) that ReShade sees, before the call. Fields: the window's style and extended style, window and client rectangles, frame generation state (`active`, `paused`, `off`, `none`) and `fgOffConfirmed=` (yes after ONE complete present with frame generation off and DLSS-G as the output; the replay and the border fix below need 2 such presents and 50 ms, so the field can read yes before either rule is met), `SCExclusiveFullscreen` (and its value at the previous resize), `ForceBorderless`, the window's owner thread id, the current thread id and the thread that presents, and for the call: its argument, the swapchain ReShade passed (`native=`), the bridge swapchain (`bridge=`) and the bridge's inner frame generation swapchain (`fgswapchain=`) side by side (which of the two ReShade passed is then visible), the verdict and the value the handler would return. The probe only reads (window styles and rectangles, frame generation state, thread ids) and logs; it changes no window and never prevents a call. The ReShade event needs ReShade (the log line `Window: ReShade set_fullscreen_state event registered` at start-up says whether it was subscribed).

**Border fix (`on`).** When `SCExclusiveFullscreen` goes from true to false, the module arms a fix. The flag is sampled at every bridge resize and at the end of every game present (the hook flips it without any resize necessarily following; the logged startup enter has none). From the end of a game present, once frame generation is confirmed off in the strict sense (like the replay below: at least 2 complete off presents and at least 50 ms since the first of them, so that after a leave that was not held the restyle does not land in the very first off present), it reads the window's styles. If the style has neither a caption nor a sizing frame but the extended style carries `WS_EX_CLIENTEDGE` or `WS_EX_WINDOWEDGE`, it clears those bits and applies them with `SetWindowLongPtr(GWL_EXSTYLE)` plus `SetWindowPos(NOMOVE | NOSIZE | NOZORDER | NOACTIVATE | FRAMECHANGED)`; the client area is again as large as the window. A window with a caption or a sizing frame (a real windowed mode) is never touched. A "complete off present" is a game present that started and ended with frame generation inactive, with DLSS-G as the output (Streamline applies "off" inside the next present); the fix needs 2 of them and the 50 ms, as stated above (the probe field `fgOffConfirmed=` is only the one-present condition). The fix never runs while frame generation is active (it can come back about ten frames after a Deactivate); it waits for the next off period, gives up after 120 checks or when 600 presents or 30 s have passed since it was armed, and runs only on the window's owner thread (otherwise it logs `owner thread differs, border fix skipped` once and does nothing). It is never called inside `ResizeBuffers` or a paced present.

**Deferred mode switch (`on`).** A ReShade add-on event runs before the game's `IDXGISwapChain::SetFullscreenState`. When all of these hold, the call is held back and the handler returns `true` (ReShade's "prevent"): `[XeFG] ForceBorderless` is on, the output is DLSS-G, frame generation is active, the call would really change `SCExclusiveFullscreen` (a repeat of the state in effect is not held), the call is for the bridge swapchain, its target output is null or the window monitor (the replay passes a null target), and the window's owner thread, the calling thread and the presenting thread are one thread. The module then asks frame generation off through the feature API (what upstream's hook does first: `UpdateTarget` and `Deactivate`), remembers the swapchain (no extra reference is taken; the hold is dropped, unreplayed, when the bridge swapchain changes or is destroyed, and the replay only runs on the live bridge), and from the end of a game present, once DLSS-G is confirmed off (at least 2 complete presents with frame generation off and at least 50 ms since the request), replays `SetFullscreenState(state, null)` directly on the swapchain ReShade passed (not through ReShade, so the event is not entered again). Upstream's hook and Streamline then see an ordinary call with frame generation already off. A second call while one is held keeps only the latest; if the latest asks for the state already in effect the held call is dropped. The wait is bounded: after 6 presents or 2 s the call is replayed if frame generation is off at that moment, a game present has reached the frame generation present since the request (or since the last time frame generation was asked off again) and at least 50 ms have passed since that request; frame generation can come back after about ten frames, so every present that finds it active asks it off again and the replay never runs with it active; only the hard limit (24 presents and at least 500 ms, or 6 s) replays regardless, with a warning (on a presenting thread that is not the window owner thread the hold is dropped with a warning instead of being replayed). A bridge resize while a call is held deactivates frame generation again (Streamline applies "off" inside the next present), so it restarts the count of off presents and the 50 ms floor, like a new request. Limits, not verified in game: (a) the 50 ms floor is an absolute time while frame generation pauses for about ten frames after a Deactivate; the first complete off present ends about one frame in, so at 138 game presents per second (7.2 ms) the floor leaves about two frames of margin, at 165 about one, and from roughly 190 to 200 game presents per second the floor outlasts the pause: frame generation comes back before the floor is over, the count restarts at every re-request, the confirmed replay does not come, and the hold ends at the hard limit with frame generation active (a warning), and the border fix expires without applying (`border fix expired`); the first in-game session reads the `replaying ... (after N presents, M ms ...)` line, reports which reason fired (`frame generation confirmed off`, `wait limit reached` or `hard wait limit reached without a confirmation`) and at what presents per second; (b) both conditions of the hard limit use the clock (24 presents need 500 ms as well, and the other limit is 6 s), so a clock that stood still would leave no hard limit; the live clock (`GetTickCount64`) is monotonic, so this is informational. A hold that is dropped instead of replayed (the hard limit on a thread that is not the window owner thread, a changed or destroyed bridge swapchain) forgets the call for good: the game was told the call succeeded but the window did not change, and frame generation was asked off and comes back about ten frames later; the log line `held SetFullscreenState dropped` means the mode did NOT change. Anything unexpected passes the call through as today. The monitor argument of the event is logged but never used. What the game receives for a prevented call is decided by ReShade and is not documented in the local headers; the log records only what this handler returned.

**Log lines.** All start with `Window:` (the logger puts the function name in front). `module active, mode=...` once; `ReShade set_fullscreen_state event registered` at start-up; `resize-done ...` and `set-fullscreen-state ...` probe records; border fix: `border fix armed`, `border fix waiting`, `border fix applied exstyle A -> B client WxH -> WxH`, `border fix gave up`, `border fix FAILED`, `owner thread differs, border fix skipped` (warning, once); mode switch: `SetFullscreenState(TRUE|FALSE) held back: frame generation asked off, ...` (before the request) and `... held back, frame generation asked off; handler returns true (prevent)` (once the request returned), `hold cancelled, the frame generation request failed (...); handler returns false` (warning: the call passes, and the `returned=true` of the record above it is void), `replaces the held call`, `held call dropped`, `held SetFullscreenState dropped, not replayed: ...` (the mode did not change), `frame generation came back while a call is held`, `replaying SetFullscreenState(...)` with the reason and `replayed SetFullscreenState(...) returned 0x...` (both are written after the call returned, so that a failing log cannot lose the held call; a hang inside the game's call leaves neither line), and, if the module's lock bookkeeping is ever found inconsistent, a warning `a nested entry left the module lock depth raised during a call out` (once; the bookkeeping is put right and nothing aborts). A probe record ends its call part with `verdict=` (`defer` or `pass(reason)`), `wouldReturn=` (what `on` would return) and `returned=` (what was returned).

**Complete presents.** "DLSS-G confirmed off" counts only game presents that really reached the frame generation present. The bridge advances its back buffer index only after the frame generation swapchain's `Present` returned success, with frame generation on or off, and never on one of its early error returns; the module reads that index at the start and at the end of each game present. A changed value (not "greater": the index wraps) is a complete present, an unchanged one resets the off count and is not counted. With fewer than two buffers the index cannot change, and with no bridge known (or a different bridge by the end of the present) nothing can be told: such a present is counted as it always was. Log lines: `the bridge present counter is live` (once: the positive proof), `the bridge present counter is not available (fewer than two buffers)` (once), `a game present ended before the frame generation present ... not counted` (the first five). Failed presents delay the replay up to the hard limit (24 presents and at least 500 ms, or 6 s): the soft wait limit described above needs a present that reached the frame generation present since the request, so a run of failed presents does not end at the soft limit, and a hard-limit replay with nothing confirmed logs a warning `hard wait limit reached without a confirmation` with the frame generation state (`fg=...`) at the end of the replaying line. With no counter (fewer than two buffers, or no bridge known) every present counts as having reached it, so the soft limit works as before, with the 50 ms floor. An unconfirmed replay at the soft limit logs `wait limit reached` instead of `frame generation confirmed off`.

**Open points, continued.** (6) The live side's two out-calls (the frame generation request in the order `fgChanged`, `UpdateTarget`, `Deactivate`, and the replay with a null target) are tested on fakes, by a source check that the live code goes through them and by a read-only source check that upstream's hook (`hooks/FG_Hooks.cpp`) still does the same three steps in the same order; the module lock being given up around each call out is tested as a scope on a fake mutex (a nested entry inside a call out never unlocks more than the thread owns), and its live use is pinned by a source check (each of the three calls out has its unlock scope before the call, each of the five entry points takes and counts the lock); that the real mutex is free during a call out is not exercised by a test. (7) If the bridge's swapchain has a single buffer the present counter is unavailable (see "Complete presents") and a present that failed before the frame generation present cannot be told apart; the gate then behaves as before this check. (8) One bridge swapchain is assumed (FFXIV creates one): the module remembers only the last bridge it saw at a resize, so with two live bridges the present counter of the last resized one would judge the other one's presents (an unchanged counter reads as an aborted present, the gate never counts and a hold would wait for the hard limit).

**Open points.** (1) What ReShade hands back to the game for a prevented call is not documented in the vendored headers; the module logs what its handler returned (`true`) and nothing else, and the game may or may not accept a call that is carried out a few frames later. (2) Which thread owns the game window is not known from the logs; the probe prints it next to the calling and presenting threads, and every action is skipped (the call passes through as today) unless they are one thread. (3) Whether FFXIV rewrites its own frame-less style after the fork's leave branch has run is inferred from window sizes in a log, not observed; the probe lines show the style before and after, and the border fix keeps checking for a while and then gives up without touching a window that still has a caption. (4) Whether the replayed call, made with frame generation off, avoids the Streamline stall can only be seen in the game: look for the absence of `Potential dead-lock in Present` after a `replaying SetFullscreenState` line. (5) The hold cannot cover a game `ResizeBuffers` that changes the size: no ReShade event exists before a resize, and a size-changing resize runs Streamline's flush at once, before any present has applied "off". So the call is held only when the FG swapchain already has the window's size (the probe line prints `swapchain=WxH` next to `client=`); otherwise it passes through with a warning `the follow-up ResizeBuffers is not protected`. The border fix must therefore have made the client 3840x2160 first: do the risky switch (leave or enter with frame generation on) only after a border-clean leave. The size guard is necessary, not sufficient: a leave from the 3840x2160 pseudo fullscreen to a smaller windowed mode passes it (the swapchain has the window's size at that moment) and is held, but the game's follow-up `ResizeBuffers` to the smaller size is a real resize that runs at once, before any present applied `off`; the hold is then no worse than today, not better. The first session compares the `swapchain=` value of the `resize-done` line after the call with the window size.
