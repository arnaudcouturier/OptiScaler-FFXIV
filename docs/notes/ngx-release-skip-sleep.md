# Quality change without the stall: full description

Material moved out of [FEATURES.md](../FEATURES.md#quality-change-without-the-stall) on 2026-10-23; the paragraphs are copied from it with only internal names renamed or removed and the in-game status corrections of 2026-10-23.

**Quality change without the stall.** Changing the DLSS quality in FFXIV releases the DX11 upscaler and builds a new one; upstream sleeps a fixed 500 ms between the two. On a matched FFXIV build the release can now prove the work is finished and skip that pause. It closes the upscaler's handle to new evaluates, waits (at most 200 ms) for an evaluate already running on another thread, drains the GPU queues the feature could still be running on (the upscale queue, and the frame generation queue when frame generation is attached to this feature; each with a fence wait capped at 5 s) and only if all of that is proven (log result `drained`) skips the sleep. Anything unproven gives `not-applicable`: a null queue, a removed device (also one lost during the wait), an evaluate that does not finish in time, a release called from inside an evaluate of the same handle, any other game or non-bridge upscaler. Then nothing changes: the handle is reopened at once and the 500 ms pause stays, with evaluates running through it as before. A failed drain (`failed`) refuses the release as before. With XeFG output and `[XeFG] ResetOnUpscalerChange` on (the default) the release also rebuilds the XeFG context, which the drain does not cover, so that path is treated as unproven by design and the pause stays. The sleep after the reset (`Dx11DelayedInit`, off by default) is not touched. On a proven release the handle stays closed for the few milliseconds until its entry is detached: an evaluate on it returns without output, the state a released handle is in until the game builds the next upscaler. The DX11 upscaler table has a narrow lock now (entries are reference-stable, an entry is detached under the lock and destroyed after it; the lock is never held across NGX, the driver, a drain, the frame generation mutex or an NR lock), because the game changes quality on its update thread while the render thread evaluates. The lock covers the table structure and the current-feature pointer writes; the contents of an entry are still written outside it (a race that existed before and is not made worse), and about 40 readers of the current-feature pointer stay unlocked. The log shows the thread of every create and release, and of an evaluate on its first call, when its thread changes, and as one summary line per 10 s (at most 4 first/moved lines per 10 s, the rest counted as `suppressed=<n>`); that settles which threads really do what, the update-thread claim above is inferred from the code and not yet seen. Status: new, unit-tested (drain classification, lock and registry, release sequence with fakes, thread trace, source pins); ran in game (RTX 4090) since 2026-10-20: the sleep was skipped and 0.06 to 30 ms were waited instead of 500 ms. Known limits: the release covers the upscale queue and the frame generation queue only; the real D3D12 glue and the lock-order premise (NR and frame generation never call back into the DX11 table) are pinned by source text and not by a run; skipping the pause changes timing on the game's update thread. Config: `[NgxRelease] SkipReleaseSleep` (ini only, default on; off = the old flow exactly: no closing, no waiting, the 500 ms pause; the table lock stays). Log: `FFXIV upscaler release: handle <n> result=<drained|not-applicable|failed> (...), waited <x> ms, sleep <skipped|kept (500 ms)|n/a (shutdown)>` and `FFXIV NGX thread: ...`. Code: `ext/dx11bridge/NgxLifecycle.cpp`, `NgxFeatureTable.h`, `ReleaseSequence.h`, `ReleaseDrain.h`, `ext/gpu/DrainResult.h`, `GpuQueue.cpp` (`DrainQueueEx`), `ext/upscaler/NgxThreadTrace*.h`. Seams: dx11bridge `BeforeReleaseFeature` (now returns a three-way result), `ShouldSkipReleaseSleep`, `SetCurrentFeature`, `ClearCurrentFeatureIf`; upstream: `inputs/NVNGX_DLSS_Dx11.cpp` (+13 -13: the table type, one locked iteration, the evaluate pin, the detach in release, the sleep condition); the thread lines are two calls in `ext/upscaler/UpscalerSeams.cpp` and `ext/Seams.cpp`.
