# OptiScaler-FFXIV seam catalog

The conflict surface of the fork. Contract and mechanics are in [SEAMS.md](SEAMS.md); this file lists every seam, its form, host and cost. On every nightly sync, review the host files below and nothing else. A seam that is added, removed or moved must update this file in the same commit.

Where an earlier proposal conflicted with SEAMS.md section 5, the catalog follows section 5.

## Conventions

- **Form:** `hook` = fire-and-forget call. `decision -> T` = upstream branches on the returned value; on any failure it returns the upstream-default answer. `inline-guarded` = inline wrapper in `Seams.h` that tests a feature bit or flag (relaxed atomic or `thread_local`) before an out-of-line call; cost when off is one load and one branch. `RAII` = scope object constructed by one upstream line.
- **Frequency:** `init`, `teardown`, `rare` (resize, colour-space change), `per-create` (per device, swapchain, feature or DLL load), `per-resource`, `per-cmdlist`, `per-frame`.
- **Owner IDs** are the fork's feature-series names (SEAMS.md section 2). Later series use words instead of a letter and number (for example `MENU`, `PT`, `ADOPT-FG`, `ADOPT-MIP`, `ADOPT-NR`, `ADOPT-REL`); their commit subjects carry the same tag.
- **Naming:** group names as in SEAMS.md; PascalCase functions. Where earlier notes named the same seam differently, the name below is the single one (see "Renames" below).
- **Free functions over virtuals.** No virtual is added to an upstream class. Per-object state hangs off one `_ext` member (section C).
- **Hdr truth:** `ext::hdr::Active()` is an inline reader of nightly's `hdrOutputActive`/`outputColorSpace` (SEAMS 5). `isHdrActive` does not exist.
- **Count basis for the footprint:** added plus removed lines (numstat sum), the same basis as the 6.8k figure of SirenBrink's fork at the import base (36c53a15) merged with the upstream nightly. Replacing an N-line block with one seam call therefore counts N+1.

## config

Fork keys live in per-feature structs bound by a declarative table; `ext::Cfg()` aggregates them. Section and key names are identical to today. `Config.h` loses every fork member (the ~460 `Config::Instance()->X` fork call sites exist only in fork code that moves to ext). Dropped keys (E1 `ProxyProbe`/`UseProxy`/`ScanAnchor*`, E2 `ProbeD3D11`, E6 `External`, dead `AdaBlackwellKernels`, migration-only `WhitePointFromExposure`) are not carried. `AutoCapture` becomes a real key (default false).

## gpu

C6 submission ownership (`GpuLifetime`, `GpuSubmission`, `ext/gpu/`). The wrappers replace every `Hdr10::ResetCommands/ExecuteCommands`; they are inline in `ext/gpu/Gpu.h` (included by `Seams.h`) and cost one relaxed load while no owner is registered.

**Owner registry.** A feature that keeps GPU objects alive across submissions (NR, the HDR conversion pool, the AMD PreSR bridge) calls `ext::gpu::RegisterOwner(const Owner&)` once at init and then `ext::restrack::EnsureHooks(device)`. `Owner` is a table of optional function pointers: `begin` (capture a `GpuSubmission` before the real execute), `quarantine` (failure path of `begin`), `reset` (a list was Reset), `isolate` (index of a list that must run alone, AMD PreSR pending list), `before`/`after` (around each actual execute). Slots are never recycled, `SetOwnerEnabled(handle, bool)` toggles. `SubmissionOwnersActive()` (inline, feature bit `F::Gpu`) and `OwnersWantReset()` are the fast-path tests. The detour and `ExecuteCommands` run every owner in registration order: all `before`, all `begin`, execute, all `after`, all `CompleteNoThrow` (the AMD Submitting / NR / HDR / AMD Submitted order of the import base). A throwing `begin` calls that owner's `quarantine` and the submission proceeds. When the detour covers the queue, `ExecuteCommands` only executes (the detour does the owners' work), so tokens are not doubled.

Ext-internal (not seams): `ext::gpu::Scope` (RAII over a bridge-owned recording: `Reset` through the owners, `Submit(queue)` = Close + `ExecuteCommands`, an abandoned scope closes the list; the SEAMS 7 item 1 line for the recorded-Init block), `ext::gpu::DrainQueue(queue)` (5 s fence drain, device-removal tolerant; was `WaitForFfxivReleaseQueue`), `ext::gpu::ExecuteOrdered(queue, list, fence, OrderedFence&, UINT64& allocatorValue)` (the C6 half of `ext::fg::SubmitSC`: execute, `++value`, signal, `failed` on a failed signal).

## (e) Open points that SEAMS.md does not settle

1. **Recorded Init dependency on C6/C10.** SEAMS 5 makes it `[UP]`; an earlier proposal was an out-of-line `ext::dx11bridge::InitFeature` using `Hdr10::ResetCommands/ExecuteCommands`. A self-contained `[UP]` commit can only use raw `Reset`/`ExecuteCommandLists`; the C6 and C10 series then add inline `ext::gpu::*` and `ext::hdr::BridgeInitScope` lines inside the block (+4-6 lines). Open: whether Init needs GpuLifetime registration at all (the Vulkan variant uses raw calls). The catalog assumes raw in `[UP]`, one RAII line from C10, no `ext::gpu` in Init.
2. **Bridge fence/allocator hardening scope.** `ProcessDx11Textures` (13 lines) and `dx11_with_dx12_sc.cpp` (~44 lines) are generic and upstream-worthy; SEAMS 5 does not list them. Catalog: `[UP]` rows 18-19. Alternative: inline `// ext: C6`.
3. **Menu tone-map under OptiHDR (resolved in C8).** `UseSdrUiTarget()` returns SDR from `getUiTargetMode()` while the menu layer composites into the HDR output. Visual parity with the import base still needs an in-game check.
4. **XeFG camera build.** Two options: a seam (`XefgBuildCamera`, chosen: ~37 lines of footprint) or an inline `[UP]` fix with only non-mutating near/far (~8 lines, loses `BuildView` validation). SEAMS 5 lists the XeFG barrier but not the camera fix.
5. **Detours transaction lock.** One proposal was a process-wide `ext::core::DetourLock` shared with ResTrack/DXGI hooks; SEAMS 5 puts the Streamline mutex under `[UP]` (self-contained, file-local) and lists `DetourLock` under `ext/core`.
