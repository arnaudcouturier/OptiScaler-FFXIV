# HUD-less engine: design

Status: **implemented, opt-in (`[HudLess] Mode = off` by default), tested in game on 2026-10-17; see sections 15 and 15a for what was verified and the known limits.** Statements marked **(inferred)** below come from reading code before the diagnostic runs; section 15 records what those runs found.

Source comments call this work S10 and name its parts as packages: A (FFXIV boundary detector, section 10), B (engine, config and menu), C (GPU mask and paste), D0 (ReShade probe), D1 (diagnostic build, section 12) and E (live source and ReShade integration, section 16).

## 1. Goal and decisions

With DLSS-G at 2-4x the HUD stays sharp (no smear/ghost) in fast camera motion: frame generation interpolates the **UI-free image** and the UI is **pasted back at the real frame rate**. Nothing else about the picture changes.

| Decision (2026-10-16) | Consequence in this design |
|---|---|
| The REST-based HUD path of SirenBrink's fork at the import base (36c53a15) never ran here (its ReShade add-on was never built) | Nothing to stay compatible with; no old keys carried |
| New engine around the mask and paste maths of that fork's HUD-less code (written there by byunjoe); its code and WARP tests are a reference | New modules. The GPU module and shaders share code with that reference (mask maths, shaders, defaults, API names); its WARP tests become test data (section 13). New here: the state machine, coverage guard, fenced slots and native capture |
| Provider parity with that fork | Full engine (UI-free FG + paste) on DLSS-G only; FSR-FG / XeFG get the hud-less / UI image tags (section 9) |
| Difference-based UI mask | Threshold 0.008, dilation 1, three-level alpha cleanup (section 7) |
| `[HudLess] Mode = off | recomposition | ui_free`, default off | Section 11 |
| Fail open | Any doubt means today's behaviour (section 5) |
| HDR via SDR capture + OptiHDR conversion; scene HDR keeps priority on frames it imports | Section 8 |
| ReShade integrated as a built-in add-on (decided 2026-10-16) | Section 16: presets are applied in place at the UI boundary, the HUD stays unfiltered; fail open if ReShade is absent or the integration fails |
| Dalamud overlays count as UI if the hook order allows | Measured by D1 |

## 2. Frame flow

Today (bridge, `Dx11wDx12SC::Present`, `with_dx12/dx11_with_dx12_sc.cpp` ~361-441, read 2026-10-16):

```
game draws scene -> game draws UI -> game calls Present (bridge wrapper)
  _RequestSharedBackBuffer -> _CopyDx11BackBufferToShared (backbuffer WITH UI) -> _WaitDx11ThenDx12
  -> _CopyDx11SharedToDx12FGBackBuffer -> _WaitForInteropCopyOnPresentQueue
  -> hidden real D3D11 Present (no wait) -> FG swapchain Present (DLSS-G dispatches; generated frames follow)
```

With the engine in `ui_free` mode:

```
game draws scene -> [boundary: first UI draw] source snapshots the bound scene RT (UI-free)
  -> game draws UI -> Present:
  PreInteropCopy      engine copies the snapshot into the slot's shared hud-less texture (same D3D11 context, before the signal)
  existing copies     backbuffer WITH UI -> shared -> D3D12 (unchanged)
  UiFreeFrame         decision: use the hud-less copy as the FG base? (all guards of section 5 pass)
  PostInteropCopy     on the FG queue: tag HudlessColor (+ UIColor in recomposition), build the paste image
  FG swapchain Present, then for EVERY output present (real and generated):
  BeforeOverlay       UiPaste::Paste draws the newest completed paste image over the backbuffer (while the paste is visible, section 5)
```

`recomposition` mode skips the base swap and the paste: DLSS-G receives HudlessColor + UIColor and recomposes the UI itself (it still interpolates the UI layer; documented limitation of that mode).

## 4. Contracts

### 4.1 `IHudlessSource` (game side)

`Active()` (cheap atomic), `Take(FrameImage&)` returning `NoSource | NotThisFrame | Rejected | Ok` (newest wins, never blocks), `LastReason()`, `EndFrame()`. `FrameImage` = D3D11 texture + typed format + size + sequence. The source snapshots the scene RT **at the boundary** into its own texture (one reused texture); the engine copies it into the shared slot at Present. This is one extra 4K RGBA8 copy per frame (about 33 MB read + write; negligible next to the frame's other traffic). A single-copy variant (source writes straight into the shared slot) is possible later if D1's cost numbers say so.

### 4.2 GPU API

`UiPaste::{Produce, Invalidate, Ready, Release, Paste, SetPasteEnabled, SetDebugTint, SetSteadyTiming, Snapshot}` and `UiImage::{Build, Release}` with `MaskParams` / `PasteStatus`. Semantics follow the `UiPaste` of the import base (section 7) with three additions: `PasteStatus::coverage` (share of pixels flagged, from a one-counter readback that is read two frames later without stalling), an explicit `hdrFinalImage`, and `SetPasteEnabled(bool)`, an output-side gate (on at start): while it is off `Paste` returns at once, draws nothing and counts no skip, and `Produce` / `Invalidate` are not affected (section 5, paste hold).

### 4.3 Engine entry points (exact signatures: `SEAMS-catalog.md`, group `hudless`)

| Seam | Site | Does |
|---|---|---|
| `ext::hudless::PreInteropCopy` (P0/P1) | bridge `Present`, before `_WaitDx11ThenDx12` | `Take()` from the source, copy into the slot's shared texture on the D3D11 immediate context |
| `ext::hudless::UiFreeFrame` (P2) | before `_CopyDx11SharedToDx12FGBackBuffer` | returns the D3D12 resource to use as FG base (hud-less) or null (normal path) |
| `ext::hudless::PostInteropCopy` (P3/P4) | after `_WaitForInteropCopyOnPresentQueue` | tags, builds UI image / paste image on the FG queue, advances the ring |
| `ext::hudless::OnReleaseInterop` (P5) | the bridge's release / resize path | drops slots and paste images |
| `ext::present::BeforeOverlay` (P6) | `LocalPresent`, before `MenuOverlayDx::Present` (`wrapped_swapchain.cpp` ~484) | `UiPaste::Paste` when mode is `ui_free` and a paste image is ready |
| `ext::hudless::Wanted()` / `SetWanted()` | hook sites; defined in `HudlessState.cpp` | atomic: `Mode != off` and the game source exists (zero-cost early-out). B calls `SetWanted` when the config loads or the menu changes Mode; A and the hook sites only read it |
| DLSS-G option seam | `ext/fg/dlssg/DlssgSeams.cpp` `AdjustUiRecomposition` | reads engine state instead of the `HudlessLink` stub |

Persistent footprint budget for all upstream-file lines of this feature: **<= 25** (footprint baseline 746 before the feature).

## 5. Engine state machine and fail-open

States (shown in the menu): `Off` (mode off, FG inactive or no source), `Searching` (armed, no capture yet), `Active` (>= 90 % of the last 60 presents delivered a usable capture), `Fallback(reason)`.

The decision is **per frame**, with hysteresis only for the displayed state:

```
useHudless = mode == ui_free
          && FG active && provider is DLSS-G
          && Take() == Ok
          && size / format match the FG backbuffer, not MSAA, not an array
          && slot free (reader fence completed)          // never block the game thread
          && paste ready (UiPaste::Ready)
          && !frameOwnedBySceneHdr                        // section 8
          && coverageGuardOk                              // not tripped; a tripped guard still takes the capture (below)
otherwise: today's path, exactly (full-frame FG), reason recorded
```

Fallback reasons (enum + text, all counted): `ModeOff`, `NoFrameGeneration`, `ProviderUnsupported`, `NoSource`, `NoBoundaryThisFrame`, `CaptureRejected`, `SizeMismatch`, `FormatUnsupported`, `MsaaOrArray`, `SlotBusy`, `PasteNotReady`, `SceneHdrOwnsFrame`, `MaskCoverage`, `DebugTintOn`, `PausedByPreset` (recomposition mode only: the DLSS-G render preset A or C turns NVIDIA's UI recomposition off, the fork does not request it and the engine captures and tags nothing; it applies only when recomposition was wanted at all, that is the mode, a hud-less source for the game build and `[DLSSG] UIRecomposition` not off).

**Coverage guard:** the mask pass counts flagged pixels (the readback arrives one or two real frames late, and only a readback that is new counts as a sample). Reason: black/white fades and, if ReShade presets turn out to run before the capture, preset-changed pixels would make the mask cover most of the screen. The limit is `CoverageGuard` (initial 0.60, a starting guess to calibrate from diagnostic runs); the guard has four parts:

- **Trip.** 5 consecutive fresh samples over the limit: the engine falls back to the normal base with `MaskCoverage`.
- **Silent probe.** While tripped the engine does not stop. Every present still asks the source; with `ProbeInterval = 1` it also takes the capture and builds the paste image on every present (one present in N with `ProbeInterval = N`, next bullet), so coverage keeps being measured and the source stays armed. The present only does not swap the base and sends no hud-less tag (section 9.1); its reason is `MaskCoverage` unless a capture step failed first (`NoBoundaryThisFrame`, `CaptureRejected`, `SizeMismatch`, `SlotBusy`, ... : the first failure of a present wins, so these now take precedence over `MaskCoverage` during a trip). `paste built` therefore counts nearly every present of a black screen, not only the captured ones. Under HDR output the probe prepares the slot's PQ conversion resources itself, because the usual caller (`PasteReady`) is skipped.
- **Probe interval (`[HudLess] ProbeInterval`, live, menu slider "Probe one frame in N while falling back", default 8 = one present in eight; 1 = every present).** With N above 1, while the guard is tripped only one present in N probes (the trip present is the first); the others stage nothing and build no image, and the present before each of them tells the source to skip that frame's copy (`IHudlessSource::SkipNextCopy`, optional: a source that ignores it copies anyway and the engine drops the image). The source is still asked on every present, so it stays armed: the FFXIV boundary applies the ReShade presets in the same place on every frame (never alternating with ReShade's own end-of-frame pass, which would filter the HUD on some frames and not on others) and the same-frame facts (anchor-later) keep coming. Those presents fall back with `MaskCoverage` (a frame without a boundary or with a refused capture among them is therefore counted as `MaskCoverage` too, and the boundary text of the status keeps the value of the last probe); so does a present whose copy was skipped and that finds no capture when the guard lets go on it, which is the guard's doing, not a missing boundary. With `ShowDetectedUi` on every present probes whatever N is: the tint draws the newest completed image of each probing present, and between two probes the ring is empty. Samples arrive once per probe, so the release takes about 30 x N presents of a clean scene (density: 60 x N), and the 120-present fail-open counts only probing presents (120 probes). Presents without a capture invalidate the paste ring as before, so the first swap after a release waits for a fresh image (one or two `PasteNotReady` presents) and never pastes an image from the last probe. Why: in a play session the per-present probe was the one piece of the engine's work still running in a steady fallback, and switching it off (the engine idle under the same DLSS-G preset) removed a faint frame generation stutter that the player saw most clearly with render preset C; the frame timing measured on the CPU did not differ, so the effect is on the GPU side and its exact mechanism is not measured. In one play session on 2026-10-31 (v0.5.0, DLSS-G preset C, `ui_free`), setting this key from 1 to 8 during play made that stutter go away, and setting it back to 1 brought it back; that one session and one preset are the whole evidence, so the default is now 8 and 1 keeps the behaviour before the key. `[HudLess] ProbeAbSeconds = N` (developer, ini only, default 0) alternates the interval between 1 and `ProbeInterval` in blocks of N seconds, each pair of blocks in an order drawn at start, with one log line per block and nothing in the menu, for a blind comparison.
- **Release.** After 30 consecutive fresh samples at or below 0.75 x the limit (0.45 at the default; no config key). A fresh sample above that level restarts the count, including samples between 0.45 and 0.60, which keep the guard tripped. With `ProbeInterval = 1` the images were built all along, so the first swapped present after the release already has a completed paste image (no `PasteNotReady`); above 1 the presents between probes invalidate the ring, so the first swap waits one or two presents for a fresh image. Consequence: a cutscene whose mask sits between 0.45 and 0.60 stays on the normal base after the first trip, like `Mode = off`.
- **Fail open.** 120 probed presents without a fresh sample release the guard (the producer stopped, so nothing could ever release it otherwise). Presents that took no capture (no boundary, loading screens) are not counted. If nothing completes a readback within 8 presents the guard reads "unknown" and never trips.
- **Density policy (`[HudLess] GuardMode = density`, ini only, default `legacy` = everything above).** Trips on 3 bad of the last 12 fresh samples (three bad in a row are enough, so there is no separate run rule); releases only after 60 clean fresh samples in a row (clean = at or below 0.75 x the limit, as above) and only on a present that is not anchored after off-screen UI draws; the 120-present fail-open release is the same. The boundary's same-frame fact is available at the present itself, so a tripped guard stays tripped at once on such a present and the clean run starts again, instead of waiting two presents for the readback of that frame (`CoverageGuard::ResolveRelease`). The paste hold (`kLeaveHold`) is not touched. The effect is more time in the fallback, whose output is what `Mode = off` shows (the capture and the paste image are still built on every present: the silent probe above), and fewer switches between the two image paths when bad frames come in bursts. **Design limit:** while tripped, every anchor-later present restarts the clean run, and readbacks arrive about one per present (one per N presents with `ProbeInterval = N`, which makes the figure below 60 x N), so an anchor-later present in every 60 presents or fewer keeps the guard tripped for as long as they keep coming, also when the images of those frames measure clean (the flat windows in the saved sessions); the 120-present release cannot fire because the probe keeps the readbacks coming. `GuardReleaseHolds` and `GuardTripOnAnchorLater` (next) bound that time; with both off (the default) it is left as it is, and `legacy` still gets the old guard back. See section 15b.
- **Two opt-in extensions of the density policy (both ini only, both off by default, both ignored by `legacy`).** `GuardReleaseHolds = N` (0 = off, clamped to 600) is the time limit for the design limit above: the fallback ends after N anchor-later presents in a row whose window had at least one fresh sample and none over the release level (a window without a fresh sample, which most are with `ProbeInterval` above 1, counts neither way), even though the 60-sample clean run could not complete while they keep coming. A band sample or a bad frame in such a window restarts the count (the same definition of clean as the clean run), the release is counted separately in the summary line, and the guard trips again by the normal rule. `GuardTripOnAnchorLater = true` removes the two-present wait on such a frame: the present whose own frame is anchored after off-screen UI draws trips the guard itself, so that frame's base is not swapped and the image that would have measured over the limit never reaches the outputs. The trip then ends by the same release rules as a trip the samples caused, so a stream of such frames holds it until `GuardReleaseHolds` (or the 60-sample run) ends it. Both keys start the guard over when their value changes, like a changed policy. Status: unit-tested with replays of the engine core and of the guard, **not tried in a game**.

**Guard limit advisory.** A `CoverageGuard` whose **release level** (`0.75 x the limit`) sits below the HUD's own flagged area trips on the HUD alone and can never let go, which keeps `ui_free` off for the whole session; in one play session a limit of 0.05, sat next to `MaskThreshold` in the same fold, was mistaken for it, and hid `ui_free` for 180 s at 4-9 % coverage. The engine therefore measures the HUD's own flagged area: the **low fifth** of a recent window of the readbacks, `HudCoverageWindow` in `HudlessLogic.h`, the last `512` such readbacks (about 8 s of a 60 fps session). The readbacks it keeps are the ones that can be the HUD: at or below the limit while the guard is not tripped (an over-limit readback is a fade or a preset on its way to tripping the guard, so the excursion samples of a trip never lift the estimate) and **every** readback of a tripped guard, whose probing presents measure the HUD it trips on, so the estimate keeps moving while the guard is stuck instead of freezing at the level of the un-tripped past. A `MaskThreshold` or `MaskDilation` change starts the window over (those readbacks were measured on another mask). From 30 readbacks on the low fifth is compared, before that the a-priori flagged area of 15 %. A limit whose release level is below it warns in two places and nowhere else: one line next to the coverage guard slider (with the numbers, where they came from, and the smallest limit that releases), and one line in the log per **change** of the warning once that change has held for 500 ms (a drag across the area writes one line, not one pair per crossing; never per frame; `GuardAdvisory`, `GuardAdvisoryMenuLine`, `GuardAdvisoryLogLine` in `HudlessLogic.h`). A limit of 0 = off never warns. The value the user set is never rewritten. The HUD-less status line shows the limit in force and its release level, and while tripped why it falls back: `guard limit 60%, release below 45%` or `over the guard limit 5%, falling back; release below 3.8%`; the density policy words it as the clean run it needs (`releases after 60 clean readbacks at or below ...`, `GuardStatusLine`). The status block also shows the HUD's own flagged area (`HUD's own flagged area: 9.0% (low fifth of 412 readbacks)`) so the guard can be set against a number before anything warns, and one short line points at the warning while it is on. Those lines are the first things to read when `ui_free` never runs: a limit of 0.05 releases only at or below 3.75 %, below the HUD's own 9 %, and 0.60 releases at 45 %, far above it.

**Paste hold.** When the base goes from the hud-less image back to the normal one (the guard trips, the boundary is lost, a swap is refused), the first output of that present is generated from the previous hud-less frame and the new normal frame; in a fade these differ everywhere. The paste hides that blend only while the ring is valid, so the paste stays visible (`Core::PasteVisible()`, `UiPaste::SetPasteEnabled`) for `kLeaveHold = 2` presents after the last swapped one. A present without a capture in that window gets `PasteAction::Hold`: the ring is neither produced nor invalidated. After the window it is `Invalidate` as before, and probing presents are not drawn (they still build images for the guard). Before the first swapped present nothing is held, a swap the host undid grants no hold, and a mode change resets the hold.

**The tint while the guard is tripped (`ShowDetectedUi`).** The debug tint is a constant of the paste draw, and while the guard is tripped nothing is swapped, so the tint had nothing to draw exactly in the state a diagnostic run is about (a session reported "the tint showed nothing" for that reason). The output gate is `Core::PasteGate(tint)` = `PasteVisible()`, or with the tint on a present that produces a paste image (`PasteGateOpen`); a present that only invalidates the ring opens no gate (it has no image to draw and its outputs would all count as skipped pastes), and every other mode is closed. **What it draws while tripped is the paste, not a blend**: the draw has no blend state, so where the newest completed real frame has flagged pixels the output pixel *is* that image's pixel, with the magenta tint over it. In the flagged region the output therefore comes from the newest **real** frame: it is not a generated frame there, so that region runs at the real frame rate and carries the judder the fallback already has (in a bad state the flagged share is most of the screen). The rest of the screen is the normal base, which carries its own UI. With the tint off the gate is `PasteVisible()` exactly and the output behaviour is the same as before. Debug only: the value is per config load, the tint shows the mask in force, and it is not a view to play with.

**Never** produce a black, partial or flickering frame: every failure path leaves the normal backbuffer copy as the FG base, and the paste ring is invalidated (`UiPaste::Invalidate`) except during the hold and while probing.

### Periodic summary log (judging a play session from the log)

Every 600 real presents, same style as the scene-HDR line:

```
HudLess: mode ui_free, state Active; 600 presents: 598 captured, 2 fallbacks (SlotBusy 1, NoBoundaryThisFrame 1); mask coverage avg 4.1% max 9.7%; amplitude 0.008/0.05/0.2 avg 3.9/2.1/0.4% max 9.2/5.0/1.1%; paste built 598 pasted 1190 skipped 6; slot waits 0; boundary: ok; guard trips 0 releases 0 (0 by release limit); swapped bad frames 0; anchor-later 74 of 598 frames (12.4%), longest run 31; tag changes 2
```

Plus one line at every state change (`HudLess: state Searching -> Active`, `... -> Fallback(MaskCoverage)`).

All numbers are per window of 600 presents.

A second line, `HudLess paste cadence (10.0 s): ...`, is written about every 10 s while the paste is drawn (log only, no decision reads it): how many outputs got the UI pasted and how many paste images were built, how often the newest image was still on the GPU when an output picked one, the age of the pasted image in real frames, how many outputs each image was shown on (with M outputs per real frame a steady UI shows every image on exactly M), and the real frames whose image was never shown. A pause in the pasting longer than a second (a fallback) ends the window at its last paste.

- `mask coverage`: share of the picture the mask flagged at `MaskThreshold`, averaged and at its maximum over the fresh readbacks of the window (a readback only counts as a sample once). `n/a` when no readback completed (recomposition mode). This is the guard's number.
- `amplitude 0.008/0.05/0.2`: of the same samples, the share of the picture whose windowed per-channel difference reaches each of the three fixed levels, averaged and at its maximum (section 7). They do not follow `MaskThreshold`, so two sessions or two settings can be compared; a high 0.008 share with a low 0.2 share means the flagged area is a low-amplitude difference, not a bright UI. No decision reads them.

The fields after `boundary` only watch too: no decision reads them.

- `guard trips` / `releases`: how often the coverage guard started and ended a trip (a release by starvation counts). The number in front of `by release limit` says how many of the releases `GuardReleaseHolds`' time limit ended.
- `swapped bad frames`: swapped bases whose own paste image measured over `CoverageGuard`. Each image's coverage is read back about two presents after it was built; the count is made when that readback arrives, against the base state of the present that built the image. 0 with `CoverageGuard = 0`.
- `anchor-later A of T frames`: of the T presents that asked the boundary for a frame, A had their first backbuffer UI draw preceded by UI draws into another render target (the same `r1 != r1b` test as the boundary line's `anchor after off-screen UI draws`, answered by the boundary for the same frame). `longest run` is the longest string of consecutive such presents inside the window.
- `tag changes`: presents whose set of tags sent to the frame generator (hud-less, UI image) differs from the previous present's. A present that sent nothing is the empty set.

## 6. Interop and synchronisation

- **Ring:** one slot per FG buffer (`BUFFER_COUNT`, keyed like the bridge's fake index). A slot = a shared-NT-handle D3D11 texture (typed, RGBA8 or the capture's format), the opened D3D12 resource, and the D3D12 value of the last queue operation that reads it.
- **Rule:** the D3D11 side may write slot i at Present N only if the D3D12 reader fence has **completed** that slot's last read (non-blocking `GetCompletedValue`). Otherwise this frame has no hud-less (`SlotBusy`). The import base reuses slots guarded only by the copy-allocator fence while FG-queue readers (the DLSS-G tag and the paste producer) are not fenced **(inferred)**; this design fences them.
- **Ordering across APIs:** the hud-less copy is recorded on the D3D11 context before the existing D3D11 -> D3D12 signal, so the single existing `_WaitDx11ThenDx12` covers both copies (the import base does the same).
- **Paste images:** 4 slots; the producer reuses a slot once its own write and its last paste completed and no paste picked it in the meantime (`ring::Writable`; a pending cleanup read by a later producer pass does not hold it back, because that read and the new write are queued in order on the same queue), and never waits on the GPU; a retired image is destroyed only when, in addition, the last producer pass that read it as its cleanup input completed (`ring::Idle`); the consumer picks the newest COMPLETED image, at most 250 ms old, never older than the last one pasted.
- **Lifetime:** nothing is destroyed while the GPU may still read it; teardown retires resources behind the GPU fence (existing `GpuLifetime`).

## 7. UI mask and paste algorithms (reference: `UE_Common.h` and `UiPaste.cpp` of the import base; the values are its tuned defaults)

Per pixel `p` of the real frame, with `F` = final image, `H` = UI-free image:

- difference `d(p) = max(|F.r-H.r|, |F.g-H.g|, |F.b-H.b|)`;
- `isUi(p)` = any pixel within the square window of radius `dilation` (clamped to the image) has `d > threshold`;
- amplitude counters: the same windowed difference is also counted at three fixed levels, `d > 0.008`, `d > 0.05` and `d > 0.2`, whatever `threshold` is. They are per channel, 0..1, on the SDR pair (`F` and `H` as the mask sees them) and they only measure: the guard, the paste and the tags still use `threshold` alone. Each pixel counts in the highest level it reaches, so the three shares the log prints are nested (a 0.2 share is part of the 0.05 share, and that one is part of the 0.008 share). They answer the question `mask coverage` alone cannot: how much of the flagged area is a low-amplitude difference (a few steps per channel, as a fade or a tiny tint gives) and how much is a bright or structured UI;
- paste image: `isUi` -> `(F.rgb, 1.0)`; else if cleanup is on and the previous paste image had alpha > 0.75 here -> `(F.rgb, 0.5)` (clears ghosts of UI that just closed); else `(0,0,0,0)`.
- Paste draw: full-screen triangle over the backbuffer, `discard` when alpha <= 0, output alpha 1, **no blend state** (pasted pixels overwrite).
- Recomposition mode: `UiImage` writes `(F.rgb, 1)` or `(0,0,0,0)`, alpha strictly 0 or 1 (valid for premultiplied and straight consumers), R8G8B8A8_UNORM.
- Known limit: full-screen black/white fades differ from the UI-free frame everywhere and read as UI (the coverage guard trips and the engine keeps the normal base while it probes; section 5). Nameplates can look displaced at low FPS because the held UI and the generated scene represent different times (from that fork's documentation, unverified here).

## 8. HDR

The tested HDR setup is OptiHDR with scene HDR (`[HDR] Mode = 1`, `FfxivHDR`, NR/DLSS scene input). The design follows the documentation of the import base, which describes SDR and HDR gameplay tests of its own hud-less path; it is not re-verified here:

1. The UI-free capture and the mask are **SDR** (the game's native SDR chain).
2. The FG base in HDR is the hud-less image converted by the production OptiHDR converter (`Hdr10::Convert`, same call the bridge already makes on its copy source).
3. The paste needs the converted **final** image too (one extra convert per real frame in `ui_free` + HDR). Paste storage in HDR: `R10G10B10A2` PQ with the three-level alpha.
4. **Scene HDR priority:** on frames where `ISceneHdr::Open(presentation=true)` supplies a scene, the existing mode-1 HudlessColor re-tag (`BridgeHdr.cpp` ~94-117) keeps ownership: the engine does not swap the base on that frame (`SceneHdrOwnsFrame`) and invalidates the paste. These frames were rare in the last HDR test run (the DLSS scene-HDR path alternated native-HDR and SDR-fallback periods; the Present-path counter showed 2 imports in 1,800 requests). Revisit with data from a second HDR diagnostic run.
5. HDR10 output is carried by `ui_free` only (items 2 and 3). `recomposition` over HDR output is refused with `FormatUnsupported` (`ext/hudless/HudlessCore.h`): it would need a PQ UI image that DLSS-G refuses and a hud-less tag converted to PQ. HDR output is detected only through OptiHDR (`ext/hdr` sets the bridge's `hdrOutput` when it configures the frame generation swapchain); a game that reaches HDR10 by another route (for example FFXIV's own in-game HDR10 setting) is treated as SDR, so any refusal there comes from the format checks below; untested. `FormatUnsupported` is also returned when the captured UI-free image and the bridge's backbuffer copy differ in format (`HudlessEngine.cpp`, capture validation), and on SDR output when the frame generation swapchain format differs from the hud-less slot's at the base swap.

### 9.3 Tag slot

The tag slot must be the slot the provider's own Dispatch will use (next subsection).

### 9.4 Dispatch index (a pre-existing mismatch the engine must not trip over)

`IFGFeature::GetIndexWillBeDispatched()` (predictor, stateless) and `GetDispatchIndex()` (consumer, writes `_lastDispatchedFrame`, returns -1 for an already-dispatched frame) disagree in the resync branch **(read 2026-10-16)**: the consumer tests `HasResource(Depth|Velocity|UIColor|HudlessColor, GetIndex())`, the predictor only `HasResource(Depth)`. With a frame that carries only hud-less/UI resources the tag can land one frame off.

- The bridge must **not** call `GetDispatchIndex` (it would consume the frame and make the provider skip it).
- Fix: make the predictor mirror the consumer's resync predicate exactly (same four resource types, same index), still stateless. This is a small upstream-file edit (~6 lines) and an upstream-candidate fix. It comes with a unit test (`framegen` has none today, so the test slices the two functions the way `nr_reuse_api` slices production code) and is recorded as `[UP]` if it stays generic.
- If the mirror cannot be made exact, the fallback design is tagging at a dispatch-time seam right after the provider's own `GetDispatchIndex` call.

## 10. FFXIV boundary detector (`ext/ffxiv/ui/`, work package A)

**Hook consumer, no new Detours.** `FfxivLightingCapture.h` already hooks `CreatePixelShader`, `CreateInputLayout`, all draw entry points and `CopyResource` on the immediate context (`Around()` is the central draw wrapper, `inside` guards re-entry). A adds one early line at the top of `Around()` guarded by `ext::hudless::Wanted()` (an atomic) and one call in `CreateShader` that forwards the bytecode to `ui::TagShader`. Only the immediate context is hooked **(read)**; whether the game ever uses deferred contexts is measured by D1.

**Stage information in SDR.** The scene-HDR stage tagger (`FfxivSceneHdr::Tag`, CRC -> stage 1..5, `FfxivHdrPreview::Tag` -> stage 6) runs at shader creation unconditionally, so the tags exist in SDR; but `FfxivSceneHdr::AfterDraw` (which tracks them) runs only when HDR is requested (`Active() && hdrOutputActive`). A therefore reads the stage tag straight from the pixel shader's private data per draw (one `PSGetShader` + `GetPrivateData`, only when `Wanted()`), and keeps its own per-frame tracking: draw ordinal, last scene/post stage seen (CRCs: 0x85E777EF tonemap=1, 0xF8F57F0A post-tonemap pre-LUT=2, 0x27EBC404 LUT=3, 0x1F264D17 LUT=4, 0xF6E81A1B fullscreen gamma=5), UI-tagged draws.

**UI shader set (starting point).** The seven CRCs of the HDR "UI only" stage (3865947726, 2966694105, 3759127293, 1898885941, 4076256744, 3915247300, 1823062889). They are transmittance-related and may not cover every UI draw, and a shader created before the hook installs is never tagged; D1 measures both.

**Boundary rule candidates (the diagnostic build D1 compared them; R1b is the live rule):**
- **R1 (tag-based):** first draw whose pixel shader carries the UI tag, after the last scene/post stage of the frame.
- **R2 (position-based, hash-independent):** first draw after the last stage-5 (fullscreen gamma) draw whose render target is the backbuffer.
- **R3:** R1 or R2, whichever fires first (union), if neither alone is reliable.
- **R1b (live rule, decided from the first diagnostic run, 2026-10-16):** the first UI-tagged draw after the last scene/post stage whose bound render target IS the full-size RGBA8 backbuffer. Draws into other render targets before it are skipped, not rejected. The 352x352 B8G8R8A8 target is an off-screen UI target drawn in every in-world frame, right after the post-process tail and before the HUD (probably the minimap; it is not a character preview: the fork's own preview targets are 576x960); a 1024x1024 one appears now and then. R2/R3 never fire in FFXIV and are diagnostics only.
- **Early anchor (`[HudLess] AnchorRule = early`, live, Advanced combo "UI-free capture point"; default `r1b` = the rule above; unit-tested, not tried in a game).** Why (the association is observed, the cause inferred: the draw that spoils the late capture is not identified, and a full-screen layer that only the final frame has is not ruled out): in a city (Tuliyollal, 2026-10-30) most frames have no UI draw into the backbuffer before the off-screen block, so R1b falls on the first HUD draw, 19 draws after the last scene stage instead of 3, after the off-screen block and the untagged draws that follow it. On those frames the mask flagged 77 to 90 % of the picture, while frames of the same session whose first UI draw went to the backbuffer read the HUD's own 9 to 10 %. In normal frames the block and the untagged draws after it come after the capture; in those frames they come before it. Rule: on a frame whose R1 (the first UI-tagged draw after the last scene/post stage) goes to a render target that is not the backbuffer, the live source captures at R1, before that draw runs, by copying the swapchain backbuffer, and R1b of that frame then does nothing. The backbuffer is fetched from the bridge's swapchain by the same choice of chain the detector uses for its pointer identity, held for the copy only (never across a draw), and must be that very texture; the render-target guard checks its size, format and sample count. ReShade: at R1 the bound target is the off-screen one, so presets cannot be applied in place there. The source therefore asks what the effects call would return (`ext::reshade::PresetsWouldApply`: the same checks as the call, without calling ReShade or counting a call; it shares the call's cached runtime choice and technique count, so on a frame kept on R1b the techniques are recounted twice as often, and the boundary's own call counters do not see early frames) and takes the early capture only when it would apply nothing (`ReShadePresets = off`, no ReShade, no runtime, nothing to apply). With presets to apply, or a call that would fail, the frame keeps R1b, so the presets stay where they always run and ReShade's own end-of-frame pass is skipped on the same frames as before. On an early frame no effects call is made, and the predicted result is counted as that boundary's effects result in the summary. A later scene/post stage that drops R1 before any UI draw reached the backbuffer takes the early action back (nothing was applied there; every counter it moved is undone) and the frame acts again at its next R1 off-screen or R1b, as it would without the key (`re-armed`); one that drops the R1b that followed rejects the frame (`Superseded`, as on R1b). `SkipNextCopy` works as on R1b: the frame is acted on and nothing is copied. A frame that draws no UI into the backbuffer after the early capture is not delivered (`no boundary in this frame`, counted under "UI only off the backbuffer", as without the key: the counters its early action moved are taken back at the end of the frame, and only the early detail counts it, under `off-screen only`; its copy was made for nothing). Any doubt (no backbuffer identity, a failed fetch, another texture, the guard, no snapshot texture) leaves the frame to R1b untouched. Frames whose first UI draw goes to the backbuffer take the R1b path whatever the key says. The same-frame fact handed to the engine (`anchoredAfterOffscreenUi`) and the anchor-later counters stay `r1 != r1b`. Both HUD-less modes use this capture (`recomposition` tags it as the hud-less image). The coverage guard runs only in `ui_free`: in `recomposition` nothing checks the content of an early image, only its size and format, so a wrong one (for example from an R1 into a full-size target that is not the backbuffer, which also takes the early copy) goes to DLSS-G as it is. Try `early` in `ui_free` first. Log: the boundary's 600-frame line (`FFXIV UI boundary: N frames: captured ...`) gains `, early anchors N` (frames captured at R1 from the backbuffer) after `copy skipped by the engine N`; once the early rule has run, that field is followed by `(re-armed N, off-screen only N; declined: backbuffer unknown N, presets N, fetch N, target N, texture N)`, the take-backs, the early frames that drew no UI into the backbuffer afterwards and, per cause in the order of the checks, the off-screen R1 draws where the early capture was not taken (no backbuffer identity or size, presets that would run or fail, a fetch that failed or named another texture, the render-target guard, no snapshot texture), so `early anchors 0` in a game says why; and `FFXIV UI boundary: AnchorRule r1b -> early` is written once for each change of the rule in force (menu or ini). Not covered: a frame with an empty early layer and no off-screen block keeps the late capture (R1 == R1b there). Risk: post-tail draws that come after the off-screen block (seen on 2026-10-28) are missing from an early capture, so the mask can read wide on such frames and the coverage guard falls back, as today.
The capture: before the boundary draw executes, `OMGetRenderTargets` -> RTV 0 resource; require single sample, non-array, same size as the swapchain backbuffer; copy into the reused snapshot texture. D1 logs identity/size/format of that RT against the backbuffer (the engine ring assumes the capture matches the bridge copy source).

**Arming and frame hooks (who owns which lines).** Package A's `Armed()` is `[HudLess] Diagnostics` (its own small binder `ext/ffxiv/ui/UiConfig`, same ini section as the engine's keys) **or** `ext::hudless::Wanted()`; `IHudlessSource::Active()` returns `Armed()`. The diagnostic build (package A alone) therefore arms from `Diagnostics = true` without any engine code. Package A owns the bridge's `ext::dx11bridge::PresentScope` in `ext/hdr/BridgeHdr.cpp` (constructor runs at bridge `Present` entry, destructor at every exit): the constructor runs the ReShade/Dalamud probe and the per-frame bookkeeping, the destructor calls `ext::game::Current().hudless->EndFrame()` when the pointer is non-null. **The engine (package B) must not call `EndFrame()` and must not edit `PresentScope`.**

**Exclusions:** draws issued under `ext::core::BypassScope` (`HooksBypassed()`) are ignored.

**Cost:** with `Mode = off` the added code is one atomic load per draw. With the feature on, the per-draw cost is a pointer test plus `GetPrivateData` on candidate draws only; D1 reports draws per frame and hook ticks per frame.

### 12.1 Developer probes (log only)

Two probes measure what frame generation delivers and which UI draws could be nameplates, so that drawing the nameplates at the full output rate can be judged from data before anything is built. Both are developer-only, off by default and change nothing in the frame: they read, they never draw, bind, copy or wait on the GPU. With the keys off the behaviour and the cost are what they were (no hook is added, nothing is allocated, no file is made).

| Key (`[HudLess]`, ini only, no menu control) | Default | Meaning |
|---|---|---|
| `PlateDiagnostics` | `false` | master switch of the probes; set it before the game starts |

Output goes to `OptiScaler\plate-probe\<run>\` next to the game (the five newest runs are kept). A write failure switches the probes off with one warning in the log.

**Output probe.** The output hook runs once per output present, on the presenting thread(s); the bridge present runs once per real frame on the game thread, and the multiplier of that frame is known when the frame generator is dispatched, right after it (DLSS-G with a fixed multiplier: generated frames + 1; dynamic mode: unknown). All three push raw timestamped events into a lock-free ring (a full ring drops the new event and counts it); a writer thread merges them in QPC order, holding the newest 100 ms back so a late push cannot read as lag, and runs the accounting. The probe has its own feature bit: it does not turn the HUD-less engine on and never reaches it.

- `outputs.csv`, one row per output present: `qpc,t_ms,thread,back_buffer,window,batch,index,multiplier,lag_posts,lag_ms,since_prev_ms,ticks_since_post`. `window` is the real frame whose present opened the interval the output arrived in; `batch` and `index` give the real frame the output belongs to by order (first in, first out) and its position in it; `lag_posts` is how many real frames were posted between that frame and the output; `ticks_since_post` is the raw QPC ticks from the present that opened the window to the output (-1 before the first one). Capped at 48 MiB (the summary line goes on).
- Summary line every 10 s: `Plate probe: outputs N, batches B, batches with count == M X% (E of K judged, T settling, U without M), count histogram {n:windows,...}, threads {id:outputs,...}, max lag (outputs seen after the next Post) L posts, ... ms, ... late outputs (this interval: ... posts, ... ms, ... late), order check first-output lag {...} (this interval {...}), pushed out of order ..., late events ..., posts P, options per Post R, options orphaned O, options on the Post's thread X% (S of N), options delay after Post mean D ms, max M ms (Post interval mean I ms), resets Z, probe drops D` and then the draw probe's tail (below). The lag values exist twice: for the whole run, and for the time since the previous line ("this interval"), so one start-up glitch does not hide how the pacer behaves later. A "batch" there is the outputs that arrive between one real-frame present and the next, counted from the stream itself, so a dropped or a bunched output lowers the percentage and shows in the histogram. The first three batches after a start, a reset or a multiplier change are not judged (the pacer can trail by two). "Options per Post" should read 1.00: it checks that the multiplier is noted once per real frame. The next three fields check that it is noted for the right frame: the multiplier is tagged to the latest real-frame present when it is noted, which is right only if the frame generator is dispatched after that present, on the same thread. "Options on the Post's thread" should read 100%, "orphaned" 0, and the mean delay after the present should be a small fraction of the mean present interval; a delay close to one interval means the multiplier is noted a frame late (and a constant multiplier would hide it). "Probe drops" is the ring overflowing, never a pacer drop.
- Not measured: which output of a batch is the real one (that would need a pixel compare on the present path); batch order is judged from PresentMon and the log.

**Draw probe.** Reads the D3D11 state of every draw through the existing draw hooks (CPU side Get calls; the detector is armed while the key is on, a few milliseconds per frame). The probe reads no game packets: every logged row counts as no-packet (an indexed draw) or not-indexed, see the summary tail below.

- `draws.csv`: rows for the first 600 frames, then every 100th frame, for draws that are UI-stage or come after the first UI draw of the frame, plus draws that satisfy rule r0 whatever their phase (at most 400 rows per frame; a priority row, that is a row that satisfies rule r0, goes on up to 1200 rows per frame, so the rows the probe is about are not the ones that get dropped). A frame that lost rows gets a comment row after its rows, `# frame N capped at 400 rows, M draws dropped`, and, if even the priority limit was reached, `# frame N priority limit 1200 reached, P r0 draws dropped`; an analysis tool skips every line that starts with `#`. Without that line, "r0 never fires" in a busy in-world frame could be a dropped row rather than a fact. Caps per run: 6 MiB for frames 1..600 (title and loading screens) and 40 MiB for the later sampled frames, so the menus cannot use up the room the in-world samples need. Columns: `frame,draw,vs,ps,stage,kind,index_count,instance_count,start_index,base_vertex,topology,stride,rt,rt_w,rt_h,rt_fmt,vp_w,vp_h,dsv,depth,depth_write,depth_func,stencil,blend,src,dst,op,src_a,dst_a,srvs,r0`. `vs`/`ps` are the CRC32 of the bytecode (`pre#N` for a shader created before the hook); `srvs` are `slot:id/WxH/format` of the first four pixel shader textures (`id` counts textures in order of first sight within the run); `vp_w` and `vp_h` are still logged. The probe reads no game packets, so there are no packet columns (no batch, queue key, vertex box or interception marker).
- Packet association (logged frames only). No packet source is hooked up: the game's UI batch functions, its draw command enqueue and its draw state bind are not detoured, so no packet record is ever bound to a draw. Every logged row counts as no-packet (an indexed draw) or not-indexed; the summary tail below counts the outcomes.
- Where POSITION sits in the vertex comes from the input layout the draw is bound with, and only the layouts of the three nameplate vertex shaders are tagged with it (the lighting hooks tag them when they are created, and the catalog counts them for its nameplate health). No box is resolved or logged; the tagging stays for the catalog, not for the rows.
- The tail of the `Plate probe:` summary line counts what happened to the logged rows: `, draw rows R (not indexed I, with packet A, no packet N, rejected J {stale:a, changed:b, mismatch:c}), box from vertices B, without box U {untagged:a, strides:b, norun:c, nonfinite:d}, records made M, refused {capacity:x, read:y, busy:z}, indices outside packets W, rows capped C (frames F), priority rows lost P, batch cut K of R, header cap hit H`. Every logged row is exactly one of: not an indexed draw (no packet can sit behind it), with a packet, without one (nothing was bound to it, or the indices of its record reached no packet), or rejected (`stale`: the record was older than 250 ms; `changed`: the command's bytes changed between enqueue and bind; `mismatch`: the draw was not the draw of the record). `without box` splits an associated row that has no box into its one reason: `untagged` (the draw's input layout carries no position tag), `strides` (the strides of the packets, of the renderer's slot and of the bound vertex buffer do not agree, or the layout does not fit them), `norun` (no vertex bytes were copied for the draw, or they do not fit the vertices it uses), `nonfinite` (every used vertex has a position that is not a finite number). `rows capped` is how many rows the per-frame row cap of `draws.csv` refused over the run, in `frames` frames, and `priority rows lost` how many of them were priority rows (the second limit was reached; any value above 0 means the cap may have hidden an r0 row). `batch cut` is how many of the `R` batch calls whose packets were looked at (frames of the schedule only) ran out of probe time, either before all their headers were read (the batch is then not used at all and its draws read `0` and `-`) or later, while it enqueued its draws (the batch stays in use and only the draws after that point get no record); the counter does not tell the two apart. `header cap hit` is how many listed more than 2048 packets and were not read at all (see "Packet association"). `refused` counts records that were not made (`capacity`: the limits above; `read`: game memory could not be read; `busy`: the map was in use). Every row is without a packet: no packet source is hooked up, so `no packet` counts every indexed row and `rejected` stays zero. The line is also printed when only the draw probe has something to say (frame generation off).
- Rule r0 (`r0` column): depth view bound, depth test on with `GREATER_EQUAL`, no depth write, no stencil, drawn into the backbuffer or a texture of its size and format. A missing depth-stencil state is the D3D11 default (`LESS`, writes on) and never matches.
- `shaders-plate.csv`, rewritten at frames 120, 600 and every 1800: per pixel shader, draws and r0 draws in the early frames (1..600) and in the world frames (later), frames with at least one, the most in one frame, and draws by render target class. Compare a run with nameplates off against one with them on: the `world_r0` columns of the nameplate shaders should differ.

Status: unit-tested (accounting, formats, ring, rule r0, seam routing, wiring pins, no-packet association and box arithmetic, overlay mapping), not tried in a game. Not verified without the game: what the box units would be, and which draws carry a tagged layout.

## 15. What the diagnostic runs answered

1. ReShade runs outermost on the game's D3D11 swapchain, before the bridge copy (section 16).
2. The boundary rule that works is R1b (section 10). R2 and R3 never fire and are not used.
3. UI shaders are stamped at creation whether or not the detector is armed, so a Mode switched on after the game loaded still finds the boundary.
4. Dalamud overlays are drawn into the frame before the bridge copy, so they count as UI.
5. The hook costs about 0.16 ms per frame in a city scene.
6. `render_effects` applied in place at the boundary works and restores state; ReShade's own end-of-frame pass is then skipped for that frame.

## 15a. Status and known limits

- Tested in SDR with DLSS-G 2x to 4x on an RTX 4090: the engine stays Active on 96 to 100 % of presents in normal scenes and falls back (by design) on title screens, loading screens and fades. The author saw no visible difference against `Mode = off`, so treat the benefit as unproven.
- HDR output with `ui_free` is untested. FSR-FG and XeFG only receive tags and are untested. The paste producer cannot start under HDR output as the code stands (**inferred from reading, not run**): its first image needs the slot's PQ conversion resources, which are only prepared once a paste image already exists (`PasteReady`); only the probing path prepares them itself. `[HudLess] HdrPaste = on` removes that deadlock (section 15b); it is off by default.
- Guard rework (silent probe, release at 0.75 x the limit after 30 samples, two-present paste hold, hud-less tag only on swapped presents; section 5). It targets a flash at the start and end of fades and loading screens and a flicker of cutscene text boxes that appeared with `ui_free` and not with `Mode = off`. In game on 2026-10-18 (cutscenes, fades, dialogue boxes and busy gameplay) neither appeared: Active periods of 212 s, 129 s and 384 s, only short (0.4-2 s) Fallback dips at fades, no flapping on high-coverage cutscene frames. Probing builds the capture and the paste image on the probing present during a fade (one present in `ProbeInterval` while the guard is tripped, so every present only with `ProbeInterval = 1`; **inferred**: about the GPU cost of an Active present).
- One GPU hang (`DXGI_ERROR_DEVICE_HUNG`) happened shortly after the Mode was switched off, on and off again within about seven seconds, at 6x frame generation (the experimental RTX 40 MFG unlock). The same switching at 2x to 4x ran 24 times without a problem. The cause was not isolated.
- **A switch of Mode away from `ui_free` could fault the GPU (found 2026-10-30, fixed).** Each paste image pass reads the previous image as its cleanup input, and that read was not recorded: the retire on a mode change (or a resize) destroyed the previous image as soon as its own write and its pastes had completed, while the newest pass, queued behind the frame on the GPU, was about to read it. In a game the driver reset the GPU 31 ms after `HudLess: mode off, releasing the hud-less slots` (three driver resets, a watchdog report, the game closed 10 s later); in the fallback nothing is pasted, so no paste read kept that image alive. The read is now recorded with the pass's fence value, and a retired image is destroyed only when nothing still writes or reads it, that cleanup read included (`ring::Idle` in `UiPasteRing.h`); reusing a slot for the next write needs only its own write and pastes done (`ring::Writable`: the pending cleanup read is queued before that write on the same queue). The 6x hang above happened after the same kind of switch and is probably the same fault (not re-tested).
- **`ui_free` can sit in fallback for a whole session (observed 2026-10-22).** In one SDR session on an RTX 4090 (Performance, DLSS-G 2x) the engine reported `Fallback(MaskCoverage)` for most windows: `600 presents: 154 captured, 446 fallbacks (MaskCoverage 444, ...); mask coverage avg 73.6% max 99.5%`, and in one window `0 captured, 600 fallbacks (MaskCoverage 600); mask coverage avg 100.0%`. The mask compares the final frame with the UI-free capture and counts the pixels that differ. When it covers almost everything, the guard correctly refuses to paste, and frame generation runs on the full frame with NVIDIA's UI recomposition off (`AdjustUiRecomposition ... false (HudLess mode ui_free ...)`). A faint micro-stutter was seen in motion with frame generation on. Switching live to `Mode = recomposition` gave `state Active; 600 presents: 600 captured, 0 fallbacks` and no artifact. The cause of the wide mask in that scene is not known (inferred candidates: something applied between the capture point and the final frame that changes most pixels, or a capture/paste timing offset; nothing was measured). Until this is investigated, use `recomposition`.
- **`ui_free` has a known micro-stutter; the default probe interval removes it in the one session it was compared (2026-10-30 and 2026-10-31).** The user saw it on v0.3.0, on v0.4.0 and on a test build of this line, with DLSS-G preset Auto and with preset C; it was gone with `Mode = recomposition` and `[DLSSG] RenderPreset = auto`, which the author confirmed again on 2026-10-30. On 2026-10-31, v0.5.0 in game with preset C, setting `[HudLess] ProbeInterval` from 1 to 8 during play made the stutter go away and setting it back to 1 brought it back, so the default is now 8 (section 5). That is one session with one preset: the per-present probe is the suspected cause, not a measured one, and `ui_free` stays experimental. Use `recomposition` with preset auto for the safe setup.
- **Recomposition and the DLSS-G preset.** With preset A or C, NVIDIA's runtime forces its UI recomposition off (verified in nvngx_dlssg 310.9.16, `ApplyRenderPreset`). The fork therefore requests recomposition only with Auto or B, from the first DLSS-G option call (`ext/fg/dlssg/UiRecompositionRule.h`). Before that rule, a boot with `recomposition` and `RenderPreset = 3` created DLSS-G with the option on and paused it 0.09 s later. That forced a recreation, after which only about 59 of about 132 presents per second were distinct on screen. With the rule, the log shows `AdjustUiRecomposition DLSSG UI recomposition: false (... dropped by the DLSS-G render preset (Preset C))` once and the sentence `Preset C turns NVIDIA's UI recomposition off on this runtime ...` once, and the engine reports `Fallback(PausedByPreset)`. The rule remembers whether the preset control exists once, at the first time the runtime asks the driver for its preset or at the first DLSS-G option call, whichever comes first. Known gap (not seen, and not on an RTX 40 setup): if the boot latched the RTX 20/30 runtime and the user later unticks it, a live switch to A or C is allowed while the rule still reads Auto.
- The capture is refused, with a one-line reason in `OptiScaler.log` (`HudLess: the UI-free capture was refused: ...`), if the capture and the bridge copy differ in device, size or format.

## 15b. Counters and opt-in keys for the `ui_free` stability work

The four keys of this section are ini only (no menu control) and default to the behaviour described above. Status: **unit-tested with replays of the engine core and of the guard, not tried in a game.**

**What the saved sessions showed.** Over 190 windows of 600 presents from 13 `ui_free` sessions, the share of anchor-later frames followed the mask coverage (mask coverage average about 15.8 % plus 0.84 x the share in percent, Pearson 0.86, fitted over the 179 windows that are not lobby or loading screens; 0.67 over all 190), and the relation held with ReShade disabled. Of the 153 windows with a share of 10 % or more, 150 follow the line and 3 stay flat, which reads as anchor-later content that does no harm. In recomposition-only sessions 2 to 45 % of frames were anchor-later (test sessions; the everyday share is not known), in bursts with minutes at 100 %. What those frames carry that the UI-free capture lacks is not known, so the keys below are mitigations, not a fix, and `ui_free` stays experimental.

**Counters.** The summary line (section 5) now ends with the guard's trips and releases (and how many of those releases the time limit ended), swapped bad frames, the anchor-later share and longest run, and tag-set changes; they only watch. `swapped bad frames` is the number of swapped bases whose own paste image measured over `CoverageGuard`, counted when that readback arrives, about 2 presents after the build (not "frames pasted while the coverage was over the limit"). A recorded stream of decisions (calm play, fades, lost boundaries, every other and every fourth frame bad, bursts of 5 to 60) comes out identical with and without the boundary's same-frame fact, and identical with the two guard options at their defaults.

**Guard policy (`GuardMode = legacy | density`, default `legacy`).** See section 5. In replays of 3,600 presents (one minute at 60 fps), with a frame bad exactly when it is anchor-later, the figures below are the bounds the tests assert, not measurements from a game. With every other frame bad the legacy guard never trips (1 switch) and swaps more than 1,500 bad frames; `density` makes 2 switches and swaps at most 8 bad frames, none after its first trip; with every fourth frame bad legacy swaps more than 700 and `density` at most 8, none after its first trip. The gain on alternating frames is therefore in swapped bad frames, not in switches. With a burst of 5 to 60 bad frames and 35 clean presents between bursts, legacy leaves and re-enters the fallback on every burst (at least 176 switches for the 5-frame burst, at least 70 for the 60-frame one) and `density` stays in it (exactly 2 switches, under a tenth of legacy's). With bursts 200 presents apart (the clean gap exceeds 60 samples) both release between bursts, `density` makes no more switches than legacy, and over five bursts it swaps at most 25 bad frames, no more than legacy (the test asserts `<= 25`; the three bad measurements that trip it plus the two presents the readback takes come to 5 for a burst). Whether the fallback hides the micro-stutter, and how much of a session it spends there, is not measured. Set `GuardMode = density` and compare the `anchor-later` and `guard trips` fields with the window's `captured` count.

**Release limit (`GuardReleaseHolds = N`, default `0` = off) and per-frame trip (`GuardTripOnAnchorLater = true`, default `false`).** See section 5. In replays of 900 presents where three bad measurements trip the guard and an anchor-later frame then comes every 40 presents with clean images: with both keys off the guard stays in the fallback for the rest of the stream (1 trip, 0 releases, 26 anchor-later frames); with `GuardReleaseHolds = 3` the release comes at the third of those frames (present 120) and the base is swapped from that present on; three bad measurements later it trips again and the limit ends that trip too (2 trips, 2 releases, both by the limit). With anchor-later frames from the start and every image clean: with the keys off every present swaps; with `GuardTripOnAnchorLater` the frame at present 40 is not swapped and the guard stays tripped (each frame in every 40 restarts the 60-sample run); with both keys (`GuardReleaseHolds = 1`) exactly the anchor-later frames of an open run are skipped and the release presents swap again (8 trips and 7 releases over 600 presents). These are the bounds the tests assert in the fake engine cycle, not measurements from a game.

**HDR paste (`HdrPaste = off | on`, default `off`).** Under HDR output the paste image is built from a PQ copy of the final frame, and that copy needs the slot's HDR stage. The readiness check creates the stage only after a first paste image exists, and a present that is not probing did not create it before building the image, so the first image was never built and `ui_free` under HDR output stayed on normal frame generation (`PasteNotReady`) (inferred from reading the code, never observed in a game). With `on` the stage is made before the producer on every HDR present (one condition, `EnsureHdrStageBeforeProduce` in `HudlessLogic.h`), and a failed creation of the stage is not tried again on every present: it is latched until the HDR output state or the setting changes, and written to the log once (`HdrStageLatch`). With `off` the old order is kept exactly, retries included. **Status: unit-tested with a fake of the engine's producer step, not tried in a game.** The path it switches on (`BuildHdrFinal`, the PQ conversion of the final frame for the paste) has never run in a game, so it stays opt-in until someone with an HDR display confirms it. Anything other than `on` reads as `off`.


## 16. ReShade integration (built-in add-on; decided 2026-10-16)

**Why:** ReShade 6.8.0 (the tested setup) is outermost on the game's D3D11 swapchain (`ReShade.log`: it "redirects" the game's `CreateSwapChain`, one runtime, on that chain). Its effect pass therefore runs in its Present hook, before the bridge copy, on the full frame including the HUD. A UI-free image snapshotted at the first UI draw is taken before that pass, so without help FG would drop the presets and the difference mask would flag every preset-changed pixel.

**Design (the behaviour of the external REST add-on of the import base, done natively: no REST, marker or extra file):**
1. `ext/reshade/ReShadeAddon`: after OptiScaler loads ReShade (`dllmain.cpp` ~1165-1179, one seam call `ext::reshade::OnReshadeLoaded(module)`), register OptiScaler's own module with `ReShadeRegisterAddon(module, 20)` (header-only registration in ReShade's public API headers, vendored, `BSD-3-Clause OR MIT`) and subscribe to `init_effect_runtime`, `destroy_effect_runtime`, `reshade_begin_effects`, `reshade_finish_effects`, `reshade_present`.
2. At the boundary (package A's detector) call `effect_runtime::render_effects(cmd_list, rtv, rtv_srgb)` for the runtime of the game chain, in place on the scene render target; then snapshot. The HUD is drawn afterwards and is not filtered.
3. Suppress ReShade's own end-of-frame effect pass for that frame so the effects are not applied twice.
4. Engine state: new fallback reasons `ReShadeUnavailable`, `ReShadeEffectsFailed`. Any failure in steps 1-3 means: no presets applied at the boundary, the end-of-frame pass is left alone, the engine falls back to normal full-frame FG (today's behaviour). Never a half-applied frame.
5. The full integration (package E) was built after the diagnostic build answered F1-F5 (below). The probe (package D0) contains only registration, event logging and the guarded probes.

**Feasibility questions F1-F5** (answered by the D1 and D0 builds in the first diagnostic run, written to `reshade-probe.txt`):
- **F1** registration succeeds in-process; the runtime on the game chain appears (device API, hwnd, technique names with enabled state, preset path).
- **F2** `render_effects` can be called in place from a draw-time hook on the immediate context without corrupting game or ReShade state (probe armed from the menu, one frame; compare the render target before/after; run twice).
- **F3** ReShade's end-of-frame pass can be skipped for that frame (event or effects state), checked by counting effect passes per frame.
- **F4** depth-based techniques see valid depth at the boundary (log ReShade's depth-buffer detection state).
- **F5** cost: effects run once per real frame; measured with QPC around the call.

**Not in scope:** HDR-specific ReShade handling (effects stay SDR), ReShade versions other than the tested 6.8.0 (API 20; other versions fail the registration check and fall back).

**Depth events (automatic ReShade scene depth, `[FFXIV] AutomaticReShadeDepth`; see [FEATURES.md](FEATURES.md#automatic-reshade-scene-depth)).** Once the add-on registration is accepted, the depth binder subscribes more ReShade events. At load, right after the registration (`OnReshadeLoaded`) and whatever the option says, five: `init_effect_runtime`, `destroy_effect_runtime`, `reshade_reloaded_effects`, `reshade_set_technique_state` and `reshade_set_current_preset_path` (`LateRegistrationPlanner::kLoadEvents`); `begin_effects` and `finish_effects` are subscribed from inside the `init_effect_runtime` callback (finish first, then begin, so a begin never exists without its finish), which makes them run after the `begin_effects` of REST and Generic Depth (`kRuntimeEvents`). A ReShade that loads later gets all six at once after the late registration (`kEvents`). The callbacks return at once while the binder does not exist yet (the facade is built by the first evaluate with the option on), so the menu switch needs no restart. The begin and finish callbacks sit after Generic Depth's and REST's (see FEATURES.md, Events). After the depth, the same begin realigns the G-buffers that REST binds to NORMALS, DECALS, DECALS_WATER, MOTIONVECTORS and MATERIAL. The callbacks are the depth binder's own free functions in `ext/reshade/ReShadeDepthEvents.cpp`, separate from the boundary tracking and the probe above, which subscribe the same events with callbacks of their own. They need neither `[HudLess] ReShadePresets` nor `ReShadeProbe`, and the boundary `render_effects` call is untouched. Between `begin_effects` and `finish_effects` the `DEPTH` input of the effect runtime points at an output-sized copy of the game's depth made by the DLSS evaluate; `finish_effects` puts the original binding back. A ReShade that loads after OptiScaler (installed as `dxgi.dll`) is looked for again once a second, 60 attempts at most, while the option is on (`ext/reshade/ReShadeDepthLate.cpp`); the registration state is shared with the registration of this section (`ext/reshade/ReShadeRegistrationState.*`).
