# Feature reference

What this fork adds to OptiScaler, where each piece lives, how it attaches to upstream files, and how to configure it. The short status table is in [.github/README.md](../.github/README.md); this file is the long version and uses the same status words.

**Status words.** *tested* means the maintainer played the game with it on an RTX 4090. *untested* means it compiles and follows the same code paths as the tested features, but nobody has verified it on real hardware (or in game) yet. Where a feature runs inside a tested path but was never exercised alone, the entry says so. Nothing here is a promise that a feature works on your system.

**How to read the entries.**

- **Code:** directories and key files under `OptiScaler/ext/`. Every file the fork owns is under `OptiScaler/ext/`.
- **Seams:** the one-line calls in upstream files that reach the fork code, by name. The full list with host files is [SEAMS-catalog.md](SEAMS-catalog.md); the rules are in [SEAMS.md](SEAMS.md).
- **Config:** `[Section] Key` as written in `OptiScaler.ini`. The defaults and the explanation of each key are in the matching fragment under `OptiScaler/ext/ini/`, which `tools/package.ps1` merges into the shipped `OptiScaler.ini`.
- **Menu:** the card in the in-game OptiScaler menu.

## DLSS Neural Rendering (NR)

**What it does.** Runs NVIDIA's DLSS Neural Rendering model on the frame, either before ordinary super resolution (pre-SR) or after it, in one to three passes with per-pass profiles. A colour pipeline maps the game's image into what the model expects and back (white point, exposure, reversible tone mapping). It also contains the exposure scan, which reads the game's exposure from resource creation and unordered-access views, and named user presets.

**Status.** tested (RTX 4090), pre-SR multipass included. Exposure scan, white point, presets, compare views and the debug view are used by the tested sessions but not tested separately. `DeferredDLSS`, `ResidualFG`, spatial compression and `WorkingScale` other than 1.0 are experimental or opt-in and untested.

**Code.**

- `OptiScaler/ext/nr/pass/DlssNr_Dx12.cpp`: the Direct3D 12 pass (compute shaders in `ext/nr/shaders/`, compiled at build time).
- `OptiScaler/ext/nr/presr/`: pre-SR placement, pass profiles, cadence, trail guard, split frame work.
- `OptiScaler/ext/nr/exposure/DlssNr_ExposureScan.cpp`: exposure scan.
- `OptiScaler/ext/nr/NrResampler_Dx12.cpp`: the NR-owned resampler used for `WorkingScale`.
- `OptiScaler/ext/nr/presets/NrUserPresets.h`: named user presets.
- `OptiScaler/ext/nr/forwarder/dlssnr_forwarder.cpp`: the `nvngx.dll_dlssnr.dll` forwarder (second project in `OptiScaler.sln`). The odd file name is deliberate: NVIDIA's model only answers a caller whose module path contains `nvngx.dll`.

**Seams.** nr: `EvalBefore`, `EvalAfter`, `PreSrScope`, `NormalizeDlssPresets`, `WrapNvapi`, `NeedsDlssgRuntime`, `AppendNgxSearchPaths`. restrack: `OnCommandListReset`, `WantsCommandListReset`, `NoteUav`, `NoteResourceCreated`, `WantsResourceCreateHooks`, `OnDeviceHooked`, `ReleaseQueueHook`, `OnFeatureRelease`. dx11bridge: `OnNgxInit`, `OnNgxShutdownBegin`. menu: `MergeBoxes`, `PollShortcuts`, `HandleShortcuts`, `KeybindRows`, `DrawOverlays`, `WantsFrame`, `ShaderTimeRows`. gpu: `ResetCommands`, `ExecuteCommands`.

**Config.** `[DlssNr]` (82 keys): `Enabled`, `DisableOnFocusLoss` (experimental, off by default: pauses NR while the game window is not focused; also read under the name `PauseOnFocusLoss`), `ToggleKey`, `RunBeforeSR`, `Passes`, `PassFeedback`, `Pass2*`, `Pass3*`, `Preset`, `Style`, `Intensity`, `WorkingScale`, `ReversibleMode`, `WhitePointSource`, `ScanAnchors`, `LightingHistory`, `SkinProtection`, `PreSRTrailGuard`, `SplitFrameWork`, `Compare*`, `DebugView`, `Runtime` (which NR model file runs, see "Model version picker" below). `[Hotfix] RenderSizeFromWidthHeight` and `[QualityOverrides] ForcePerfQuality` belong to the FFXIV module.

**Pause on focus loss.** `[DlssNr] DisableOnFocusLoss` (off by default, experimental) pauses NR while the game window is not focused. It covers the D3D12 and D3D11-bridge scene NR and the character preview NR; native Vulkan is not paused. The preview shows its plain image while paused and resumes with a clean history; its paused renders are not counted as fallbacks in the preview card (the card lines say "focus pauses not counted"; the dump keys `nr.fallbacks` and `nr.production.fallbacks` keep their names and also leave focus pauses out), and the log shows `CharaView NR: paused, window not focused` and `CharaView NR: resumed`. `PauseOnFocusLoss` is accepted as another name for `DisableOnFocusLoss` (a copied ini from another build keeps working): it is moved into `DisableOnFocusLoss` when the ini is read and saved back as `auto`; when both are set, `DisableOnFocusLoss` wins. Pausing starts after 1 s without focus (at once when minimised), a little later than the other build, which pauses at once. Status: new; unit-tested, nothing of the preview pause has run in game (the in-game proof needs a visible but unfocused window, not a minimised one).

**Menu.** `dlss_nr` (tab Upscaling), plus an overlay for the compare tags and the exposure-scan lamp, a GPU-time row, and the NR on/off shortcut in the Keybinds list.

**Model version picker (live).** Put each NR model file in its own folder named `OptiScaler\NR.<version>` (digits separated by dots, for example `OptiScaler\NR.310.9\nvngx_dlssnr.dll`) next to the game, beside or instead of the old single `nvngx_dlssnr.dll`. The `NR model version` combo in the Neural Rendering card lists the old file ("Legacy location") and every valid folder with its file version, size and the start of its SHA-256 (computed in the background), and switches the running model without a restart, in the scene and in the character previews. `Automatic` (the default) is the newest version; on a tie the old file wins, and a folder that appears later never moves Automatic by itself (the card's `Rescan` button looks again). A choice that is not installed never falls back to another model: the card says Neural Rendering is unavailable and the pass shows the plain upscaler image until a model is chosen again. Clicks are coalesced (a switch happens 250 ms after the last click). A switch parks the model's features behind their GPU fences, clears the NR history and the bottleneck-reuse state (reuse stays off on the new module until its kernel blob is verified), forgets a failure that the old model caused (a failure of the forwarder, the NGX core, the colour codec or the depth and motion inputs is kept), and loads the new file by its full path; model files are never unloaded, so every model used in a session stays in memory. The old recursive search for `nvngx_dlssnr.dll` skips every folder whose name starts with `NR.`, so a versioned folder is never picked by search order. A failed or partial rescan keeps the previous list and the card says so. Restart is needed only where it physically is: the NGX core's first search path (set once at startup), native Vulkan NR, the hybrid FP4 precision (`Precision=4`) and the AMD bridge; the card says so from the real state. The hybrid FP4 lock is sticky: once `Precision=4` was in use in a session, live switching stays off until the next start, because its prepared weights belong to the device and not to the model file. Config: `[DlssNr] Runtime` (empty or `auto` = newest, `legacy`, or a folder name such as `NR.310.8`); it is not part of the saved NR presets. Log: `DLSS-NR runtime catalog: N candidate(s)`, `DLSS-NR runtime revision N: <id> (<path>), file version ...`, `DLSS-NR runtime generation change`, `NR reuse: runtime switched ...`, `CharaView NR: NR runtime revision N ...`; the SHA-256 of the loaded model is logged only after the card has been opened once (hashing starts then, not at startup, so the default path reads no extra file). Status: new. The catalog, scan, selection, switch, text and glue are unit-tested (including a test that two same-named DLLs in two folders load as two modules when loaded by full path); nothing of it has run in game. Known limits: the first load of a second 276 MB model happens on the render thread and will probably be a hitch; whether NVIDIA's code looks itself up by file name (which would see the first copy loaded) cannot be seen without running two models in game, so the first in-game check compares the two versions' own version lines; the combo shows the request while the status line shows the model actually loaded (they can differ when a create failed or switching is locked, the status line is the truth); a preview stream is rebuilt lazily after a switch; the capability block is bound again to each model by the forwarder's own populate step, which could only be tested with stand-ins. Code: `OptiScaler/ext/nr/runtime/` (`NrRuntimeCatalog.h`, `NrRuntimeScan.h`, `NrRuntimeSelection.h`, `NrRuntimeSwitch.h`, `NrRuntimeCore.h`, `NrRuntime.cpp`, `NrRuntimeText.h`), `ext/nr/pass/DlssNr_Dx12.cpp` (`RuntimeHost`, `PollRuntime`), `ext/ffxiv/chara/CharaNr.cpp` (`SyncRuntime`, `NrPreviewRuntime.h`). Seams: nr `AppendNgxSearchPaths` (body changed, no new seam). Menu: `dlss_nr` card, combo `NR model version` and `Rescan`.

**Needs from you.** NVIDIA's `nvngx_dlssnr.dll`; see [Install](../.github/README.md#install).

## NR native path and ViT capture

**What it does.** The fork drives the NR model's own DLL directly. It records which CUDA entry points the game queried (`WrapNvapi`), identifies the model's CUDA module by size and SHA-256, and can skip repeated vision-transformer launches (`VitEvery`) for a module that has been verified. Unknown modules are never touched: reuse stays off and the log says why.

**Status.** The native path is tested as part of NR. `VitCapture` is a diagnostic that only observes. `VitEvery=2` reuse is untested for speed: it only activates for a module listed as verified in `ext/nr/native/DlssNrModuleProfiles.h`, and is a no-op otherwise. `VitAllowUnverified=true` skips the fingerprint check and can hang the GPU; leave it off.

**Code.** `OptiScaler/ext/nr/native/` (`DlssNrNative.cpp`, `DlssNrModuleProfiles.h`, `DlssNrVitCapture.h`, `DlssNrVitReuse.h`), `OptiScaler/ext/nr/hybrid/`. The capture summariser is `tools/nr-vit-capture-summary.ps1`; how to profile a new model file is in [nr-vit-reuse-profile-runbook.md](nr-vit-reuse-profile-runbook.md).

**Seams.** nr: `WrapNvapi`, `AppendNgxSearchPaths`.

**Config.** `[DlssNr] VitCapture`, `VitFirstPassOnly`, `VitEvery`, `VitAllowUnverified`, `Precision`.

**Menu.** Status text in the `dlss_nr` card.

## Other NR paths

**AMD HIP pre-SR.** Runs the pre-SR pass on AMD devices through a small bridge. Status: untested (community). Code: `OptiScaler/ext/nr/amd/` (`AmdBridge.cpp`, `AmdPreSr.cpp`, shaders). Seams: nr `PreSrScope` (the AMD edit is chosen inside it), restrack `OnDeviceHooked`. Config: none of its own; it follows `[DlssNr] RunBeforeSR`.

**Vulkan NR path.** NR for native Vulkan games, kept for reuse with other games; FFXIV never reaches it. Status: untested. Code: `OptiScaler/ext/nr/vk/`, `OptiScaler/ext/nr/NrResampler_Vk.cpp`. Seams: nr `VkEvalBefore`, `VkEvalAfter`, `VkDeviceExtScope`. Config: follows `[DlssNr]`.

## HDR

All HDR code is under `OptiScaler/ext/hdr/`. The four parts share one set of seams.

**OptiHDR (HDR10 output).** Presents the D3D11 game through OptiScaler's DX12 presenter as HDR10 (R10G10B10A2, PQ). In the default mode the game's SDR image is expanded to HDR. Windows HDR must be on for the game display before launch.

- Status: tested (RTX 4090).
- Code: `ext/hdr/Hdr10.cpp`, `PresentHdr.cpp`, `BridgeHdr.cpp`, `FgHdr.cpp`, `ext/hdr/menu/` (menu layer composited into the HDR output), `ext/hdr/shaders/Hdr10.hlsl`.
- Seams: present `PlanDx12Presenter`, `PatchPresenterDesc`, `LogPlainPresenter`. dx11bridge `ConfigureOutput`, `OnDestroy`, `OutputFormat`, `OnResizeDone`, `ConvertCopySource`, `SetColorSpace`. fg `SetResourcePre`, `SetResourcePost`, `NormalizeFormat`, `DlssgTagHudless`, `XefgPrepareHudless`, `AdjustConstants`. menu `AdjustFgOutputOptions`, `UseSdrUiTarget`, `AdjustTheme`. gpu `ResetCommands`, `ExecuteCommands`. hdr `OverlayRtvFormat`, `OverlayPrepare`, `OverlayScope`, `OverlayRelease`.
- Config: `[HDR] FfxivHDR` (restart after changing), `PeakNits`, `PaperWhiteNits`, `HighlightExpansion`, `Contrast`, `Saturation`, `Vibrance`.
- Menu: `ffxiv_hdr` (tab FFXIV, second card; titled "FFXIV HDR10 output").

**RenoDX scene HDR (`[HDR] Mode = 1`).** Replays the game's tone-mapping stages in FP16 next to the SDR chain, so HDR output keeps the highlights the SDR path clips. The SDR chain, ReShade and the HUD are untouched. Two experimental switches feed the linear scene into NR (`NRSceneInput`) or DLSS (`DLSSSceneInput`).

- Status: tested (RTX 4090) for `Mode = 1`; `ReShadeHighlights`, `NRSceneInput`, `DLSSSceneInput` are experimental and untested.
- Code: `ext/hdr/scene/` (`FfxivSceneHdr.h`, `SceneHooks.cpp`, `DlssSceneInput.h`, `NrSceneInput.h`), `ext/hdr/DlssHdr.cpp`, `ext/hdr/shaders/renodx/` (RenoDX shaders; licence and notice shipped as `Licenses/RenoDX_*`).
- Seams: hdr `DlssExt`, `AdjustDlssCreateFlags`, `RestoreDlssCreateFlags`, `DlssEvalScope`, `BridgeInitScope`, `BridgeEvalScope`. dx11bridge `PresentScope`, `BeforeSharedCopy`. fg `SceneRawHudless`.
- Config: `[HDR] Mode`, `ReShadeHighlights`, `NRSceneInput`, `DLSSSceneInput`.
- The scene stages are recognised by shader fingerprint, so a game patch that changes those shaders disables it; see [FFXIV-PATCH-RUNBOOK.md](FFXIV-PATCH-RUNBOOK.md).

**HDR PNG capture.** Saves one PNG on a key press, as SDR for sharing or as HDR, with BT.2100 PQ metadata (an ICC-only variant exists for viewers that mishandle the cICP chunk).

- Status: untested (the maintainer does not use it day to day); the PNG writer has unit tests.
- Code: `ext/hdr/screenshot/`.
- Seams: dx11bridge `PrepareScreenshot`; the menu variant (`ScreenshotMenu`) is taken inside `hdr::OverlayScope` with no extra upstream line.
- Config: `[HDR] ScreenshotKey`, `ScreenshotFormat`, `ScreenshotIccOnly`, `ScreenshotMenu`.
- Menu: key row in the Keybinds list; options in the `ffxiv_hdr` card.

## Frame generation

**DLSS-G multi frame generation unlock, RTX 40.** Raises the frame-generation ceiling that the driver reports for GeForce RTX 40 cards, in memory only (the `nvngx_dlssg.dll` on disk is never modified), and applies a targeted temporal correction. Only supported runtime builds are patched; an unknown build is left alone.

- Status: tested (RTX 4090) at 2x to 4x. 5x and 6x are experimental; the maintainer saw one GPU hang at 6x.
- Code: `ext/fg/dlssg/MfgUnlock.cpp`, `AdaTemporal.h`, `DlssgSeams.cpp`; `ext/fg/streamline/StreamlineSeams.cpp`.
- Seams: streamline `MfgUnlockTick`, `MfgCeilingStale`, `RaiseMfgCeiling`, `OnDlssgModuleLoad`, `WarnMfgOverrideIgnored`. fg `AdjustMfgMax`, `AdjustDlssgOptions`, `AdjustReflexOptions`, `AfterDlssgSetOptions`, `OnActivated`.
- Config: `[DLSSG] AdaMfgUnlock` (save and restart after changing). Do not combine with an external unlocker.
- Menu: `fg_unlocks` (tab Frame Gen, titled "Frame generation unlocks", after the runtime cards; the RTX 20/30 runtime sits in its closed fold "RTX 20/30 frame-generation runtime").

**DLSS-G MFG loader for RTX 30.** Loads a separate RTX 20/30 frame-generation runtime (a DLSS-G build) from `OptiScaler/dlssg_sm86` so Ampere cards can generate more than one frame. Status: untested. Code: `ext/fg/dlssg/AmpereMfgLoader.cpp`. Seams: streamline `OnLoadStreamline`. Config: `[DLSSG] AmpereMfgUnlock`, `AmpereMfgMaxFrames`, `AmpereMfgKernelImage`, `AmpereMfgRouter`, `AmpereMfgHardwareBilinear`, `AmpereMfgOptimized`, `AmpereMfgPreset`, `AmpereMfgSpoofArchToGame`, `AmpereMfgLogLevel`. Menu: `fg_unlocks`. You must supply the runtime DLL yourself. ("Companion" in this document means only the FFXIV nameplates.)

**DLSS-G render preset (A, B, C), switchable while the game runs.** Chooses the render preset of NVIDIA's frame generation runtime (`nvngx_dlssg.dll`): Auto (the driver and the runtime decide), Preset A, B or C. The request is answered inside the process only: at start-up the driver-settings query of the runtime for the preset (setting id 0x10E41DF1) is answered with the preset number (a "setting not found" reply too), and no NVIDIA profile is written. That is the only id answered. The separate DLSS override id (0x10E41E03, NVIDIA's "DLSS override" switch) is never answered, because answering it "on" made NGX load NVIDIA's own copy of the runtime from its model store (`C:\ProgramData\NVIDIA\NGX\models\dlssg\...`, log `Built with APP_NAME = nvapp_override`) instead of the patched `OptiScaler/nvngx_dlssg.dll`: no multi-frame unlock (`max generated frames 1`) and about a third fewer frames per second (frame rates as the maintainer measured them on one RTX 4090 setup, not from the logs); with only the preset id answered the local runtime loads (`APP_NAME = endpoint`, `max generated frames 5`) and logs `Applying settings for render preset N.` (checked in game on 2026-10-22 with `RenderPreset = 3`, about 74 fps on that setup). A user whose own NVIDIA profile, or the NVIDIA app's "DLSS override" setting, turns the override on may get NVIDIA's copy of the runtime regardless of this tool: that is inferred from the run in which this tool answered the override id itself, no log with a real profile value exists. The menu shows a warning line and the log gets one WARN line when NGX's init line for frame generation shows that copy (`Built with APP_NAME = nvapp_override`); it states what the log shows, not why. The preset is applied by that copy too (`Applying settings for render preset N.` was seen with it), without the unlock. Changing it in the menu while the game runs switches frame generation off, waits, releases the DLSS-G resources on a later frame (at least 3 frames and 100 ms after the switch-off, never in the same frame), lets the runtime build its next endpoint under the new request and resumes with fresh history. The installed runtime caches its settings, so the live change hooks three of its functions in memory (the cached-settings reader, the endpoint create function and the configuration copy function). This happens once, at the first live change, after the frame generation switch-off and the release, with only the calling thread enlisted (no other thread is suspended), and only after structural checks of the module's code passed: every pattern unique, every target a function start, the endpoint create function is decoded instruction by instruction and its context argument is followed from the function entry to the settings read (kept in any callee-saved register or frame slot, no fixed register is assumed; nothing may write that place in between and nothing may jump into that stretch), the shared configuration and the two copy sites are checked, the create function's argument count and status constant are read from the decoded code, and stack-frame sizes are read from the code so 310.8 and 310.9 builds both pass. The file hash is logged but is not the gate; only 310.8 and 310.9 runtimes are accepted. Any failed check or release keeps the old request and the menu says "restart needed"; nothing is hooked while the key stays on Auto, and a session that started on a preset can go back to Auto live only if the driver's own answer was seen first. Preset A turns off the runtime's own UI recomposition (Preset C only when the runtime confirms that it applied C; that C turns the recomposition off is inferred from the preset number, the runtime does not state it), so in the HUD-less recomposition mode the option is not requested while that is the case (a menu note says so; the `ui_free` mode is not affected). The menu shows whether the runtime asked the driver for the setting, the last NVIDIA preset log line verbatim (with a "confirmed" mark when its format is known) and what the runtime reports back (`requested`, and `applied` or `effective` depending on the build); it recognises the 310.9.16 wording (`Applying settings for render preset N.`, `ReportOverrideStates: render preset (requested=N, effective=N)`, `Ignoring unsupported render preset ID N.`) as well as the 310.9.1.0 wording, and it shows a private driver flag that forces part of the preset off (UI recomposition or FG Lite) as an override while the preset itself is still applied; when two lines disagree the later one wins (NGX's `Applied: No` does not outrank a later report that says the requested preset is in force; only `Applied: Yes` has been seen in a real log, so what `Applied: No` means is unverified); it says "In use" only when the runtime confirmed the preset, and a single `Applying settings for render preset N.` line is enough for that (the 310.9.16 runtime prints no `ReportOverrideStates` and no `Override Reported` line on a normal start with the preset id answered alone; their absence is not shown as a failure). The selector stays visible; when the chosen preset and the one in use differ the menu says `Chosen: X, in use: Y` with the reason (the change is made when frame generation runs next, or restart needed with the reason of the failed step, shown only while the chosen preset is the one that failed; the restart note says what stays until the next start, with "not confirmed" where the runtime did not confirm it, and that the ini value applies then), and with the control off it says `Chosen: X, not in use:` and the reason (Auto reads as the reason alone). "Chosen" is the selector's value, which is the saved one after Save Settings. The readout comes from a log relay on the Streamline log lines: with `[Log] LogLevel` at warn or higher, or with `LogAsync`, it stays empty and the menu says so. Disabled, with the reason shown, for the RTX 20/30 companion runtime, a replacement runtime and any output other than DLSS-G. Config: `[DLSSG] RenderPreset` (0 Auto, 1 A, 2 B, 3 C; the ini value applies at the next start either way). Status: the code checks pass on the real 310.9.16, 310.9.1.0 and 310.8.0 runtimes (manual recipe `tests/ext/fg/fg_preset_guards_dll.cpp`); in game, a start with `RenderPreset = 3` loads the local runtime (`max generated frames 5`) and applies Preset C; the live change Auto to Preset C from the menu was also seen working (2026-10-21, `max generated frames 5`, about 74 fps as the maintainer measured it on one RTX 4090 setup); the way back to Auto after a start on a preset, and live A and B, are still in-game checks. Known limits: the 310.9.1.0 runtime acts on A (1) and B (2) only (C is ignored there: the menu says so and nothing is paused), while 310.9.16 acts on all three (A and C turn the runtime's UI recomposition off, B turns it on, C also turns its FG Lite setting on: read from the runtime's code and the preset number, not stated by its log); "confirmed" rests on the lines the runtime prints when it creates an endpoint, so after a live switch the real UI recomposition and FG Lite behaviour are an in-game check; whether releasing the DLSS-G resources in a live scene is safe is an in-game question (the wait is 3 frames and 100 ms, not a proven GPU drain). Code: `ext/fg/dlssg/Preset*.h|.cpp` (`PresetX64.h` is the instruction decoder of the guards), `ext/fg/MenuFgPreset.cpp`. Seams: fg `PresetSwitchTick`; the driver-settings hook calls `ext::fg::preset::OnDrsGetSetting` (upstream: `nvapi/NvApiHooks.cpp` +2 lines, `framegen/dlssg/DLSSG_Dx12.cpp` +2 lines). Menu: section "DLSS-G render preset" of the `fg_unlocks` card. Manual check on a new runtime: `tests/ext/fg/fg_preset_guards_dll.cpp` (see its recipe).

**Dynamic MFG on RTX 50.** The fork reads back the multiplier that DLSS-G actually applied and shows it, and sends the frame limit you set to Reflex in dynamic mode. Status: untested. Code: `ext/fg/MenuFgStatus.cpp`, `ext/fg/dlssg/DlssgSeams.cpp`. Seams: menu `ObservedMultiplier`; fg `AfterDlssgSetOptions`, `AdjustReflexOptions`. Config: upstream keys `[DLSSG] ForceDMFG`, `OverrideForceDMFG`. A `FramerateLimit` read from the ini that is not a positive number (`nan`, `inf`, `0` or negative) means no limit and is saved back as `auto`; a limit set at run time with the "Set as FPS Limit" button of the VRR calculator is not checked.

**Automatic multiplier (dynamic MFG) on RTX 40.** Chooses 2x, 3x or 4x from the real frame time and changes the count while DLSS-G keeps running, instead of the off/on cycle of the Frame Gen slider (which costs about half a second without frame generation and one long frame). It reaches for the lowest multiplier that still presents the target frame rate, steps up after 1 s, down after 0.5 to 2 s, waits 3 s between changes (more when it flaps), ignores one-off long frames, and when the output sits at the target (a display-bound output pins it there) tries one step lower every 12 s or longer and keeps it only if the target is still reached. It also reverts a step up that gains less than 4 percent. Whether a count change in place avoids the long frame is not known: after every change the fork watches one second; a long frame right after a change slows it to one change per 12 s and the same signature on two changes in a row, or on three in all, stops it (an earlier one is forgotten only after ten clean changes in a row, counted in changes and not in time), a change that is not applied or that upsets Streamline goes back to the last good count and stops it. It never goes above 4x, is off by default, and is inert on RTX 50 (use Force Dynamic MFG there), with Frame Gen on Default, with Force Dynamic MFG and with the other frame generation outputs. A guard also keeps NVIDIA's own dynamic mode from choosing 5x or 6x on an unlocked RTX 40 (the cap is for Streamline only: the Frame Gen slider keeps showing your 5x or 6x, and a frame limit that OptiScaler enforces itself (the `FPS limit through ...` log line) still paces for that slider count, so with Force Dynamic MFG on an unlocked RTX 40 and a frame limit keep the slider on 4X; the warning line in the log says so), and falls back to the fixed mode when Streamline says dynamic MFG is unsupported (Force Dynamic MFG used to be sent without that check). Status: untested in game. The check: set `[DLSSG] AutoMFG=true`, `AutoMFGSelfTest=true`, the slider on 3X or 4X, start the game, stand in the game world for about 70 seconds (the test waits for 20 seconds without a stall first), then read `OptiScaler.log` for `AutoMFG self-test: PASS` or `FAIL` (needs the INFO log level and `AdaMfgUnlock`). Code: `ext/fg/DynamicMfg.h` (selector), `DynamicMfgControl.h` (gating, kill-switch, self-test), `DynamicMfgGate.h`, `DynamicMfgGlue.h` (the per-frame tick and the guard, tested with fakes), `DynamicMfgSeams.cpp`, `MenuAutoMfg.cpp`. Seams: fg `AdjustDlssgOptions`, `AfterDlssgSetOptions`, `OnActivated` (no new seam). Config: `[DLSSG] AutoMFG`, `AutoMFGMax` (2 to 4), `AutoMFGTarget` (0 = the lower of the frame rate limit and the display refresh), `AutoMFGSelfTest`. Menu: `fg_auto_mfg` (tab Frame Gen, after the Frame Gen runtime cards and the `fg_unlocks` card; titled "Automatic multi frame generation"; its slider is "Target FPS (automatic multiplier)").

**Automatic multiplier, behaviour after review.** A step up is judged on the first half second after it, so a scene that gets heavier meanwhile does not revert it; a trial step down that is lost to a pause-like frame doubles the interval before the next trial; a display refresh reported as 0 or 1 Hz counts as unknown (the frame rate limit is the target then); and a count of 0 from the plugin, a Streamline status that was already set before the change, or a short pause around the check is not counted as a failed change. The self-test, and turning the automatic multiplier off during it, put the multiplier back to the one in use before the test (in Frame Gen Default the game keeps choosing the count, and the stored one is reset for when you leave Default); the cap on an unlocked RTX 40 never rewrites the slider. New log lines to look for: `AutoMFG self-test: Nx -> Mx (back to the count in use before the test)`, `AutoMFG: Nx settled (worst interval ... ms, applied Mx)` (or `applied unknown`) and `AutoMFG: 10 clean changes since the last long frame, normal hold and probes again`. Status: untested in game.

**Automatic multiplier, second review round.** A bad Streamline status or a count of 0 from the plugin has to last three samples and at least 150 ms at the end of the one-second check before it counts as a failed change (at 224 fps three frames are 13 ms); a fault that is still younger than 150 ms when the second ends keeps the check open for up to 150 ms more, so that it can still be convicted (see the third review round below). The first two intervals after a change are left out of the average, the same two the long-frame check looks at, so a stall in the second one cannot revert a correct step up. Three long-frame signatures in all (an earlier one is forgotten only after ten clean changes in a row) stop the mode as well (a plugin that re-creates DLS-G only when the count goes up would otherwise never stop). Turning the key off after the mode ran, or a GPU that Windows has not reported yet, no longer leaves per-frame work or a wrong permanent "not NVIDIA" behind; the observation of the DLS-G state is now part of the tested glue. Limits, stated: on a Windows game running through vkd3d-proton with the Vulkan menu overlay, opening the menu during the one-second check can read as a failed change (native Windows is not affected); the paused input of the tick exists but the plugin never reaches it while paused, the protection there is the persistence rule above; a hitch in the third interval or later after a change counts as an ordinary slow frame. Status: untested in game.

**Automatic multiplier, third review round.** A bad Streamline status or a count of 0 that begins in the last 150 ms of the one-second check is no longer dropped: the check stays open for at most 150 ms more, until the fault has lasted three samples and 150 ms (then it is a failed change) or has gone (then the change is clean). A fault that begins after the check has closed is not held against that change. The text "ten clean changes forget the earlier ones" now says what the code does: strikes are forgotten by the number of clean changes in a row, not by time, and after the first long frame the mode changes rarely, so a strike can stay for hours and three of them stop the mode. The menu card asks which GPU is installed only when the DLS-G output is the active one; the GPU question itself is asked at most 12 times, five seconds apart, after which the GPU stays unknown for the session (the automatic mode stays off and one warning line in the log says so; the menu card stays offered). In the log: a failed change that was caught late reads like any other (`Streamline status 0x..` or `applied count 0 != requested ..`), and `AutoMFG: the GPU could not be identified after 12 tries` (or `AutoMFG menu card: ...`) is new. Status: untested in game.

**Automatic multiplier, stall rule.** The first two runs in game showed that a loading screen, or a DLSS preset change in the menu, can stall the game at about 18 real frames per second at the very moment a count change is being checked: the new count was applied late, the check read that as a failed change and stopped the automatic mode for the whole session. Now the controller keeps its own average of the real frame interval (an exponential average over 250 ms in which one frame counts as at most 50 ms, so one long frame is no stall) and calls the game stalled while the average is above 30 ms (below about 33 real frames per second). While it is stalled no new change starts (the selector is not asked, and it starts over when the stall ends, so its usual wait follows the stall), a change that was already made is not checked, and the self-test does not start. Once the average has been at or below 30 ms for one second without a break, that change gets a fresh one-second check and is judged by the usual rules, so a real fault is still caught about one second after the stall. A change that cannot be judged within 5 seconds of its switch because of stalls ends as unknown: no strike, no stop, the count stays where it is, the selector starts over, and the log says `AutoMFG: judging the change at Nx skipped, the game was stalled`. The self-test starts only after 20 seconds without a stall, and a stall during it ends it as `AutoMFG self-test: FAIL (interrupted: the game stalled)` (the multiplier in use before the test comes back after the stall; the line has the FAIL prefix like every interrupted test); a stall before its first change sends it back to waiting for 20 quiet seconds. Faults at normal frame rates are judged exactly as before: the same one second, the same long-frame check, the 12 s wait and the stop rules. Limit, stated: on a setup that runs below about 33 real frames per second all the time (not counting the generated frames) the automatic multiplier never changes the count and the self-test never starts; use the Frame Gen slider there. Status: untested in game. The check: stand in the game world with `AutoMFG=true`, change a DLSS preset in the menu or load a zone, and read `OptiScaler.log`: there should be no `automatic mode stopped` line, and a change made right before the stall ends with `settled` or with the `skipped` line.

**Pacing, markers and hardening.** The frame-rate cap counts generated frames when NVIDIA frame generation is active (`FrameInterval`); for FFXIV the fork sends its own simulation and render latency markers so Reflex pacing sees the game's real frames (`ext/ffxiv/markers/`); ordered swapchain-command submission, guide matching for the history reset, and several Reflex and Streamline fixes that are carried as small `[UP]` commits (the list is in [SEAMS-catalog.md](SEAMS-catalog.md), section (a)). Status: runs inside the tested DLSS-G path, not tested separately. Code: `ext/fg/` (`FrameInterval.cpp`, `GuideMatcher.cpp`, `GuideSeams.cpp`, `MarkerSeams.cpp`, `Dx12Sc.cpp`), `ext/gpu/`. Seams: present `FrameInterval`; fg `MarkersBeforePresent`, `MarkersNextFrame`, `OnUpscaleStart`, `GuideAge`, `DispatchResetHistory`, `PostDispatch`, `ForceConstantsReset`, `SubmitSC`, `PrepareSC`, `ReleaseGuides`, `OnDeactivating`; gpu `ResetCommands`, `ExecuteCommands`. Config: `[LowLatency] Input`, `Output` (menu selection saved). Marker pacing needs a matched FFXIV build.

## Window mode

**What it is for.** FFXIV runs borderless when `[XeFG] ForceBorderless = true` (a setting the fork does not turn on by itself). In that mode upstream's hook swallows the game's request to change the window mode and restyles the window itself. Two problems come from that, both seen in logs: after leaving the pseudo fullscreen the window keeps a thin edge (the client area becomes 3836x2156 inside a 3840x2160 window), and one window-mode switch made while DLSS-G was running stalled Streamline's frame pacer, which logged "Potential dead-lock in Present - please make sure DLSS-G is disabled when making any modifications to the window" and ended with the GPU device removed.

**Zero-code advice.** In the game's display settings choose "Borderless Window", and restart the game after changing the mode. Do not switch to "Fullscreen" while the game runs. Without any switch the window is clean and nothing here is needed.

**Status.** Opt-in, off by default, untested in game. The rules and the decision flows have unit tests on fakes (frame generation, window, clock and swapchain are replaced by test doubles) and the window calls are tested on a real hidden window; the game itself decides whether it tolerates a held-back window-mode call (see "Open points" below).

**Config.** `[Window] Mode`: `off` (default: nothing runs and nothing is logged), `probe` (log only), `on` (probe, border fix and deferred mode switch). Applies after a game restart; any other value counts as `off`. The same setting is a drop-down in the menu card "Window mode (FFXIV)" (Frame Gen tab, after the DLSSG settings): the choice is stored for the next start and the card shows the mode that is active in this session. With `off` the module costs one atomic load and one branch at each of its five entry points (bridge resize, bridge destruction, Present entry, Present exit, ReShade event), and the ReShade event is not even subscribed.

**Probe.** With `probe` or `on`, one line starting with `Window:` is written (a) after every successful resize of the bridge swapchain and (b) for every window-mode call (`IDXGISwapChain::SetFullscreenState`) that ReShade sees, before the call. Fields: the window's style and extended style, window and client rectangles, frame generation state (`active`, `paused`, `off`, `none`) and `fgOffConfirmed=` (yes after ONE complete present with frame generation off and DLSS-G as the output; the replay and the border fix below need 2 such presents and 50 ms, so the field can read yes before either rule is met), `SCExclusiveFullscreen` (and its value at the previous resize), `ForceBorderless`, the window's owner thread id, the current thread id and the thread that presents, and for the call: its argument, the swapchain ReShade passed (`native=`), the bridge swapchain (`bridge=`) and the bridge's inner frame generation swapchain (`fgswapchain=`) side by side (which of the two ReShade passed is then visible), the verdict and the value the handler would return. The probe only reads (window styles and rectangles, frame generation state, thread ids) and logs; it changes no window and never prevents a call. The ReShade event needs ReShade (the log line `Window: ReShade set_fullscreen_state event registered` at start-up says whether it was subscribed).

**Border fix (`on`).** When `SCExclusiveFullscreen` goes from true to false, the module arms a fix. The flag is sampled at every bridge resize and at the end of every game present (the hook flips it without any resize necessarily following; the logged startup enter has none). From the end of a game present, once frame generation is confirmed off in the strict sense (like the replay below: at least 2 complete off presents and at least 50 ms since the first of them, so that after a leave that was not held the restyle does not land in the very first off present), it reads the window's styles. If the style has neither a caption nor a sizing frame but the extended style carries `WS_EX_CLIENTEDGE` or `WS_EX_WINDOWEDGE`, it clears those bits and applies them with `SetWindowLongPtr(GWL_EXSTYLE)` plus `SetWindowPos(NOMOVE | NOSIZE | NOZORDER | NOACTIVATE | FRAMECHANGED)`; the client area is again as large as the window. A window with a caption or a sizing frame (a real windowed mode) is never touched. A "complete off present" is a game present that started and ended with frame generation inactive, with DLSS-G as the output (Streamline applies "off" inside the next present); the fix needs 2 of them and the 50 ms, as stated above (the probe field `fgOffConfirmed=` is only the one-present condition). The fix never runs while frame generation is active (it can come back about ten frames after a Deactivate); it waits for the next off period, gives up after 120 checks or when 600 presents or 30 s have passed since it was armed, and runs only on the window's owner thread (otherwise it logs `owner thread differs, border fix skipped` once and does nothing). It is never called inside `ResizeBuffers` or a paced present.

**Deferred mode switch (`on`).** A ReShade add-on event runs before the game's `IDXGISwapChain::SetFullscreenState`. When all of these hold, the call is held back and the handler returns `true` (ReShade's "prevent"): `[XeFG] ForceBorderless` is on, the output is DLSS-G, frame generation is active, the call would really change `SCExclusiveFullscreen` (a repeat of the state in effect is not held), the call is for the bridge swapchain, its target output is null or the window monitor (the replay passes a null target), and the window's owner thread, the calling thread and the presenting thread are one thread. The module then asks frame generation off through the feature API (what upstream's hook does first: `UpdateTarget` and `Deactivate`), remembers the swapchain (no extra reference is taken; the hold is dropped, unreplayed, when the bridge swapchain changes or is destroyed, and the replay only runs on the live bridge), and from the end of a game present, once DLSS-G is confirmed off (at least 2 complete presents with frame generation off and at least 50 ms since the request), replays `SetFullscreenState(state, null)` directly on the swapchain ReShade passed (not through ReShade, so the event is not entered again). Upstream's hook and Streamline then see an ordinary call with frame generation already off. A second call while one is held keeps only the latest; if the latest asks for the state already in effect the held call is dropped. The wait is bounded: after 6 presents or 2 s the call is replayed if frame generation is off at that moment, a game present has reached the frame generation present since the request (or since the last time frame generation was asked off again) and at least 50 ms have passed since that request; frame generation can come back after about ten frames, so every present that finds it active asks it off again and the replay never runs with it active; only the hard limit (24 presents and at least 500 ms, or 6 s) replays regardless, with a warning (on a presenting thread that is not the window owner thread the hold is dropped with a warning instead of being replayed). A bridge resize while a call is held deactivates frame generation again (Streamline applies "off" inside the next present), so it restarts the count of off presents and the 50 ms floor, like a new request. Limits, not verified in game: (a) the 50 ms floor is an absolute time while frame generation pauses for about ten frames after a Deactivate; the first complete off present ends about one frame in, so at 138 game presents per second (7.2 ms) the floor leaves about two frames of margin, at 165 about one, and from roughly 190 to 200 game presents per second the floor outlasts the pause: frame generation comes back before the floor is over, the count restarts at every re-request, the confirmed replay does not come, and the hold ends at the hard limit with frame generation active (a warning), and the border fix expires without applying (`border fix expired`); the first in-game session reads the `replaying ... (after N presents, M ms ...)` line, reports which reason fired (`frame generation confirmed off`, `wait limit reached` or `hard wait limit reached without a confirmation`) and at what presents per second; (b) both conditions of the hard limit use the clock (24 presents need 500 ms as well, and the other limit is 6 s), so a clock that stood still would leave no hard limit; the live clock (`GetTickCount64`) is monotonic, so this is informational. A hold that is dropped instead of replayed (the hard limit on a thread that is not the window owner thread, a changed or destroyed bridge swapchain) forgets the call for good: the game was told the call succeeded but the window did not change, and frame generation was asked off and comes back about ten frames later; the log line `held SetFullscreenState dropped` means the mode did NOT change. Anything unexpected passes the call through as today. The monitor argument of the event is logged but never used. What the game receives for a prevented call is decided by ReShade and is not documented in the local headers; the log records only what this handler returned.

**Log lines.** All start with `Window:` (the logger puts the function name in front). `module active, mode=...` once; `ReShade set_fullscreen_state event registered` at start-up; `resize-done ...` and `set-fullscreen-state ...` probe records; border fix: `border fix armed`, `border fix waiting`, `border fix applied exstyle A -> B client WxH -> WxH`, `border fix gave up`, `border fix FAILED`, `owner thread differs, border fix skipped` (warning, once); mode switch: `SetFullscreenState(TRUE|FALSE) held back: frame generation asked off, ...` (before the request) and `... held back, frame generation asked off; handler returns true (prevent)` (once the request returned), `hold cancelled, the frame generation request failed (...); handler returns false` (warning: the call passes, and the `returned=true` of the record above it is void), `replaces the held call`, `held call dropped`, `held SetFullscreenState dropped, not replayed: ...` (the mode did not change), `frame generation came back while a call is held`, `replaying SetFullscreenState(...)` with the reason and `replayed SetFullscreenState(...) returned 0x...` (both are written after the call returned, so that a failing log cannot lose the held call; a hang inside the game's call leaves neither line), and, if the module's lock bookkeeping is ever found inconsistent, a warning `a nested entry left the module lock depth raised during a call out` (once; the bookkeeping is put right and nothing aborts). A probe record ends its call part with `verdict=` (`defer` or `pass(reason)`), `wouldReturn=` (what `on` would return) and `returned=` (what was returned).

**Complete presents.** "DLSS-G confirmed off" counts only game presents that really reached the frame generation present. The bridge advances its back buffer index only after the frame generation swapchain's `Present` returned success, with frame generation on or off, and never on one of its early error returns; the module reads that index at the start and at the end of each game present. A changed value (not "greater": the index wraps) is a complete present, an unchanged one resets the off count and is not counted. With fewer than two buffers the index cannot change, and with no bridge known (or a different bridge by the end of the present) nothing can be told: such a present is counted as it always was. Log lines: `the bridge present counter is live` (once: the positive proof), `the bridge present counter is not available (fewer than two buffers)` (once), `a game present ended before the frame generation present ... not counted` (the first five). Failed presents delay the replay up to the hard limit (24 presents and at least 500 ms, or 6 s): the soft wait limit described above needs a present that reached the frame generation present since the request, so a run of failed presents does not end at the soft limit, and a hard-limit replay with nothing confirmed logs a warning `hard wait limit reached without a confirmation` with the frame generation state (`fg=...`) at the end of the replaying line. With no counter (fewer than two buffers, or no bridge known) every present counts as having reached it, so the soft limit works as before, with the 50 ms floor. An unconfirmed replay at the soft limit logs `wait limit reached` instead of `frame generation confirmed off`.

**Open points, continued.** (6) The live side's two out-calls (the frame generation request in the order `fgChanged`, `UpdateTarget`, `Deactivate`, and the replay with a null target) are tested on fakes, by a source check that the live code goes through them and by a read-only source check that upstream's hook (`hooks/FG_Hooks.cpp`) still does the same three steps in the same order; the module lock being given up around each call out is tested as a scope on a fake mutex (a nested entry inside a call out never unlocks more than the thread owns), and its live use is pinned by a source check (each of the three calls out has its unlock scope before the call, each of the five entry points takes and counts the lock); that the real mutex is free during a call out is not exercised by a test. (7) If the bridge's swapchain has a single buffer the present counter is unavailable (see "Complete presents") and a present that failed before the frame generation present cannot be told apart; the gate then behaves as before this check. (8) One bridge swapchain is assumed (FFXIV creates one): the module remembers only the last bridge it saw at a resize, so with two live bridges the present counter of the last resized one would judge the other one's presents (an unchanged counter reads as an aborted present, the gate never counts and a hold would wait for the hard limit).

**Open points.** (1) What ReShade hands back to the game for a prevented call is not documented in the vendored headers; the module logs what its handler returned (`true`) and nothing else, and the game may or may not accept a call that is carried out a few frames later. (2) Which thread owns the game window is not known from the logs; the probe prints it next to the calling and presenting threads, and every action is skipped (the call passes through as today) unless they are one thread. (3) Whether FFXIV rewrites its own frame-less style after the fork's leave branch has run is inferred from window sizes in a log, not observed; the probe lines show the style before and after, and the border fix keeps checking for a while and then gives up without touching a window that still has a caption. (4) Whether the replayed call, made with frame generation off, avoids the Streamline stall can only be seen in the game: look for the absence of `Potential dead-lock in Present` after a `replaying SetFullscreenState` line. (5) The hold cannot cover a game `ResizeBuffers` that changes the size: no ReShade event exists before a resize, and a size-changing resize runs Streamline's flush at once, before any present has applied "off". So the call is held only when the FG swapchain already has the window's size (the probe line prints `swapchain=WxH` next to `client=`); otherwise it passes through with a warning `the follow-up ResizeBuffers is not protected`. The border fix must therefore have made the client 3840x2160 first: do the risky switch (leave or enter with frame generation on) only after a border-clean leave. The size guard is necessary, not sufficient: a leave from the 3840x2160 pseudo fullscreen to a smaller windowed mode passes it (the swapchain has the window's size at that moment) and is held, but the game's follow-up `ResizeBuffers` to the smaller size is a real resize that runs at once, before any present applied `off`; the hold is then no worse than today, not better. The first session compares the `swapchain=` value of the `resize-done` line after the call with the window size.

**Code.** `ext/window/`: `WindowRules.h` (pure rules: border rule, DLSS-G off gate, thread rule, defer verdict), `WindowDeferral.h` (the Idle/Pending/Replaying machine), `WindowProbe.h` (the line format), `WindowController.h` (decisions, driven through an `Env` interface so tests use fakes), `WindowWin32.cpp` (window reads and the extended-style call), `WindowModule.cpp` (live `Env`, entry points), `WindowConfig.h`, `WindowMode.h`, `WindowSeams.h`.

**Seams.** None in upstream files. The module is called from the existing fork seam bodies `dx11bridge::OnResizeDone` and `dx11bridge::PresentScope` (`ext/hdr/BridgeHdr.cpp`) and from a ReShade add-on event (`ext/reshade/ReShadeEvents.cpp`).

## FFXIV module

Everything that is specific to FFXIV is under `OptiScaler/ext/ffxiv/`. It activates only when the running `ffxiv_dx11.exe` matches the supported build recorded in `ext/ffxiv/GameBuild.h` (see [FFXIV-PATCH-RUNBOOK.md](FFXIV-PATCH-RUNBOOK.md)); on any other executable the pieces below do nothing. The module implements the interfaces in `ext/game/`.

**Native quality and forced quality.** Reads the game's own DLSS quality setting and its live changes, answers the game's size query with the preset you choose (`ForcePerfQuality`), requires true DLAA where the game asks for it, and lets the render size follow. **Quality change without the stall.** Changing the DLSS quality in FFXIV releases the DX11 upscaler and builds a new one; upstream sleeps a fixed 500 ms between the two. On a matched FFXIV build the release can now prove the work is finished and skip that pause. It closes the upscaler's handle to new evaluates, waits (at most 200 ms) for an evaluate already running on another thread, drains the GPU queues the feature could still be running on (the upscale queue, and the frame generation queue when frame generation is attached to this feature; each with a fence wait capped at 5 s) and only if all of that is proven (log result `drained`) skips the sleep. Anything unproven gives `not-applicable`: a null queue, a removed device (also one lost during the wait), an evaluate that does not finish in time, a release called from inside an evaluate of the same handle, any other game or non-bridge upscaler. Then nothing changes: the handle is reopened at once and the 500 ms pause stays, with evaluates running through it as before. A failed drain (`failed`) refuses the release as before. With XeFG output and `[XeFG] ResetOnUpscalerChange` on (the default) the release also rebuilds the XeFG context, which the drain does not cover, so that path is treated as unproven by design and the pause stays. The sleep after the reset (`Dx11DelayedInit`, off by default) is not touched. On a proven release the handle stays closed for the few milliseconds until its entry is detached: an evaluate on it returns without output, the state a released handle is in until the game builds the next upscaler. The DX11 upscaler table has a narrow lock now (entries are reference-stable, an entry is detached under the lock and destroyed after it; the lock is never held across NGX, the driver, a drain, the frame generation mutex or an NR lock), because the game changes quality on its update thread while the render thread evaluates. The lock covers the table structure and the current-feature pointer writes; the contents of an entry are still written outside it (a race that existed before and is not made worse), and about 40 readers of the current-feature pointer stay unlocked. The log shows the thread of every create and release, and of an evaluate on its first call, when its thread changes, and as one summary line per 10 s (at most 4 first/moved lines per 10 s, the rest counted as `suppressed=<n>`); that settles which threads really do what, the update-thread claim above is inferred from the code and not yet seen. Status: new, unit-tested (drain classification, lock and registry, release sequence with fakes, thread trace, source pins); not tested in game. Known limits: the release covers the upscale queue and the frame generation queue only; the real D3D12 glue and the lock-order premise (NR and frame generation never call back into the DX11 table) are pinned by source text and not by a run; skipping the pause changes timing on the game's update thread. Config: `[NgxRelease] SkipReleaseSleep` (ini only, default on; off = the old flow exactly: no closing, no waiting, the 500 ms pause; the table lock stays). Log: `FFXIV upscaler release: handle <n> result=<drained|not-applicable|failed> (...), waited <x> ms, sleep <skipped|kept (500 ms)|n/a (shutdown)>` and `FFXIV NGX thread: ...`. ## Character preview (CharaView)

**What it does.** The game draws the 3D character preview (character, equipment and glamour windows) in a small separate render. CharaView gives that render its own isolated DLSS Super Resolution pass with 2x output (jittered rasterisation, replayed G-buffer draws for signed motion vectors, depth and camera guides, native alpha composed back), and offers an optional FXAA-style spatial anti-aliasing pass with 2x upscaling for the equipment preview. It was reconstructed from an unpublished build by Nickle and written fresh; credit and method: [ATTRIBUTION.md](ATTRIBUTION.md) and [RECONSTRUCTION-NICKLE.md](RECONSTRUCTION-NICKLE.md). The preview's sub-pixel jitter cycle is 32 phases (the guides ask for at least 8 x (output / render)^2, which is 32 at the preview's fixed 2:1); the log line "CharaView: DLSS path in that burst" ends with "jitter cycle 32 phases".

**Status.** Off by default and untested in game. Not implemented, as in the build it was reconstructed from: frame generation for previews (not needed: the preview is part of the UI, which the game's frame generation does not interpolate separately), portrait windows (it is not known which windows reach this renderer), and deferred contexts (those draws stay native).

**Preview Neural Rendering (new work).** `[FFXIV] PreviewNR` (false) runs the DLSS NR model on each open character preview window. This is new work and is not reconstructed from Nickle's build, which never had it (its menu said NR was not active). The NR model only runs on Direct3D 12, so the preview image is handed to the DirectX 11 on 12 bridge's device through shared textures and fences, processed there and drawn from a shared result texture; every failure keeps the native image and switches preview NR off for the session. It needs an NVIDIA card, the bridge running, `nvngx_dlssnr.dll` and `nvngx.dll_dlssnr.dll`; `[DlssNr] Enabled` is not needed, the `[DlssNr]` tuning is shared. It works alone or with `PreviewDLSS`. Alone it runs on the native preview image (bring-up: native size, synthetic guides: a cleared depth and zero motion). With both on it runs on the Super Resolution result (production: the 2x output, copied into shared images, with copies of the preview's own depth and motion at the render size, the Super Resolution feature's depth convention and motion scale), between the Super Resolution evaluate and the alpha pass; the original alpha is recomposed onto the NR image exactly as it is onto the plain Super Resolution output, and any render where NR cannot run (the model is still being built, no command list free, a failure) shows the plain Super Resolution image. With both options on (and `PreviewNRBeforeSR` off), only the production model is built (at twice the size): a render that Super Resolution did not evaluate (the first renders after a window opens, a rejected finisher) shows the native image, exactly as with `PreviewDLSS` alone, and the first renders after the model is built are plain Super Resolution; preview NR on the native image (bring-up) runs only for a preview Super Resolution does not serve (`PreviewDLSS` off, Super Resolution latched, a failed or too large preview); the cost per window is one NR pass at 2.2 megapixels. `PreviewNRLate` applies to the bring-up only (the alpha recomposition needs the colour of the same render). It takes the equipment preview before the spatial AA; for a draw it has no result for (the first renders after a window opens, renders it skipped, a finisher the checks reject) the spatial AA still takes the draw when `PreviewAA` is on, so the AA is not lost, unless `PreviewDLSS` is on and its pass runs (then the draw stays as it is; while the `PreviewDLSS` pass cannot run, the AA takes it). `PreviewNRLingerSeconds` (5) keeps a window's model after the window closed; `PreviewNRLate` (false) shows the previous frame's result and avoids the GPU wait on the DirectX 11 side at the cost of one frame of lag. Cost per open window (GPU time, video memory) is shown in the menu and the log (`CharaView NR:` lines); it has not been measured in game yet. By default the placement is after Super Resolution when both options are on; NR before Super Resolution (a pre-pass on the render-size image) is the experimental `PreviewNRBeforeSR` option described below. In game still to be checked: the D3D12 state tracking of the production inputs under the debug layer, whether the model accepts guides smaller than the colour as the main pass's do, the image quality on the alpha-masked silhouette and on moving characters, and the cost with several windows open.

**NR before DLSS (experimental, new work).** `[FFXIV] PreviewNRBeforeSR` (false) runs the preview NR on the render-size picture before the DLSS evaluate instead of on the DLSS result: the slot's colour, depth and motion go through the NR model at the render size and the result is the evaluate's `Color`. The model works at a quarter of the pixels, so each open window is expected to use less GPU time and video memory than NR after DLSS (not measured yet: the cost lines in the log will show it); the trade-off is that NR sees a jittered picture that has not been anti-aliased, so shimmer or trails on hair and cloth are possible (the default stays after DLSS). It has an effect only with `PreviewDLSS` and `PreviewNR` both on; `PreviewNRLate` does not apply to it (the result is always used in the same frame). Fail-open: a render for which the NR step has no image yet (the model is being built, no list free, NR failed) is evaluated on the plain picture and does not start the NR after DLSS; if the DLSS evaluate refuses the NR image, that render is evaluated again on the plain picture, NR before DLSS is switched off for the rest of the session with one log line and NR runs after DLSS as before. The same switch-off happens when the repeat on the plain picture fails too: the preview then falls back to the game's own picture for about ten seconds, but a problem of the NR image cannot end the Super Resolution path. The Super Resolution history is reset when the picture handed to DLSS changes between the plain and the NR image and for the repeat after a refusal, so the two pictures are not blended. The reset for a change of the picture is given at most once per half second for a window: if the NR step is skipped on every other render (for example under heavy GPU load with several windows open) the picture alternates, and a reset on every change would keep DLSS from ever accumulating. The menu line "NR before DLSS" and the log show how many of these resets were given. A failure inside the NR step itself (for example an input that does not fit the stream) switches off all preview NR for the session, as it does for NR after DLSS; that is intended, because those failures do not depend on the placement. With `PreviewDebugTint` the preview is cyan when the evaluate used the NR image. Switching the key rebuilds the window's model after half a second. Whether the driver accepts the shared NR image as the evaluate's input, and the picture quality, are checked in the game (a refusal falls back as described); the cost lines in the log are labelled "pre-SR".

**Where.** `OptiScaler/ext/ffxiv/chara/` (with `shaders/`), hooks inside `ext/ffxiv/lighting/FfxivLightingCapture.h`, the per-frame callback through `dx11bridge::AfterSharedCopy` in `ext/Seams.cpp`, the game build entry in `ext/ffxiv/GameBuild.h`, ini fragments `ext/ini/FFXIV.ini` and `ext/ini/HDR.ini`.

**Seams.** None in upstream files.

**Config.** `[FFXIV] PreviewDLSS` (false), `PreviewAA` (false; with `PreviewDLSS` on, the DLSS pass takes the equipment preview and the AA is bypassed, but while that pass cannot run, for example because the game's D3D11 DLSS is not initialised or it failed, the AA is used instead; with `PreviewNR` on, the AA is used for every draw NR has no result for while `PreviewDLSS` is off or its pass cannot run), `PreviewUpscale` (true, only meaningful with the AA), `PreviewGuideCapture` (false; writes capped diagnostic dumps to `OptiScaler\PreviewDLSSDiagnostics\`), `PreviewNR` (false), `PreviewNRLingerSeconds` (5), `PreviewNRLate` (false) (see Preview Neural Rendering), `PreviewDebugTint` (false; debug aid, mixes magenta into the AA or DLSS result and cyan into an image preview NR produced, bring-up or production, so it can be seen which image is on screen), `PreviewDebugFlood` (false; debug aid, draws the preview as solid magenta wherever the game samples it, with or without AA or DLSS), `PreviewProbe` (false; debug probe: logs copies of the preview and draws that sample it or a copy, can save preview images as PNG to `OptiScaler\PreviewDebug\` and reads live commands from `OptiScaler\chara-probe.cmd`), `[HDR] PreviewNRTrace` (false; trace log lines only).

**Menu.** Card "Character preview" in the FFXIV tab: Preview DLSS, Preview spatial AA with its 2x upscaling option and Preview NR with "Run NR before DLSS" on top, the one-line states and the reason when the feature is off; every counter and debug aid (tint, flood, probe, "Save preview images") sits in a closed "Advanced (debug)" fold.

**Probe output.** While PreviewProbe is on, the button "Save preview images" (or the command `dump`) writes `native.png`, `aa.png`, `dlss.png`, `nr.png` (whichever exist; `nr.png` is the NR result converted to 8 bits), each with `alpha-<name>.png` (the alpha channel as a grayscale picture), and `state.txt` (one `key: value` per line) into a new `OptiScaler\PreviewDebug\<yyyyMMdd-HHmmss>\` folder; at most 40 files and 300 MiB per session. About twice a second the probe reads `OptiScaler\chara-probe.cmd` (one command per line: `tint|flood|aa|dlss|upscale|copies on|off`, `dump`, `state`, `reset`, `help`; at most 4 KiB), runs it, deletes it and appends the results to `OptiScaler\chara-probe.out` (capped at 256 KiB). Commands change the settings in memory only; the ini file is not touched.

**Safety.** It fails open: any doubt leaves the native image. It reads the game's `.text` once, read-only, for an 18-byte code pattern that must match exactly once at the documented addresses; otherwise the feature switches itself off for the session with one log line. The DLSS pass uses the driver's real D3D11 NGX and latches off for the session if feature creation fails. Switching `PreviewDLSS` off at run time releases the preview GPU objects (images and NGX features) as soon as their last GPU work has finished.

## Frame pacing trace

A CPU timing trace of the FFXIV present path (off by default) and a switch for the hidden DX11 swapchain present. Status: new. The core, the policy, the seam body (against a fake swapchain) and the DXGI flag handling (against a real WARP swapchain) are unit-tested; nothing of it has run in game.

**Trace.** With `[FramePacing] Trace=true` (or file logging at Debug or Trace with the key left on `auto`) FFXIV logs, every 10 seconds and per thread, one line per timed place: `Frame pacing CPU [<name>] tid <n>: calls N, mean x ms, max x ms, >=8ms a, >=16ms b, >=33ms c`. The names are native present (the whole DX11 bridge Present), hidden DX11 present, FG dispatch, Reflex sleep, output present (overlay plus the present of the visible swapchain), scene NR recording and preview NR. When DLSS-G is active the phases nest: the native present contains the hidden present and the output present, and the output present contains the Reflex sleep, so compare each phase on its own. The lines are CPU time only; queued GPU work is not counted, so they show where the render and present threads wait. One line at the start says whether the trace runs: `Frame pacing trace: on (key true)`, `on (Debug log)`, `off (key unset, log level 2)`, `off (key false)` or `off (not FFXIV)`. With the trace off a timed place costs a few loads and no lock.

**Hidden present switch.** `[FramePacing] HiddenPresentDoNotWait=true` adds `DXGI_PRESENT_DO_NOT_WAIT` to the DX11 bridge's present of the hidden swapchain: a busy chain skips that present instead of blocking (counted as `skipped k` on the hidden-present line; one INFO line after 120 skips in a row). It fails safe: if DXGI answers a flagged present with an invalid-argument or invalid-call result, the flag is switched off for the rest of the session (one WARN line, `hidden DX11 present: DXGI rejected DO_NOT_WAIT`) and presents go out exactly as without the key. With the key on, the frame statistics of the game-facing swapchain count only the presents DXGI accepted. Default off (the old call, unchanged).

Code: `ext/present/` (`FramePacingCore.h`, `FramePacingTrace.cpp`, `FramePacingConfig.h`, `HiddenPresentPolicy.h`, `PresentSeams.h`). Seams: present `PacingScope`, `HiddenPresent`, `NativeBegin`/`NativeEnd`, `FgDispatchBegin`/`FgDispatchEnd`, `RecordSample`. Upstream lines: 3 (`wrapped/wrapped_swapchain.cpp`, `hooks/FG_Hooks.cpp`, `with_dx12/dx11_with_dx12_sc.cpp`). Config: `[FramePacing] Trace`, `HiddenPresentDoNotWait` (ini only, no menu control).

## Automatic mipmap bias

**Two modes.** In FFXIV the bias is applied when the game binds a sampler (the bind-time mode, below). In other games, or if the sampler hooks cannot be attached, the older create-time mode is used (the paragraphs after the bind-time ones). The older mode stands down while the bind-time hooks are attached.

**Bind-time mode (FFXIV, on by default).** Keeps the texture sharpening matched to the upscaling ratio with no number to work out by hand and no restart after a quality change. The target is `log2(render width / output width)` of each DX11 upscaler evaluate (the render width is the smaller of the render subrect and the NGX Width, the output width is OutWidth, else the width of the Output texture, else the display width of the create), so native resolution (DLAA) gives 0, Quality 1.5x gives -0.585 and Performance 2x gives -1.0; `MipmapBiasAutoOffset` (-3 to 3) is added. The target is steadied: a change smaller than 1/64 of a log2 step is ignored, at most 4 new targets per second are taken, and an evaluate whose output size differs by more than 10 % from the main one (a second feature, a preview window) is ignored until it has been alone for 2 s or 120 evaluates.

**How it is applied.** FFXIV caches its sampler states, so a bias written when a sampler is created never reaches the samplers made before a quality change. The fork therefore applies the bias when a sampler is bound: it hooks `SetSamplers` and `GetSamplers` of the six shader stages on the game's immediate context and, for the samplers the game made with a negative bias (mipmapped, not comparison/minimum/maximum filters), binds an immutable copy that carries the current target. `GetSamplers` still returns the game's own sampler, so state saves and restores see what the game set. Samplers are recognised when the game creates them (an own hook on `CreateSamplerState`, attached at the first upscaler create and detached first, because two Detours hooks on one function must be undone in reverse order) or, for samplers made earlier, at their first bind. At most 256 samplers take part; the rest keep the game's bias. The copies are made at the evaluate, not on the bind path: when the target changes the samplers bound at that moment are rebound at once, and a sampler whose copy is not ready yet is bound as the game made it for at most one evaluate. There is no lock on the bind path. Deferred contexts and any other context are passed through untouched, and any failure leaves the game's own samplers. The hooks follow the immediate context recorded when the device was hooked; if the evaluate arrives on another context of the same class (a ReShade proxy), the hooks move to it and a warning names both contexts.

**Add or replace.** Some games add their own DLSS bias (FFXIV appears to add `-1 + log2(scale)` to one family of samplers), others keep constant art biases. Until the game's biases are understood, the target is ADDED to the game's own bias, which is what the manual setting does. The fork watches the samplers the game makes and the target in force when each was made. A new bias of the same sampler family that differs from an older one by the same amount as the target moved (the target must have moved by at least 0.25, the match is within 0.08) means the game follows the mode: the mode becomes REPLACE, provisional at first and confirmed when a further quality change gives another such pair or a second sampler family shows one. Several pairs that disagree keep ADD and the fork looks again at the next change; ADD for lack of data is never final. REPLACE applies only the change of the ratio since a sampler was made, plus the offset, so the game's own constant part is kept: at native resolution the game's biases are untouched, and a sampler made at Quality with -1.585 stays -1.585 until the ratio changes. A session that stays on Quality never reaches "confirmed" and stays provisional REPLACE (the look is the right one). The decision is logged (`Bind-time mip bias: ... REPLACE mode ...` or `... staying in ADD mode ...`).

**Settings.** `[Mipmap] MipmapBiasAuto` (default on for FFXIV, off for other games; `AutomaticFFXIV` is accepted as another name, the main key wins), `MipmapBiasAutoOffset`, `MipmapBiasObserve` (debug, off: logs every distinct original sampler bias seen at each ratio). A value set by hand (`MipmapBiasOverride`, also the "Mipmap Bias" card) always wins: the bind-time mode applies nothing while it is set and the log says `Bind-time mip bias: not applied because MipmapBiasOverride is set by hand`; clear it (set it to `auto`) and the feature resumes at the next evaluate without a restart. A live ini that carries a number in `MipmapBiasOverride` therefore gets none of this until that key is set to `auto`.

**Status.** Untested in game (the bind-time mode). The pure rules, the sampler table, the bind path, the six stages through real Detours hooks on a software D3D11 device, the settings and the install order are tested offline (`tests/ext/upscaler/mip_bind_*`). The older create-time mode ran in sessions with the manual value.

**Known limits.** The detector can mistake two art values of one sampler family that lie exactly one target move apart for a tracking pair; REPLACE is one global mode, so art samplers made at different ratios may differ in look (an in-game A/B is needed before treating families separately); command-list playback (deferred contexts) binds samplers without passing the hooks until the next rebind, and FFXIV uses the immediate context; the table never recycles dead entries (a warning is logged when 256 are used); the evaluate sizes (`Width` or subrect, `OutWidth`) are read as FFXIV reports them and not yet seen live; the context handling rests on the hooked class's function being the same and was tested with fake pointers and two software devices, not with a real ReShade wrapper; the hooks are attached or detached with the calling thread only, so a thread inside the first bytes of a patched function at that moment is a risk accepted at quiet moments.

**How to check.** Remove or set to `auto` any `MipmapBiasOverride` in the ini. Start the game with default settings and read `OptiScaler.log`: `Bind-time mip bias: sampler hooks installed ...`, `CreateSamplerState hook installed` at the first upscaler create, then one `Bind-time mip bias: render width W, output width O, ratio bias B, offset X -> target T (add mode, first measurement)` line and one line per later change of the quality preset (with the default offset of 0 the targets are 0.0000 at DLAA, -0.5850 at Quality 1.5x, -1.0000 at Performance 2x). After the first change one decision line says whether the game's own sampler biases follow the mode (`REPLACE`) or are art values (`ADD`). The textures must keep their sharpness after each change without a restart and the frame time must not change. With `MipmapBiasAuto=false` there are no `Bind-time` lines.

**Code:** `ext/upscaler/MipBind.h` (target, eligibility, add/replace detector, gate, texts), `ext/upscaler/MipBindEngine.h` (sampler table, variants, bind path), `ext/upscaler/MipBindControl.h` (controller and install plan), `ext/upscaler/MipBindHooks.cpp` (attaches it to the game). **Seams:** no new seam; `OnD3D11DeviceHooked`, `OnD3D11Unhook` and `OnUpscaleBoundary` also reach the bind-time module, and the first upscaler create reaches it through `mipbias::OnFeatureCreate`. **Config:** `[Mipmap] MipmapBiasAuto`, `AutomaticFFXIV`, `MipmapBiasAutoOffset`, `MipmapBiasObserve`, fragment `ext/ini/Mipmap.ini`. **Menu:** card "Automatic Mipmap Bias" in the Textures tab.

**Create-time mode (other games, or when the hooks cannot be attached).** The paragraphs below describe this older mode.

**What it does.** Works out the texture sharpening (mipmap bias) that goes with the upscaling ratio, so there is no number to calculate by hand. While `MipmapBiasAuto` is on, the value is `log2(render width / display width)` of the newest upscaler the game created (the same number as the calculator in the "Mipmap Bias" card, with the output scaling multiplier taken into account), plus an optional offset. It is applied the way upstream already applies `MipmapBiasOverride` to the samplers the game creates: added to the game's own bias, only for samplers that already have a negative bias unless "MB Override All Textures" is ticked, and, with the upstream "MB Fixed Override" option, replacing those biases by the single value (the Scale option is not supported, see "Modes and limits" below). It follows the latest accepted create, so 3840x2160 (native DLAA at the login screen) gives 0, a forced Quality preset (2560x1440) gives -0.585 and Balanced (2258x1270) gives -0.766. A create that is not a game scene (a size missing or outside 20 to 16384, a display narrower than 640 pixels, a portrait display such as the character preview's) is ignored and leaves the value alone. The override stays engaged for as long as the option is on; turning it off puts your own `MipmapBiasOverride` from the ini back. Like the manual value it only reaches samplers created after a change: samplers the game made earlier keep theirs.

**Status.** Create-time mode: opt-in, off by default; untested in game. The sampler path is the manual value's, which runs in every tested session; the automatic part (which create to follow) has only been replayed offline on the logged sessions.

**Code:** `ext/upscaler/MipBias.h` (formula, source policy, log and menu texts, tested in `tests/ext/upscaler/mip_bias_*`), `ext/upscaler/MipBias.cpp` (glue), `ext/upscaler/menu/MipBiasMenu.cpp`. **Seams:** none added; the existing upscaler seam `ApplyForcedQuality` also hands every feature create to the automatic mip bias. **Config:** `[Mipmap] MipmapBiasAuto`, `[Mipmap] MipmapBiasAutoOffset` (-3 to 3, default 0), fragment `ext/ini/Mipmap.ini`. **Menu:** card "Automatic Mipmap Bias" in the Textures tab, after "Mipmap Bias".

**Good to know.** A manual number worked out for another preset gives a different look: forcing Quality with Balanced's -0.766 typed by hand becomes -0.585 automatically, and an offset of -0.18 gives back -0.765. FFXIV seems to add a bias of its own to one family of samplers, which stacks with this exactly as it does with a manual value. The sizes are read when the game creates its upscaler, so a game that changes its render size every frame without recreating it (dynamic resolution) is not followed; FFXIV recreates its upscaler on a quality change. With FSR 3.1 inputs the display size can still be changed after the automatic bias has read it (the upscaler takes it from its own structure), so the value there follows the size the game gave NGX; not relevant for FFXIV. In the menu, "Set" and "Reset" in the upstream card above are overwritten at the next quality change while this is on.

**Modes and limits.** The additive mode (the default) is the one this feature is made for. "MB Fixed Override" replaces the game's own per-sampler biases (for example -0.5, -1, -2) by the single value, which is a different look from adding to them. "MB Scale Override" multiplies the game's bias by the value; the automatic value is negative below 1:1, so the product would blur the textures (and at native DLAA a value of 0 would wipe out the game's own bias). So the automatic bias does not engage while Scale is on: the log shows one warning, `Automatic mipmap bias: not applied while MB Scale Override is on ...`, the card shows a red line, and your own manual value stays in force. Ticking or unticking Scale while the option is on takes effect at once while the Automatic Mipmap Bias card is on screen, and otherwise at the next quality change (the next time the upscaler feature is created; only the card looks in between, so with just upstream's Mipmap Bias card pinned to the Custom Tab, or another tab open, the multiplied value stays in force until then; with no manual value of your own, the override is then empty and the upstream card greys both mode checkboxes out; press "Set" in the card above to enable "MB Scale Override" again before unticking it), and the sizes of the creates seen in the meantime are kept, so unticking applies the right ratio immediately. The output scaling multiplier is counted only where the upscaler really enlarges its output, the condition the upscalers themselves use: output scaling on and (low-resolution motion vectors or render size equal to display size); with full-resolution motion vectors and a render size below the display size the log line shows no output scaling and the plain ratio is used. The extra offset slider limits a value typed with Ctrl+click to -3 to 3. Known limits: turning the option off from the menu gives your ini value back in two steps that the texture hook does not lock against (upstream's own "Reset" button has the same exposure), so turn it off while no level is loading, or edit the ini; a screen turned to portrait (display taller than wide) is not followed, because such creates are ignored, so on a rotated monitor the bias stays at 0 plus the offset.

**How to check.** Set `MipmapBiasAuto = true`, start the game and read `OptiScaler.log`: every accepted create logs a line (on FFXIV the two DLSS layers each read the same numbers, so every line comes twice in a row and the second one says `unchanged`; the existing `SetInitParameters Render Resolution` line is doubled the same way), `Automatic mipmap bias: create render 3840x2160, display 3840x2160, ratio 1.000 -> bias 0.0000 ...` at the login screen and `... create render 2560x1440, display 3840x2160, ratio 1.500 -> bias -0.5850 (was 0.0000 ...)` after the quality switch, and a create that was ignored logs `ignored create ...` with the reason. With `MipmapBiasScaleOverride = true` the first create logs the warning above instead and no `create render ...` lines. With the debug log level the existing `Overriding mipmap bias X -> Y` lines after it show the sampler hook received the value.

**DLSS presets L and M.** The fork forwards `[DLSS] RenderPresetForAll = 12` (L) and `13` (M) to NGX unchanged, like the working `11` (K), so to see whether the installed DLL takes them set the key, start the game and look for `Using App hint Preset L` (or `Preset M`) in `OptiScaler.log`; a line that still says K means the DLL does not accept the letter.

### Game jitter probe (diagnostic, off by default) and jitter correction (experimental, off by default)

**What and why.** The game renders its scene with a jitter translation it scales itself and tells the upscaler the unscaled pixel jitter; they agree only when the game's scale s is 2. `[FFXIV] JitterProbe` (false) reads the game's camera jitter object (read only, guarded, matched game build only) and writes one log line about every 10 seconds, and early when the render size or preset changes: `Game jitter: counter N, reported jx/jy ..., ndc ..., render WxH (source), applied ax/ay ..., ratio rx/ry ..., signs ok, implied s = 2.000/2.000 (consistent), NGX saw the same values; NGX subrect ..., Width/Height ..., PerfQualityValue ...; last forced-quality answer ...`. `s = 2` on both axes means the game applies what it reports; another value means the upscaler is told a different jitter than the one in the picture; `signs MISMATCH` means an axis has the opposite sign. A failed check logs one line per episode (`Game jitter: not read, guard failed: ...`) and does nothing else. **Measured in game** (the released build, DLSS preset M): the picture moves by only 60% of the jitter the game tells DLSS about, `ratio rx/ry 0.600/0.600` in every sample, at DLAA and at Performance alike. Transformer presets (L, M) depend on accurate jitter more than the CNN preset K, which fits the reports that L and M look jittery. Quality (1.5x) and Balanced are not measured yet.

**Correction (experimental): calibrate and scale.** `[FFXIV] JitterCorrection` (false; also a checkbox, with the probe key, in the menu card "Game jitter (FFXIV)" in the FFXIV tab, after the FFXIV HDR10 card: it applies at once and is stored in the ini when the settings are saved). It learns the ratio applied/reported from snapshots of the game's jitter object and then multiplies the `Jitter.Offset.X/Y` pair of every DLSS evaluate by it, so the upscaler is told the jitter that is in the picture. The ratio is a property of one snapshot (its own jitter and NDC pair), so a snapshot does not have to belong to the evaluate in hand; this is why it works whether or not the game thread and the render thread are a frame apart. An earlier version replaced the pair only after proving, for every evaluate, that the object belonged to it; in the maintainer's session that proof held for 11% of 9418 evaluates and the correction flapped between corrected and uncorrected frames, which is why it was replaced by this design. How it works: (1) a snapshot is accepted when the object was read cleanly, the render size is known from the game's Width/Height, both axes have enough jitter to give a ratio (at least 1/64 pixel), the signs agree, the applied jitter is at most 1 pixel and the object's frame counter is higher than at the previous snapshot (the same camera step counts once; a counter that goes down, such as a re-created camera, re-bases). (2) Five accepted snapshots in a row that agree within 2% (and whose two axes agree with each other) adopt their mean as the ratio: `Jitter correction: calibrated ratio 0.600/0.600 from 5 snapshots for render 1920x1080, output 3840x2160, quality 0; scaling the reported jitter`. Until then the game's values pass through. (3) A ratio within 2% of 1 means the game already hands DLSS what it applies: nothing is applied (`the game already hands DLSS the jitter it applies`). A ratio above 1.02 or below 0.25 is refused with one line and nothing is applied. (4) The adopted ratio keeps being checked against every accepted snapshot; isolated contradictions (a torn or off-frame snapshot) are counted and change nothing, five contradictions in a row that agree with each other replace the ratio (`ratio changed after 5 contradicting snapshots: was ..., now ...`). A failed read of the object never changes an adopted ratio; when no snapshot has been accepted for 10 seconds the ratio keeps being applied and the log says `verification stale` once, and `jitter snapshots are arriving again` when they return. (5) The calibration belongs to one configuration (render size, output size, quality, the forced-quality answer): a different one drops the ratio and learning starts again (`configuration changed to ...; calibration dropped, learning again`). (6) Every evaluate whose NGX pair is present, finite and not above 0.55 pixel is scaled: X first, then Y, with the pair read before any write; anything else passes the game's values through and is logged once per episode (`jitter pair not usable`). The first scaled pair of a calibration logs what the parameter block holds afterwards (`parameter block read back: (x,y)`). A consistent game is never touched. Both keys cost two config reads and a branch while off. Default off; to be validated in game, with frame generation off first.

**What the scaled pair reaches, and how to test it.** The correction writes once, into the parameter block of the evaluate in progress, and nothing puts the pair back afterwards (restoring it would hand the upscaler one value and frame generation another, because frame generation reads the block after the upscaler's evaluate). So everything that reads the block after the write sees the scaled pair: the DLSS super resolution, frame generation (also its guide-delay mode, which replays the corrected value together with that frame's guides), the DLSS-NR path (it copies from the same block), the `Jitter Count` value in the menu (it counts the applied pairs), and the FSR and XeSS backends if one of them is selected. A comparison of "correction on" against "correction off" with frame generation active therefore changes the upscaler and frame generation together. Test with frame generation (and NR) off first, then with frame generation on. The status line says whether frame generation is active.

**The stale block, and the status line.** Multiplying is not harmless the way writing an absolute value was: if the game does not set `Jitter.Offset` again before the next evaluate (or the engine runs twice for one evaluate), the block still holds our own result and scaling it again would shrink the jitter every time. So the engine remembers the pair it wrote last, exactly as passed to the block, and an evaluate whose pair equals it bit for bit on both axes is not scaled again; it is counted as `already scaled (block not refreshed)`. The count is also the in-game answer to the open question whether the game sets `Jitter.Offset` at every evaluate: a count near zero means it does, a count near the number of evaluates means it does not. The engine therefore remembers, next to the pair it wrote, the game's own RAW pair that it was derived from. When the pair read equals the written pair bit for bit on both axes, the block was not refreshed and the raw pair is the remembered one (never the pair read); the wanted pair is re-derived from it every time: raw times the current ratio, or the raw pair itself when nothing is to be applied (still learning, a consistent or refused game, a manual scale of 1.0 or 0, a new configuration that starts the learning again). A wanted pair that equals the written one is not written again (counted `already scaled`); a different one is written (counted `scaled`, or under `learning` / `left alone` when the raw pair is put back). So a ratio change, a configuration change or a slider drag on a block the game does not refresh never compounds (raw 0.3 at ratio 0.6 then 0.8 gives 0.24, not 0.144), and a state that applies nothing leaves the game's own pair in the block. A pair the game has refreshed is simply the new raw pair. The remembered pair is forgotten only when the game refreshed the block and when the correction is switched off; after a write that failed half way it holds what the block is believed to hold (what it held before when the first value could be put back, the mixed pair with the true raw pair when it could not, so the next evaluate repairs it). Two coincidences are possible and harmless: a raw pair of exactly (0, 0) is counted as `already scaled` although the game refreshed it (0 times any ratio is 0, so the write would change nothing), and a genuinely new raw pair that is bitwise equal to the pair written last would be treated as not refreshed for one evaluate (practically impossible: the game's jitter sequence does not repeat). The status line reads `Jitter correction: on; totals since the start of the session: N evaluates seen, N scaled, N passed through while learning, N passed through because the jitter pair was not usable, N already scaled (block not refreshed), N left alone (nothing to apply); state: calibrated ratio 0.600 for render 1920x1080, output 3840x2160, quality 0; snapshots: N accepted, N disagreed with the ratio, N ratio changes, N restarts after a configuration change; verification fresh|stale; frame generation active yes (input Upscaler)|no (input NoFG)|unknown`; the state is `learning`, `calibrated ratio R`, `consistent (ratio R), nothing applied` or `refused (ratio R), nothing applied`, each with its configuration, or `dropped after a configuration change, learning again`. It comes about every 10 seconds for the first 60 lines and once a minute after that, and every line holds the totals since the start (subtract two lines for a window). What to look for in a good session: a `calibrated ratio` line within a second or two, then `scaled` close to the number of evaluates, `disagreed` and `ratio changes` near zero. Only the input named `Upscaler` reads the scaled pair from the parameter block; with another frame-generation input (`DLSSG`, `NvngxFG`, `FSRFG` ...) the field can say `yes` while the pair never reaches frame generation.

**Manual scale for experiments.** `[FFXIV] JitterScaleOverride` (0 = off, "auto" means 0; also a slider "Manual jitter scale (0 = learn it)" in the same menu card, greyed out while the correction switch is off; it moves in steps of 0.05 so it can land on exactly 0.6 or 0.8, and anything below 0.25 snaps to 0 = off) is an experiment key and may be removed once the correction has been validated. A value from 0.25 to 1.0, used while `JitterCorrection` is true, takes precedence over the calibration: nothing is learned and every evaluate is scaled by the value through the same path as above (reads before the write, X then Y, the 0.55 pixel limit, the stale-block guard, the put-back). The values to try, one after the other with the same scene: `1.0` (nothing is changed, the baseline), `0.8`, `0.6` (what the probe measured) and `0.5`. If the calibrated build looks the same as the baseline, comparing these tells "the 0.6 theory is wrong" from "the correction works" without another build. 0 is off and is never applied as a scale; a value that is not a number, negative, below 0.25 or above 1.0 is ignored (the calibration goes on) and logged once (`manual scale value ... ignored (valid values are 0.25 to 1.0, 0 turns it off)`). A value within 2% of 1.0 writes nothing. Switching it on drops the calibration state, switching it off starts learning from scratch; a change of the value is applied to the game's raw pair, so it never compounds on a block the game does not refresh, and 1.0 or 0 puts the raw pair back; each change of the value logs `manual scale 0.800 in use, calibration off` once, and the status line then reads `state: manual scale 0.800 (calibration off)` with the same counters.

**Limits.** (1) A second, differently sized DLSS evaluate in the same frame flips the configuration at every evaluate, so the correction never finishes learning (inert, the game's values pass through; the `configuration changed` lines are capped at 32). (2) The ratio is only as good as the formula `ax = ndcX * renderW / 2, ay = -ndcY * renderH / 2` that comes from reading the game's code; the constant 0.600 at two different render widths argues that the render-size part is right, and the manual scale is the cheap test of the rest. (3) Quality (1.5x) and Balanced are not measured. (4) With both keys off a pause keeps an adopted ratio (the zero-cost default); switch the correction off and on to start learning again. (5) A pair that arrives with a jitter above 0.55 pixel, or without one, is not scaled.

**Cost and log budget.** With the probe alone, the clock decides between samples: nothing is read in the first 2 seconds after a sample; after that the parameters (nine lookups) are read on every 16th evaluate to notice a changed render size or preset, for as long as the session lasts, and again at each 10-second sample. With the correction on, every evaluate reads the parameters and the object (one pass of reads). At most 360 sample lines are written per session (then one line says so); failure episodes, unusable pairs, the first scaled pairs and each kind of calibration event are capped at 32 lines each, and the count of episodes that did not get a line is reported when it changes (`Game jitter: log line budget used up, episodes not logged so far: N probe failures, N pass-throughs, N replacements, N abandoned steps, N calibration events`; `pass-throughs` are unusable pairs and `replacements` are first scaled pairs; the first 60 reports as they change, then at most one a minute, always with the totals). The status line is thinned the same way instead of being cut off. A step that throws is abandoned (the rest of that evaluate is skipped, the learning run in progress is dropped but an adopted ratio is kept) and logged once per episode (`Game jitter: step abandoned after an exception: ...`); the same place failing again and again is one episode, even when the evaluates between two sample ticks complete, and the episodes beyond the 32-line budget are counted in the report as `N abandoned steps`. A pair whose second value could not be written is put back to the game's own first value (best effort), so the upscaler is not handed a mixed pair for that evaluate. Switching the correction key off while the probe stays on drops the whole calibration; learning starts again when it is switched back on.

**Jitter at the source (`[FFXIV] JitterSource`, experimental, default off, not yet validated in game).** In DLSS mode the game draws the scene with only a fraction of the sub-pixel jitter its generator produces (the native strength, measured 0.6, so +-0.3 px instead of +-0.5 px) and calls the generator with an unbounded phase count, so the pattern never repeats. `JitterCorrection` can only change what the upscaler is told; it cannot recover sub-pixel samples that were never drawn. With `JitterSource=true` the fork changes what is drawn: a hook on the game's jitter generator (called by the camera update) divides its output by the game's own native strength, so the game's multiplication leaves the full +-0.5 px lattice, and replaces the unbounded phase count by NVIDIA's `ceil(8 * output pixel area / render pixel area)` (8 at DLAA, 18 Quality, 24 Balanced, 32 Performance, 72 Ultra Performance), recomputed on every call, so a quality or size change follows at once. The hook only touches the WORLD camera's jitter object (the one the world-scene NGX packet is built from, learned from a second hook on the camera getter); any other object that reaches the same call site is left alone and logged. At the DX11 evaluate boundary (the same place `JitterCorrection` writes) `Jitter.Offset.X/Y` of that frame are replaced by the offset that was drawn (`x = ndcX * width / 2`, `y = -ndcY * height / 2` of the same frame, paired with the packet by its raw value, render size and age). Super resolution, frame generation (also the guide-delay replay) and the Jitter Count readout read the same block, so they all get the drawn value. The motion-vector jitter compensation and every other buffer the game derives from the jittered projection follow automatically because the change is made before the game builds them. `JitterCorrection` stands down for every evaluate the fix tells; when the fix is off or has fallen back it works exactly as before. Fail-open means today's behaviour: any mismatch of the executable (identity and the instruction-guard blocks), a failed hook install, the key off, or a generator that is not being normalised for a second (not in DLSS mode, native strength out of range, world camera not learned or never seen at the call site) switches the generator hook and the told-offset write off together. A verification runs on every frame whose generator record is known: the drawn offset is compared with the generator's own Halton value (tolerance 0.005 px); 90 consecutive frames outside, or 90 consecutive evaluates that match no camera sample, make the fix fall back for the session (switching the key off and on again tries once more). A frame that matches no camera sample is told the generator's recorded value for that raw pair when there is one and otherwise left to `JitterCorrection`; only three evaluates within a second with no record and a value above 0.55 px (more than the scaling accepts) fall back at once. The character preview keeps its own 32-phase path. Log lines: `Jitter source: hooks installed (...)`, `Jitter source: active (strength 0.600, phases 32 for render 1920x1080 output 3840x2160)`, `Jitter source: verified N frames, drawn offset equals the generator's value (max deviation ... px, outside 0.005 px: 0), ...; told offsets over N frames: x a..b px, y c..d px, D distinct pairs (phase count P)` (it says `differs ... in N frames` when any frame was outside), `Jitter source: phases A -> B (...)` on a quality change, `Jitter source: the generator's camera call site was reached with N distinct jitter object(s): ...`, `Jitter source: inactive (<reason>)`, `Jitter source: fell back to the old behaviour, ...`. With the key off no hook is installed and the cost is three config flag loads, one relaxed atomic load and a branch. Experimental: the arithmetic and the executable anchors were checked against the October 20 executable (SHA-256 46A52AB1...), but the visual result has not been confirmed in game.
