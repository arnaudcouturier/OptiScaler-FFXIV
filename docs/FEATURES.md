# Feature reference

What this repository bundles on top of OptiScaler, where each piece comes from and lives, how it attaches to upstream files and how to configure it. The short status table is in [STATUS.md](STATUS.md) (the README has a one-screen summary); this file is the long version and uses the same status words. Long histories, review rounds and measurements are in [docs/notes/](notes/); the entries link to them. Credit and licences: [ATTRIBUTION.md](ATTRIBUTION.md).

**Status words.** *tested* means the author played the game with it on an RTX 4090. *untested* means it compiles and follows the same code paths as the tested features, but nobody has verified it on real hardware (or in game) yet. Where a feature runs inside a tested path but was never exercised alone, the entry says so. Nothing here is a promise that a feature works on your system.

**Origin words.** *SirenBrink's fork* is the community repository `SirenBrink/OptiScaler_DLSSNR_Multipass_MFG_FFXIV` (GPL-3.0). *The import base* is its commit `36c53a15`. *v6.0* is its commit `e17a7362` (2026-10-20). *Ported* means the code came from SirenBrink's fork at the import base and was moved under `ext/` behind seams. *Follows the approach* means the design is the same or close and the code was written for this fork.

**Fields of an entry.** **Origin**: where the code or the design comes from. **Config**: `[Section] Key` as written in `OptiScaler.ini`; defaults and explanations are in the matching fragment under `OptiScaler/ext/ini/`, which `tools/package.ps1` merges into the shipped `OptiScaler.ini`. **Menu**: the card id in the in-game menu, with its tab. **Code and seams**: directories and key files under `OptiScaler/ext/` (every file the fork owns is under it) and the areas of the one-line seam calls in upstream files. File lists and seam function names per feature: [notes/feature-code-and-seams.md](notes/feature-code-and-seams.md); the full list is [SEAMS-catalog.md](SEAMS-catalog.md), the rules are in [SEAMS.md](SEAMS.md).

## DLSS Neural Rendering (NR)

### DLSS Neural Rendering (NR) with pre-SR multipass

**Origin.** Ported from SirenBrink's fork at the import base (originally Dagherbou's NR work, with y4my4my4m's multipass, janblade's PassFeedback and later work by wilsjo2), moved under `ext/nr` behind seams. Of the 47 files in `ext/nr` that have a counterpart at the import base, 22 are identical apart from line endings and 25 add about 8% more lines; about 20% of the lines in `ext/nr` are in files with no counterpart. The integration layer (NrSeams, NrHooks, the `[DlssNr]` config binder, build-time shaders) and `VitCapture` are fork code.

**What it does.** Runs NVIDIA's DLSS Neural Rendering model on the frame, before ordinary super resolution (pre-SR) or after it, in one to three passes with per-pass profiles. A colour pipeline maps the game's image into what the model expects and back (white point, exposure, reversible tone mapping). It includes the exposure scan (reads the game's exposure from resource creation and unordered-access views) and named user presets. It needs NVIDIA's `nvngx_dlssnr.dll`; see [INSTALL.md](INSTALL.md).

**Status.** tested (RTX 4090), pre-SR multipass included. Exposure scan, white point, presets, compare views and the debug view are used by the tested sessions but not tested separately. `DeferredDLSS`, `ResidualFG`, spatial compression and `WorkingScale` other than 1.0 are experimental or opt-in and untested, as is the frame rate governor.

**Config.** `[DlssNr]` (99 keys): `Enabled`, `DisableOnFocusLoss`, `ToggleKey`, `ScaleUpKey`, `ScaleDownKey`, `TransferToggleKey`, `RunBeforeSR`, `Passes`, `PassFeedback`, `Pass2*`, `Pass3*`, `Preset`, `Style`, `Intensity`, `WorkingScale`, `WorkingScaleX`, `WorkingScaleY`, `DepthAwareResolve`, `ClassicSharpen`, `ClassicSharpenStrength` (see [NR Classic enlargement sharpening](#nr-classic-enlargement-sharpening)), `Governor`, `GovernorTargetFps` (see [NR frame rate governor](#nr-frame-rate-governor)), `ReversibleMode`, `WhitePointSource`, `ScanAnchors`, `LightingHistory`, `SkinProtection`, `PreSRTrailGuard`, `SplitFrameWork`, `Compare*`, `DebugView`, `ReplayCapture` (ini only, see [NR frame replay](#nr-frame-replay)), `GovernorProbe` (ini only, see [NR frame rate governor](#nr-frame-rate-governor)), `Runtime`. `[Hotfix] RenderSizeFromWidthHeight` and `[QualityOverrides] ForcePerfQuality` belong to the [FFXIV module](#ffxiv-module).

**Menu.** `dlss_nr` (tab Upscaling), plus an overlay for the compare tags and the exposure-scan lamp, a GPU-time row, and the NR on/off, model resolution and enlargement shortcuts in the Keybinds list.

**Code and seams.** `ext/nr/` (`pass/DlssNr_Dx12.cpp` is the D3D12 pass; `presr/`, `exposure/`, `presets/`; shaders in `shaders/`, compiled at build time). The forwarder `ext/nr/forwarder/dlssnr_forwarder.cpp` is the second project in `OptiScaler.sln`; its odd output name `nvngx.dll_dlssnr.dll` is deliberate, because NVIDIA's model only answers a caller whose module path contains `nvngx.dll`. Seams: nr, restrack, dx11bridge, menu, gpu.

### NR model version picker

**Origin.** Follows the approach of SirenBrink's v6.0 NR model picker (same search roots in the same order, a runtime revision and "runtime generation", `Current()` and `Startup()`). The catalog, scan, card, live switch and rebuild code are written for this fork. `Runtime=auto` means the newest model here; in v6.0 it means the legacy file only.

**What it does.** Keeps several NR model files side by side and switches the running model without a restart, in the scene and in the character previews. Put each model file in its own folder `OptiScaler\NR.<version>` (digits separated by dots, for example `OptiScaler\NR.310.9\nvngx_dlssnr.dll`) next to the game, beside or instead of the old single `nvngx_dlssnr.dll`. The `NR model version` combo in the Neural Rendering card lists the old file ("Legacy location") and every valid folder; `Automatic` (the default) is the newest version, and on a tie the old file wins. A choice that is not installed never falls back to another model: the card says Neural Rendering is unavailable and the pass shows the plain upscaler image. A switch happens 250 ms after the last click and loads the new file by its full path; model files are never unloaded. A restart is needed only for the NGX core's first search path, native Vulkan NR, the hybrid FP4 precision (`Precision=4`) and the AMD bridge.

**Status.** new; tested (RTX 4090) on 2026-10-23: live switch and reload from an `NR.<version>` folder work; `NR.310.8.0.0` cannot create its feature on this GPU (NR skips itself, switching back recovers); a switch between two different working models was not seen. The catalog, scan, selection, switch, text and glue are unit-tested, including that two same-named DLLs in two folders load as two modules when loaded by full path. Known limits: [notes/nr-picker-and-focus-pause.md](notes/nr-picker-and-focus-pause.md).

**Config.** `[DlssNr] Runtime`: empty or `auto` = newest, `legacy`, or a folder name such as `NR.310.8`. Not part of the saved NR presets. **Menu.** `dlss_nr` card, combo `NR model version` and button `Rescan`.

**Code and seams.** `ext/nr/runtime/`, `ext/nr/pass/DlssNr_Dx12.cpp`, `ext/ffxiv/chara/CharaNr.cpp`. Seam: nr `AppendNgxSearchPaths` (body changed, no new seam). Log: `DLSS-NR runtime catalog: N candidate(s)`, `DLSS-NR runtime revision N: <id> (<path>), file version ...`.

### NR pause on focus loss

**Origin.** Follows the approach of SirenBrink's v6.0 `PauseOnFocusLoss`: both pause when the foreground window does not belong to the game's process. v6.0 pauses at once; this fork waits 1 s and also covers the character preview.

**What it does.** Pauses NR while the game window is not focused (after 1 s without focus, at once when minimised). It covers the D3D12 and D3D11-bridge scene NR and the character preview NR; native Vulkan is not paused. The preview shows its plain image while paused and resumes with a clean history. Log: `CharaView NR: paused, window not focused` and `CharaView NR: resumed`.

**Status.** experimental, off by default; new; unit-tested. Nothing of the preview pause has run in game (the in-game proof needs a visible but unfocused window, not a minimised one).

**Config.** `[DlssNr] DisableOnFocusLoss` (off by default). `PauseOnFocusLoss` (the v6.0 name) is accepted as another name: it is moved into `DisableOnFocusLoss` when the ini is read and saved back as `auto`; when both are set, `DisableOnFocusLoss` wins.

**Menu.** In the `dlss_nr` card. **Code and seams.** `ext/nr/NrFocus*.h`, `ext/nr/NrConfig.cpp`, `ext/ffxiv/chara/CharaNr.cpp`. No new upstream seam.

### NR native path and ViT capture

**Origin.** Ported from SirenBrink's fork: the native path (`WrapNvapi`, module identity by size and SHA-256), `VitEvery` (following janblade's work) and the hybrid precision. The verified-module profile table uses the technique of wilsjo2's commit with a small addition here. `VitCapture` is fork-original (a log-only diagnostic).

**What it does.** The fork drives the NR model's own DLL directly. It records which CUDA entry points the game queried (`WrapNvapi`), identifies the model's CUDA module by size and SHA-256, and can skip repeated vision-transformer launches (`VitEvery`) for a module that has been verified. Unknown modules are never touched: reuse stays off and the log says why.

**Status.** The native path is tested as part of NR. `VitCapture` is a diagnostic that only observes. `VitEvery=2` reuse is untested for speed: it only activates for a module listed as verified in `ext/nr/native/DlssNrModuleProfiles.h`, and is a no-op otherwise. `VitAllowUnverified=true` skips the fingerprint check and can hang the GPU; leave it off.

**Config.** `[DlssNr] VitCapture`, `VitFirstPassOnly`, `VitEvery`, `VitAllowUnverified`, `Precision`. **Menu.** Status text in the `dlss_nr` card.

**Code and seams.** `ext/nr/native/`, `ext/nr/hybrid/`. The capture summariser is `tools/nr-vit-capture-summary.ps1`; profiling a new model file: [nr-vit-reuse-profile-runbook.md](nr-vit-reuse-profile-runbook.md). Seam: nr.

### NR frame replay

**Origin.** Fork-original.

**What it does.** A developer tool for checking NR shader changes without the game. With `[DlssNr] ReplayCapture = true`, a capture trigger (the `dlssnr-capture.trigger` file or `AutoCapture`) records a replay set of the NR pass instead of the before/after frames: two consecutive frames, every compute dispatch of the pass with its constants, the views it binds and the contents of what it reads and writes, the model's answers and the untouched game frame, in `dlssnr-capture\replay-<time>\` (manifest format version 2, one record per line). A test replays each dispatch on the Direct3D software adapter (WARP) with the build's own compiled shaders and compares the result bit for bit with a blessed reference made the same way; an incomplete set (a skipped dispatch, a missing picture) fails before anything runs. Blessing writes the reference images and needs its confirmation (`OPTISCALER_NR_REPLAY_BLESS_OK` set to `1` next to the bless request), or the test refuses and writes nothing. A capture shows the player's screen: keep it out of version control. The ordinary before/after capture's "before" image is now the untouched game frame (it was the encoded proxy).


**Status.** New; unit-tested on the software adapter with synthetic sets; not tried in game (no real capture yet). The game's exposure texture is not recorded, so the exposure paths replay with an empty input. Dispatches outside the scene pass (the deferred pre-upscale stages, the character preview) are not recorded. Limits: the write holds the render thread for seconds (a hitch at capture time only); the recorder moves the pass's guide inputs (the game's depth and motion when they are used directly) between the shader-read and copy-source states, relying on the input-state contract the pass already relies on.

**Config.** `[DlssNr] ReplayCapture` (ini only, default false). **Menu.** None. Details: [notes/nr-frame-replay.md](notes/nr-frame-replay.md).

**Code and seams.** `ext/nr/diag/NrReplay*.h`, the recorder calls in `ext/nr/pass/DlssNr_Dx12.cpp`; tests `tests/ext/nr/nr_replay*`. Seam: nr (no upstream change).

### NR spatial compression profiles

**Origin.** The Peripheral profile is the existing spatial compression (`PeripheralWarp` by BeliyG3, see [ATTRIBUTION.md](ATTRIBUTION.md)). The Foveated profile follows the design of maximedgoulet/FoveatedDLSS5 (MIT, copyright Carlos Lopez Jr. 2025, from RenoDX; its foveated grid is that repository's own work). The maths in this fork is written independently from that description. The independent X and Y axes, the pixel-share readout, the 500 ms settle and the partial park are this fork's.

**What it does.** The NR model runs on a smaller, warped copy of the frame and its answer is unwarped before it is composed. Both profiles keep the middle of the picture at the native pixel density and spend fewer pixels toward the edges; depth and motion vectors are warped with the colour. `SpatialCompression` is the master switch of both.

- *Peripheral* (default): a central region and a work budget as percentages of the frame, a continuous compression curve outside the centre (unchanged). The vertical sliders are independent of the horizontal ones in the config; the menu has a menu-only "Link X and Y" checkbox, on by default, that makes the horizontal slider set both axes as before.
- *Foveated*: per axis, density 1 inside a centre zone, a smoothstep falloff over one falloff length, then a flat edge density (0.25 to 1, set separately for width and height). The centre size and the falloff are in pixels of the output, with the share of the output printed beside each slider; they are converted to the frame the model actually processes (on the pre-SR path that is the active rectangle inside the larger colour allocation) and clamped to it every frame without changing the stored values. A centre as wide as the frame, an edge density of 1 or an axis shorter than 16 pixels leaves that axis unchanged. The placement offsets (`SpatialOffsetX/Y`) move the centre zone; the work shift is Peripheral only. When the saving would be under 5% of the NR pixels the profile stands down and ordinary NR runs; the menu says why.
- *Readout.* The card shows "NR pixels: NN% of full (model WxH)" for both profiles (the share of the ordinary NR pixels the model handles), plus the status text.
- *Falloff and the frame edge (Foveated).* The falloff is capped per side so that it ends at the frame edge when the centre zone plus the falloff would not fit on that side; the edge density is then reached exactly at the edge, with no flat part. With the centre offset at its extreme the short side's falloff can become short (a few tens of pixels) but stays smooth. An out-of-range offset is clamped (Peripheral still refuses it and stays inactive).
- *Settle.* A change of the model's working size (a Foveated or Peripheral size slider, Model resolution) is acted on after it has held for 500 ms; until then the model keeps running the layout it has. A change that only moves the warp at the same working size (an edge density, an offset) resets the NR history and keeps the model. A change of the frame size, of where NR runs, of the NR tuning, or a spatial fallback is handled at once as before. When only the working size changes, the frame-sized scratch textures are kept instead of being parked.

**Status.** Experimental and off by default. Unit-tested: the packed-distance maths against a numerical integral, pack/unpack round trip, the clamps and the identity cases, the sizes and share for 3840x2160 and for a 1920x1080 frame inside a 3840x2160 output, the 5% boundary, the layout and settings equality, the settle decisions and the 500 ms boundary, the preset round trip, and source pins for the pass wiring and the menu. The shader checks on the D3D11 software adapter pass (pack, guides and unpack against the host maths for both profiles; the fused native resolve against the legacy unpack for both profiles); the product builds with the shaders in every variant. Not tried in game: the visual quality of the Foveated profile, its real GPU cost, and the 500 ms settle on a live model.

**Config.** `[DlssNr] SpatialProfile` (0 Peripheral, the default; 1 Foveated), `FoveaWidth` (2400), `FoveaHeight` (1350), `FoveaFalloff` (400), `FoveaEdgeX`, `FoveaEdgeY` (0.5, clamped to 0.25 to 1). The pixel defaults are sized for a 3840x2160 output and give about 78% of the NR pixels. `SpatialCompression` stays false by default. All six are saved in the NR presets; a preset saved before they existed loads with these defaults. **Menu.** `dlss_nr` card, under "Peripheral spatial compression (experimental)": a "Spatial profile" combo, the sliders of the chosen profile, the readout; the offsets are in the closed Advanced fold (see "Menu layout").

**Code and seams.** `ext/nr/spatial/FoveatedWarp.h` (host maths), `ext/nr/NrSettle.h` (settle decision, partial-park selection), `ext/nr/spatial/DlssNr_Spatial.h` (layout, geometry), `ext/nr/shaders/dlssnr_spatial_warp.hlsli` (shared by `dlssnr_spatial.hlsl` and `dlssnr.hlsl`; the profile is a bit in the constant `flags` word and in the high bits of the resolve selector, no constant buffer grew), `ext/nr/pass/DlssNr_Dx12.cpp`.

### NR per-axis model resolution and depth-aware enlargement

**Origin.** The ideas follow xenmods/DLSSNR-Cost-Scaler (MIT): a model size that differs per axis and a depth-aware enlargement of the model's answer. The code is this fork's own, written from the description; no source was copied.

**What it does.**

- *Per-axis model resolution* (`[DlssNr] WorkingScaleX`, `WorkingScaleY`, default 0 = follow `WorkingScale`): the model works at (X x width) by (Y x height), each 0.25 to 2. Cost follows the product. DirectX 12 only: the Vulkan path and the AMD bridge use `WorkingScale` for both axes. With a different scale per axis the guides are resampled to the model's size on each axis and the motion vectors are scaled per axis. Spatial compression stays limited to 100% on both axes. A model resolution above 100% on one axis and below 100% on the other is not supported: when either axis is above 100% the other is raised to at least 100% (150% across with 50% down runs 150% x 100%); the menu, the guides and the motion vectors use the raised numbers. If the NR runtime refuses a model size that differs per axis, the pass logs one line and works at the uniform Model resolution on both axes until Model resolution or the horizontal or vertical setting changes (or the model file is switched); a refusal at a uniform size still ends NR for the session.
- *Depth-aware enlargement* (`[DlssNr] DepthAwareResolve`, default off): when the model works below the frame's size, each of the four taps used to enlarge its answer (Classic) or its changes (Matched residual) is weighted by how close the game's depth under the tap is to the depth under the output pixel, so the answer does not bleed across the edge of an object. Plain filter when the depth is unusable. DirectX 12 only; inactive with spatial compression, at model resolution 100% on both axes, and while either axis is above 100% (the checkbox and the Enlargement mode are greyed out and the status line says so).
- *NR time* readout: "NR time: x.xx ms" (GPU time of the last NR evaluation, "n/a" until measured) under the model size and next to the NR pixel share.

**Status.** Experimental and off by default. Unit-tested (sizes per axis, the mixed-axis rule, the refusal latch, the depth weights against a host reference) and checked on the D3D11 software adapter with synthetic depth; with the keys at their defaults the shader output is bit-identical to the previous shader. Not tried in game: an anamorphic model size has never been run through the NR runtime, and the depth-aware resolve has not run on the real depth buffer.

**Cost of the model resolution (measured on the benchmark client, not in game).** The official FFXIV benchmark (one RTX 4090, 2560x1440 output, the game's DLSS Balanced, NR in one pass) logged an NR time of 3.21 ms a frame at `WorkingScale` 1.0, 2.66 ms at 0.85, 2.18 ms at 0.70 and 1.72 ms at 0.50, as the median of the per-frame NR time (`DLSS-NR cost`). Against 1.0 that is 17 % less NR time at 0.85, 32 % at 0.70 and 46 % at 0.50. The picture gives up more than that: measured as the variance of the Laplacian over the benchmark's own screenshots, 0.85 and 0.70 keep about 45 % of the sharpness NR adds over NR off, and 0.50 about 18 %. The default stays 1.0; choose a lower scale by what the picture can take in the scene you play, not by the frame time alone.

**Config.** `[DlssNr] WorkingScaleX`, `WorkingScaleY` (0), `DepthAwareResolve` (false); all three are saved in the NR presets. **Menu.** `dlss_nr` card: Model resolution > Advanced: per-axis resolution, Model resolution > Depth-aware enlargement, and the NR time line.

**Code and seams.** `ext/nr/NrModelSize.h` (per-axis scales, the mixed-axis rule, the refusal latch), `ext/nr/DepthAwareWeights.h` (depth weights, shared threshold), `ext/nr/NrReadout.h`, `ext/nr/shaders/dlssnr.hlsl`, `ext/nr/pass/DlssNr_Dx12.cpp`. No new seam.

### NR Classic enlargement sharpening

**Origin.** Upstream OptiScaler's plain RCAS (`shaders/rcas/precompile/rcas.hlsl`), after the RCAS-for-ReShade port of AMD FidelityFX RCAS. The sharpen shader, its dispatch and the strength plumbing are fork code; the main shader and its blob are untouched, so every existing replay set still matches.

**What it does.** An optional 3x3 adaptive sharpen over the resolved frame, after the resolve. Off by default; applies only when Enlargement is Classic. **Status.** New; unit-tested, not tried in game.

### NR frame rate governor

**Origin.** Fork code, following the AutoMFG pattern (a pure decision core, applied without writing config).

**What it does.** While `[DlssNr] Governor` is on, the pass steps the model resolution down and up over 100/90/80/70/60/50% to hold a target frame rate. Steps down only below 95% of the target (so an auto target pinned at the display cap holds instead of ratcheting down), and probes one tier up after 10 s at or above 97% of the target (an auto target pinned at the display cap still probes back up): the probe is kept only if the rate holds at least 97% of the target over the 2 s after the new size renders, otherwise it reverts and the next probe waits twice as long (up to 96 s). A down step within 30 s of a kept probe counts as a failed probe: the next probe waits twice the dwell in force before the keep (up to 96 s). Between stepping down (below 95%) and probing up (at or above 97%) the tier holds. Never above 100%, never below 50%. Each step goes through the existing 500 ms settle and model rebuild. The governor never writes a config key: it applies its tier as a run-time cap where the pass reads its scales, so the guides and motion vectors always agree with the model size; `WorkingScale` stays the ceiling (a user at 150% steps to 100% first, a user at 85% to 80%). The displayed rate uses the detected frame-generation multiplier (the observed count plus one). The menu controls follow the capped tier: while the governor holds below the ceiling, the model resolution slider, the Enlargement combo and the Classic sharpening controls show the capped size. It stands down, running the user value and saying why in its status line, while AutoMFG is on, while a per-axis key is set, or while spatial compression is on; it holds its tier while the previous size's retired textures still wait for the GPU and freezes there if the fences never resolve. A pass pause over 1 s reseeds the average instead of stepping on stale timers. Freshness is a present counter, not a timestamp: while a frame-generation feature owns presents, a counter that stops advancing across ticks reads no-signal and holds the tier; with the governor on, a once-a-second debug line logs the interval, the multiplier and the counter advance. Selected-but-idle frame generation reads as off (the displayed rate is the present rate). A feature that reports itself active without an observed count is waited for 2 s at most: past that the present rate is the signal, read as if nothing were generated, and the status line says so. Target 0 (`GovernorTargetFps`) is auto: the lower of the frame limit and the display refresh (manual values below 30 fps are raised to 30 fps). After a step, a ceiling change or an applied size change the next second of samples is dropped and the average reseeds from the following half second, so the rebuild hitch never causes a step. After any NR model rebuild AutoMFG ignores the next two frame intervals. The default-off `[DlssNr] GovernorProbe` (ini only) logs once per model build that no below-created-size evaluate exists and changes nothing, whether or not the governor is on.

**Status.** New; untested, not tried in game.

**Config.** `[DlssNr] Governor` (false), `GovernorTargetFps` (0), `GovernorProbe` (false, ini only). `Governor` and `GovernorTargetFps` are saved in the NR presets; `GovernorProbe` is not.

**Menu.** `dlss_nr` card, under Model resolution: "Frame rate governor (experimental)", "Governor target FPS", and the status line.

**Code and seams.** `ext/nr/NrGovernor.h` (pure decision core), `ext/nr/pass/DlssNr_Dx12.cpp` (one-place cap, tick, probe line, rebuild seam call), `ext/gpu/GpuLifetime.h` (`RetireSeq`/`RetirementsComplete`), `ext/fg/DynamicMfgControl.h` (`NoteExternalStall`), `ext/fg/FgSeams.h`, `ext/fg/DynamicMfgSeams.cpp`, `ext/nr/menu/DlssNr_Menu.cpp`, `ext/nr/menu/NrMenu.cpp` (hotkey toast latch fix).

### RenoDX scene HDR

**Origin.** Ported from SirenBrink's fork. The shaders come from clshortfuse's RenoDX (the FFXIV mod is by Ersh and Pumbo) as adapted there; the five shaders, `reinhard`, `shared.h`, `NOTICE.md` and the licence are identical to SirenBrink's files.

**What it does.** `[HDR] Mode = 1` replays the game's tone-mapping stages in FP16 next to the SDR chain, so HDR output keeps the highlights the SDR path clips. The SDR chain, ReShade and the HUD are untouched. Two experimental switches feed the linear scene into NR (`NRSceneInput`) or DLSS (`DLSSSceneInput`). The scene stages are recognised by shader fingerprint, so a game patch that changes those shaders disables it; see [FFXIV-PATCH-RUNBOOK.md](FFXIV-PATCH-RUNBOOK.md).

**Continuous composition (experimental, `[HDR] LegacyComposition = false`).** In scene HDR the converter used to give each pixel one of two brightness rules: the world rule (the scene's own brightness) or the interface rule (the highlight curve, up to about 2.5 times brighter), chosen from the transparency mask of the known interface shaders or, failing that, from a colour-difference band. The two rules differ by 2x to 10x, so a pixel the choice gets half right can draw a bright or dark ring around the interface. The continuous composition blends the world's HDR value and the interface curve by how much of the pixel is world, so there is no jump to make a ring. `[HDR] UiExpansion` (unset follows `HighlightExpansion`) sets the interface curve alone and is read only by the continuous composition. `LegacyComposition` stays `true` by default and the legacy path is unchanged: the compiled shader was compared pixel for pixel over 48 configurations. **Cost with `LegacyComposition = true`:** the converter builds the same values through the same function, the root-constant block grows from 16 to 20 dwords with the last row zero, and one log line says which composition is in force; nothing of the continuous blend runs. Limits: the ring itself was never captured (no HDR screenshot or HDR-output log existed when this was written; the cause was derived from the shader), interface the mask misses still shows a brightness that depends on what is behind it, and nothing was tried on an HDR display. A census of interface draws (counters only) is written under `[HudLess] Diagnostics`.

**Status.** tested (RTX 4090) for `Mode = 1`; `ReShadeHighlights`, `NRSceneInput`, `DLSSSceneInput` are experimental and untested. The continuous composition (`LegacyComposition = false`) is untested on an HDR display.

**Config.** `[HDR] Mode`, `ReShadeHighlights`, `NRSceneInput`, `DLSSSceneInput`, `LegacyComposition` (ini only), `UiExpansion`. **Menu.** The `ffxiv_hdr` card.

**Code and seams.** `ext/hdr/scene/`, `ext/hdr/DlssHdr.cpp`, `ext/hdr/shaders/renodx/` (licence and notice shipped as `Licenses/RenoDX_*`). Seams: hdr, dx11bridge, fg.

### DLSS-G render preset (A, B, C), switchable while the game runs

**Origin.** Follows the approach of SirenBrink's v6.0 `PresetCache`, committed there first (2026-10-19; live switching 2026-10-20): the setting id, the three-hook live design, the byte anchors and the create signature are shared. The guards, the instruction decoder (`PresetX64.h`), the single-thread install, the switch state machine and the readout are written for this fork. The rule that UI recomposition is requested only with preset Auto or B is also in v6.0, committed there first.

**What it does.** Chooses the render preset of NVIDIA's frame generation runtime (`nvngx_dlssg.dll`): Auto, Preset A, B or C. The request is answered inside the process (setting id 0x10E41DF1), so no NVIDIA profile is written. The DLSS override id (0x10E41E03) is never answered: answering it "on" made NGX load NVIDIA's own copy of the runtime (log `Built with APP_NAME = nvapp_override`), with no multi-frame unlock and about a third fewer frames per second (as the author measured on one RTX 4090 setup). A change in the menu while the game runs switches frame generation off, releases the DLSS-G resources on a later frame, lets the runtime build its next endpoint under the new request and resumes. Only 310.8 and 310.9 runtimes are accepted; a failed check keeps the old request and the menu says "restart needed".

Preset A and C turn the runtime's UI recomposition off, B turns it on, Auto leaves it to the application (C also turns FG Lite on). The fork requests recomposition only with `[HudLess] Mode = recomposition` and preset Auto or B (`ext/fg/dlssg/UiRecompositionRule.h`); with A or C the log says once `Preset C turns NVIDIA's UI recomposition off on this runtime, so the HUD is interpolated; use Auto or B for recomposition, or ui_free with C`. The menu shows what the runtime reported and `Chosen: X, in use: Y` when they differ; that readout stays empty with `[Log] LogLevel` at warn or higher or with `LogAsync`. The selector is disabled for the RTX 20/30 runtime, a replacement runtime and any output other than DLSS-G.

### Dynamic MFG on RTX 40 (automatic multiplier)

**Origin.** The selector rules (500 ms average, thresholds 0.93 and 1.10, dwell of 1 s up and 2 s down, hold of 3 s, frames over 250 ms ignored, 2x to 4x) are the rules of SirenBrink's XeFG selector; `DynamicMfg.h` says "same rules". The controller, kill-switch, probe and regret steps, stall rule, self-test and keys are fork-original: SirenBrink's fork has no automatic multiplier on RTX 40.

**What it does.** Chooses 2x, 3x or 4x from the real frame time and changes the count while DLSS-G keeps running, instead of the off/on cycle of the Frame Gen slider. It takes the lowest multiplier that still presents the target frame rate, waits 3 s between changes, tries one step lower every 12 s or longer while the output sits at the target, and reverts a step up that gains less than 4 percent. It watches one second after every change: a long frame slows the mode, repeated ones stop it, and a change that is not applied or that upsets Streamline goes back to the last good count and stops the mode. While the real frame rate is below about 33 fps (a stall) no change starts, and a change that cannot be judged within 5 seconds ends as unknown (log `AutoMFG: judging the change at Nx skipped, the game was stalled`).

It never goes above 4x, is off by default, and is inert on RTX 50 (use Force Dynamic MFG there), with Frame Gen on Default, with Force Dynamic MFG and with the other outputs. A guard keeps NVIDIA's own dynamic mode from choosing 5x or 6x on an unlocked RTX 40; with Force Dynamic MFG on an unlocked RTX 40 and a frame limit that OptiScaler enforces itself, keep the slider on 4X. All rules and the review-round history: [notes/automfg-history.md](notes/automfg-history.md).

**Status.** opt-in, off by default; tested (RTX 4090), 2x to 4x, stall rule seen working; the self-test has not passed in game. The stall rule came from the first two runs in game, in which a loading screen or a DLSS preset change stalled the game at about 18 real frames per second while a change was being checked and the mode stopped for the whole session.

**Check.** Set `[DLSSG] AutoMFG=true`, `AutoMFGSelfTest=true` and the slider on 3X or 4X, start the game, stand in the game world for about 70 seconds (the test first waits for 20 seconds without a stall), then read `OptiScaler.log` for `AutoMFG self-test: PASS` or `FAIL` (needs the INFO log level and `AdaMfgUnlock`). Stall check: with `AutoMFG=true`, change a DLSS preset in the menu or load a zone; there should be no `automatic mode stopped` line, and a change made right before the stall ends with `settled` or with the `skipped` line.

**Config.** `[DLSSG] AutoMFG`, `AutoMFGMax` (2 to 4), `AutoMFGTarget` (0 = the lower of the frame rate limit and the display refresh), `AutoMFGSelfTest`. **Menu.** `fg_auto_mfg` (tab Frame Gen, after the `fg_unlocks` card; titled "Automatic multi frame generation"; its slider is "Target FPS (automatic multiplier)").

**Code and seams.** `ext/fg/DynamicMfg*.h` (`DynamicMfg.h` is the selector), `DynamicMfgSeams.cpp`, `MenuAutoMfg.cpp`. Seams: fg (no new seam).

### FG event recorder

**Origin.** The recording core (bounded queue, writer thread, rotation, analyzer exit codes) is ported from SirenBrink's FFXIVRender recorder (`fg_diagnostics`, GPL-3.0-or-later), with smaller records, a session cap, no paths in any record and a shutdown that only signals. **Status.** Off by default. Ran in a played session on 2026-10-30 (RTX 4090, SDR, DLSS-G 2x, 21 minutes): 314,429 records, no gap, no dropped record, no parse error and a `session.end`. ### Live frame-generation output switch (experimental, off by default)

**Origin.** Fork code. The teardown order was measured for each library build; the measurements are in [notes/live-output-switch.md](notes/live-output-switch.md).

**What it does.** Moves frame generation between FSR FG, XeFG and plain presentation while the game runs, without a restart. `[FrameGen] FGOutputHotSwap` (menu card on the Frame Gen tab, off by default) arms it; with it on, the present switches when the configured output differs from the running one. All six directions are handled: FSR FG to XeFG and back, either one to plain and back. **Scope:** the run has to boot with FSR FG or XeFG as its upscaler-input path (`[FrameGen] FGInput = upscaler`). A run with frame generation off has nothing to switch, and a DLSS-G output is not switched live; only the three DX11-to-DX12 bridge outputs take part.

**How it stays safe.** The old chain is drained and torn down in the order measured for each library build, every new chain is created on the bridge's own queue, the hooks are re-bound under a gate so no call reaches a freed object, and the new chain is judged by its first 20 presents. A chain that fails is replaced by plain presentation (the game keeps presenting) and the target is remembered until a retry. Hard refusals (an unknown library build, a busy hook transaction) leave the running output in place and say why in the menu and the log.

**Status.** Verified on the official benchmark (windowed) in runs that booted with FSR FG and in runs that booted with XeFG, plus forced failures at create, adopt and probation that all fell back to plain. Not yet tried in a game session. The benchmark keys `FGOutputSwitchScript` and `FGOutputSwitchFault` script switches and force a failing step; the details and the per-library measurements are in `docs/notes/live-output-switch.md`.

**Cost with the key off.** Every bridge present calls `outswitch::OnPresent` first: it reads the steady clock (`steady_clock::now()`, a per-present clock read v0.4.0 did not have) and the cached key, then returns before touching the bridge. Tens of nanoseconds a present by reading; no A/B was measured.

### Automatic ReShade scene depth

**Origin.** Fork-original.

**What it does.** ReShade effects that read depth (MXAO and the like) find the game's depth buffer on their own. When the game renders below the output size (DLSS Quality and lower), its scene buffers are still output-sized and only a window of them holds this frame, so the depth ReShade finds (Generic Depth) does not line up with the picture and effects that read it misfit. That is inferred from the buffer sizes in earlier logs until the capture line in `OptiScaler.log` shows the real depth size. With this option on, each DLSS evaluate copies the Depth texture the upscaler was given (cropped by the subrect origin, nearest-mapped from the render size) into an owned R32_FLOAT texture the size of ReShade's back buffer. While ReShade renders its effects (`begin_effects` to `finish_effects`) the `DEPTH` input is pointed at that copy through `update_texture_bindings`, and finish puts ReShade's own binding back. The copy is made on the game's native immediate context, in a private context state, so the game's pipeline state is untouched. Under frame generation ReShade renders an effect pass for every output frame while the upscaler evaluates once per real frame: every pass between two evaluates binds the copy of the last evaluate (a generated frame gets the real frame's depth, which is intended), and an evaluate that stops (a menu, a loading screen) is caught by the age of the capture (250 ms), not by a frame count. The depth-owned frame counter that stamps a capture ticks once per capture; the first game test (2026-10-25) showed the earlier rule, one tick per finish, refusing about 60 % of the passes as stale under frame generation.

**G-buffers (same switch).** An add-on such as REST (ReshadeEffectShaderToggler) hands the game's G-buffers to ReShade's semantics `NORMALS`, `DECALS`, `DECALS_WATER`, `MOTIONVECTORS` and `MATERIAL` (`update_texture_bindings`, rebound in its own `begin_effects`), and effects such as the Alive NEXT preset's `ffxiv_common.fxh` read them with plain UV 0..1 (`texture texNormals : NORMALS;` and so on, declared in a namespace, so the API names are the short `texNormals`, `texDecalNormals`, `texDecalWaterNormals`, `texNativeMotionVectors`, `texMaterial`). Those buffers are output-sized with the picture only in the render window, exactly like the depth, so with the depth aligned and the normals not, MXAO drew ghost objects into walls (seen in game). With the one option on, after the add-on's begin the binder reads its binding of each buffer, and if the source is output-sized (the size of ReShade's back buffer) while the fresh depth capture says render < output, it makes an output-sized copy of the render window (the same exact-integer nearest mapping as the depth, origin 0,0) in the SAME format as the add-on's view, binds it to the same semantic until `finish_effects`, and puts the add-on's binding back (only if the entry is still ours; `overwrittenByOther` counts the rest). A depth subrect base other than 0,0 (the remap assumes the window starts at the corner; the depth honours the base), a source that is already render-sized, render equal to output (DLAA: the add-on's bindings are not even read; one log line per change), an unreadable or non-2D view, a format the pass does not do (typeless, sRGB views, integer, depth) or any failure keeps the add-on's binding (one log line per change says why). Variables of the same name that show different bindings, the EMPTY ones included (an effect's own texture next to readers that show nothing yet), are ambiguous and are left alone. The counter `kept` is counted but never logged as a rate line. The copy is made at `begin_effects` on the thread that runs `begin_effects` (two possible paths: the HudLess UI-boundary `render_effects` call and ReShade's own pass in Present; the log prints, once per thread that runs begin_effects, the thread next to the evaluate thread and the native context pointer begin_effects drew on), on the context ReShade gives (`command_list::get_native()`), serialized with the depth pass by one process-wide context-state mutex (taken with a 30 ms timeout, fail open: a holder that does not come back costs the pass 30 ms, never a freeze. A timeout happens BEFORE any state swap: the depth capture is skipped and ages out, the G-buffer remap fails and keeps the add-on's binding, a pending swap-back recovery is retried on the next call; each logs once a minute 'context state lock busy for N ms: pass skipped'. It serializes only OUR depth and G-buffer passes; the character-preview passes swap private states without it), in a private context state; one pass object per buffer, cached by (the add-on's view, the depth capture counter), so under frame generation the copy is made once per real frame and the generated passes rebind it. The slots reuse the depth binder (`DepthBinder`: a slot per semantic with its own pass state, counters and trust latch; the variable that reads exactly the copy back vouches for the pass and its pre-bind reading is the original), run only after the depth reached Bound (so a manual depth transform, an untrusted depth input or no capture means no G-buffer work), and cost no backend call when the effects declare none of the five variables. **Motion vector VALUES** are scaled per axis as well: multiplier = the motion vector scale the game reports to the upscaler (`MV_Scale_X/Y`, e.g. 3840 x 2160) divided by the render size (x2 at Performance, x1.5 at Quality), falling back to output/render when the game reports none. The scaling is always on (there is no switch). It is derived from DLSS's convention, under which the stored vector times the scale is a displacement in render pixels, so the screen-UV motion of the stretched window is the stored value times scale/render; it was tried in game and no problem was seen. Unverified undo: if no variable of that name reads the copy back (they are not the semantic's readers), the entry is erased and the slot stops until the effects reload (`erasedUnverified`, `noDepthInput`); readers that go by another name would lose the add-on's binding until it rebinds. A target format the GPU cannot make a render target for (a permanent creation failure such as E_INVALIDARG) is remembered per (view format, output size) and not retried every frame; out-of-memory and device errors are retried. Memory: up to five output-sized copies (33 MB for RGBA8, 66 MB for RGBA16F at 3840x2160), released when the option goes off.

It leaves ReShade alone, and ReShade keeps the depth it detected, whenever anything is not clearly right: another device, no `DEPTH` reader that reads the copy back, no or a stale capture, a size mismatch, the character preview (its output is not the back-buffer size), or any of `RESHADE_DEPTH_INPUT_X_SCALE`, `_Y_SCALE`, `_X_OFFSET`, `_Y_OFFSET`, `_X_PIXEL_OFFSET`, `_Y_PIXEL_OFFSET` set in ReShade's preprocessor definitions to a non-neutral value (a manual depth transform; defined with the neutral value, 1 for the scales and 0 for the offsets, it does not stand down). The game's depth is reverse-Z: if ambient occlusion looks inverted with the option on, set `RESHADE_DEPTH_INPUT_IS_REVERSED=1`. It is for FFXIV only: another executable with the key on does nothing and the status says so. It needs ReShade 6.8 or newer (add-on API 20) loaded in the game; a ReShade installed as `dxgi.dll` that loads after OptiScaler is looked for once a second for the first minute while the option is on. ReShade reports a texture variable under its short declared name (no namespace and no mangling: measured against ReShade 6.8.0.2155), so the depth input is the variable named `DepthBufferTex` or `DepthInputTex`; the matching stays exact. A texture of another effect that happens to read like it (`Foo::DepthBufferTex` comes back as `DepthBufferTex`) is caught by the readback after the bind: a candidate that shows something that is not a depth view makes the runtime untrusted, and one that does not read the copy back is not the reader.

**Status.** Opt-in, off by default. New. The decision logic, the copy pass (real shader, WARP device), the raw ReShade layer (against a fake ReShade DLL), the event wiring, the whole evaluate path (fake parameter block and fake host) and the whole loop (the real engine, the real binder and the real event dispatcher over a fake ReShade world: a full cycle ends bound, the frame stamps agree) have offline tests; the source pins keep the one upstream line and the shutdown calls in place. ### Native nameplates

**What it does.** The game draws its nameplates once per game frame. With `[HudLess] PlateInterp = endpoint` the fork takes the game's own nameplate draws out of the frame into a plate-only image on the same GPU and draws that image back over every output frame, unchanged. The picture is the same as with the key off; what changes is how the plates reach the screen. `on` is accepted for a later stage that moves the plates between outputs: this build has no plate tracker, so `on` draws exactly what `endpoint` draws and moves nothing. `PlatePhaseOffset` and `PlateMaxStep` belong to that later stage and have no effect here.

**How it stays safe.** A draw is taken only when it matches every condition of a nameplate draw (the game's own immediate context, one 8-bit SDR colour target, no unordered access view, a `GREATER_EQUAL` depth test that writes nothing and uses no stencil, the standard alpha blend, one of four nameplate pixel shaders and a nameplate input layout). The engine reserves one of three plate slots before the game's plates are hidden: no slot, no hide. Every present publishes exactly one record, and any doubt (a draw state that is not a nameplate draw, a size or format the image cannot hold, a frame the pass cannot draw, the draws and the present on different threads) leaves the game's own plates in place. It needs DLSS-G with a multiplier of 2 or more and an SDR output. Three slots at 4K are about 100 MB. With the key off nothing is reserved, redirected or written; the cost is one relaxed load a present (`hudless::OnPresentBegin`) and the plate fast path's relaxed load a draw inside the existing FFXIV draw hook.

**Status.** New, off by default. Unit-tested on a software adapter (the draw rule and its fail-closed property, the shared slot, the slot rules and locks, the engine protocol, the game side on a real D3D11 context, both sides end to end). Never tried in a game. Only a session can answer: whether the game's plate draws really have that state (the `PlateDiagnostics` census says so), whether the driver accepts the render-target shared texture, that one render thread runs the draws and the present, the two freshness windows at three or four outputs per frame, how far the pacer lags, and whether the UI boundary of the UI-free mode needs the hidden plate draws. The promise and its bounded exceptions (a plate can be drawn twice or missing for the outputs of one game frame around a hide or unhide) are in [notes/native-nameplates.md](notes/native-nameplates.md).

**Config.** `[HudLess] PlateInterp` (`off` | `endpoint` | `on`, default `off`), `PlatePhaseOffset` (`auto` | `0` | `1`), `PlateMaxStep` (0 to 256, default 24); live from the HUD-less card under "Native nameplates". **Code and seams.** `ext/ffxiv/plates/`, `ext/hudless/UiPlates.*` and the plate headers; seams on the HUD-less engine and two lines in `ext/ffxiv/lighting/FfxivLightingCapture.h`. No upstream line.

## Window mode

**Origin.** Fork-original. The `[XeFG] ForceBorderless` key it depends on is upstream's (cdozdil).

**What it does.** FFXIV runs borderless when `[XeFG] ForceBorderless = true` (a setting the fork does not turn on by itself). In that mode upstream's hook swallows the game's request to change the window mode and restyles the window itself. Two problems, both seen in logs: after leaving the pseudo fullscreen the window keeps a thin edge (client area 3836x2156 inside a 3840x2160 window), and one window-mode switch made while DLSS-G was running stalled Streamline's frame pacer ("Potential dead-lock in Present ...") and ended with the GPU device removed. Zero-code advice: choose "Borderless Window" in the game's display settings, restart the game after changing the mode, and do not switch to "Fullscreen" while the game runs.

- Probe (`probe` or `on`): one `Window:` line after every successful resize of the bridge swapchain and for every `SetFullscreenState` call that ReShade sees, with styles, rectangles, the frame generation state, thread ids and the verdict. It only reads and logs.
- Border fix (`on`): after `SCExclusiveFullscreen` goes from true to false and frame generation is confirmed off (at least 2 complete off presents and 50 ms), a window with neither caption nor sizing frame but with `WS_EX_CLIENTEDGE` or `WS_EX_WINDOWEDGE` gets those bits cleared. A window with a caption or a sizing frame is never touched.
- Deferred mode switch (`on`): when `ForceBorderless` is on, the output is DLSS-G, frame generation is active and the call would really change `SCExclusiveFullscreen`, a ReShade add-on event holds the game's `SetFullscreenState` back, asks frame generation off, and replays the call once DLSS-G is confirmed off (at least 2 complete presents and 50 ms). Soft wait limit 6 presents or 2 s; the hard limit (24 presents and at least 500 ms, or 6 s) replays regardless, with a warning. Anything unexpected passes the call through as today.

**Status.** Opt-in, off by default; tested (RTX 4090) on 2026-10-19: border fix and two held-back mode switches with DLSS-G on; the open points listed here were not exercised. The rules and decision flows have unit tests on fakes, and the window calls are tested on a real hidden window; the game itself decides whether it tolerates a held-back window-mode call. Not verified in game: what ReShade hands back to the game for a prevented call (not documented in the vendored headers); from roughly 190 to 200 game presents per second the 50 ms floor outlasts the pause in which frame generation stays off, so the hold ends at the hard limit and the border fix expires (`border fix expired`); whether the replay avoids the Streamline stall (look for the absence of `Potential dead-lock in Present` after a `replaying SetFullscreenState` line); a size-changing `ResizeBuffers` cannot be held (warning `the follow-up ResizeBuffers is not protected`), so do the risky switch only after a border-clean leave.

**Config.** `[Window] Mode`: `off` (default: nothing runs and nothing is logged), `probe` (log only), `on` (probe, border fix and deferred mode switch). It applies after a game restart; any other value counts as `off`. **Menu.** Drop-down in the card "Window mode (FFXIV)" (`window_mode`, FFXIV tab, first card): the choice is stored for the next start and the card shows the mode active in this session.

**Log lines.** All start with `Window:`: `module active, mode=...`, `border fix applied exstyle A -> B client WxH -> WxH`, `SetFullscreenState(TRUE|FALSE) held back: ...`, `replaying SetFullscreenState(...)` with the reason (`frame generation confirmed off`, `wait limit reached`, `hard wait limit reached without a confirmation`), `held SetFullscreenState dropped, not replayed: ...` (the mode did NOT change). Probe fields, the other log lines, the present-counter logic and all open points: [notes/window-mode-design.md](notes/window-mode-design.md).

**Code and seams.** `ext/window/` (`WindowRules.h` pure rules, `WindowController.h` decisions behind an `Env` interface so tests use fakes, `WindowModule.cpp` live entry points). No seams in upstream files: the module is called from the existing fork seam bodies `dx11bridge::OnResizeDone` and `dx11bridge::PresentScope` and from a ReShade add-on event (`ext/reshade/ReShadeEvents.cpp`).

### Quality change without the stall

**Origin.** Follows the approach of SirenBrink's sleep skip, committed there first (2026-10-19). The code is written for this fork.

**What it does.** Changing the DLSS quality in FFXIV releases the DX11 upscaler and builds a new one; upstream sleeps a fixed 500 ms between the two. Only if all of that is proven (log result `drained`) does it skip the sleep. Anything unproven gives `not-applicable` and the 500 ms pause stays; a failed drain (`failed`) refuses the release as before. With XeFG output and `[XeFG] ResetOnUpscalerChange` on (the default) the pause stays by design. The DX11 upscaler table has a narrow lock now, because the game changes quality on its update thread while the render thread evaluates (inferred from the code, not yet seen).

**Status.** on by default; new, unit-tested (drain classification, lock and registry, release sequence with fakes, thread trace, source pins); ran in game (RTX 4090) since 2026-10-20: the sleep was skipped and 0.06 to 30 ms were waited instead of 500 ms. Known limits and the full text: [notes/ngx-release-skip-sleep.md](notes/ngx-release-skip-sleep.md).

**Config.** `[NgxRelease] SkipReleaseSleep` (ini only, default on; off = the old flow exactly: no closing, no waiting, the 500 ms pause; the table lock stays). **Menu.** None.

**Code and seams.** `ext/dx11bridge/` (`NgxLifecycle.cpp`, `NgxFeatureTable.h`, `ReleaseSequence.h`), `ext/gpu/DrainResult.h`, `ext/upscaler/NgxThreadTrace*.h`. ## Game jitter (FFXIV)

The game renders its scene with a jitter translation it scales itself and tells the upscaler the unscaled pixel jitter. The two agree only when the game's scale `s` is 2. Three features deal with that: a read-only probe, a correction of what DLSS is told, and a fix of what is drawn. They share the card "Game jitter (FFXIV)" (`ffxiv_jitter`, FFXIV tab, after the FFXIV HDR10 card), the code in `ext/ffxiv/jitter/` and the existing upscale-boundary seam (`ext/Seams.cpp` calls `ext::ffxiv::jitter::OnUpscaleBoundary`); none adds an upstream seam. Measurements, the mechanism text and the log budget: [notes/jitter-measurements.md](notes/jitter-measurements.md).

### Game jitter probe

**Origin.** Fork-original; SirenBrink's fork has no probe. SirenBrink's `Config.md` documents the 0.6 native raster strength first (commit `5bfa6e92`, 2026-10-19); this fork's first in-game sample of 0.600 came about 1 h 22 min later, and its formula and the design of the probe date from 2026-10-18.

**What it does.** `[FFXIV] JitterProbe` reads the game's camera jitter object (read only, guarded, matched game build only) and writes one log line about every 10 seconds, and early when the render size or preset changes: `Game jitter: counter N, reported jx/jy ..., render WxH (source), applied ax/ay ..., ratio rx/ry ..., signs ok, implied s = 2.000/2.000 (consistent), ...`. `s = 2` on both axes means the game applies what it reports; another value means the upscaler is told a different jitter than the one in the picture; `signs MISMATCH` means an axis has the opposite sign. A failed check logs one line per episode (`Game jitter: not read, guard failed: ...`) and does nothing else.

**Status.** Diagnostic, off by default. Measured in game (the released build, DLSS preset M): the picture moves by only 60% of the jitter the game tells DLSS about, `ratio rx/ry 0.600/0.600` in every sample, at DLAA and at Performance alike. Transformer presets (L, M) depend on accurate jitter more than the CNN preset K, which fits the reports that L and M look jittery. Quality (1.5x) and Balanced are not measured.

**Config.** `[FFXIV] JitterProbe` (false). **Menu.** Checkbox in the card "Game jitter (FFXIV)"; it applies at once and is stored in the ini when the settings are saved. **Code and seams.** `ext/ffxiv/jitter/` (`FfxivJitterProbe.cpp|.h`, `FfxivJitterCore.h`, `FfxivJitter.h`, `FfxivJitterMenu.cpp`).

### Jitter correction

**Origin.** Fork-original mechanism: it learns the applied/reported ratio and scales what DLSS is told. SirenBrink's fork solves the same goal with the source fix described below.

**What it does.** `[FFXIV] JitterCorrection` learns the ratio applied/reported from snapshots of the game's jitter object and multiplies the `Jitter.Offset.X/Y` pair of every DLSS evaluate by it. Five accepted snapshots in a row that agree within 2% adopt their mean (`Jitter correction: calibrated ratio 0.600/0.600 from 5 snapshots for render 1920x1080, output 3840x2160, quality 0; scaling the reported jitter`); until then the game's values pass through. A ratio within 2% of 1 applies nothing; above 1.02 or below 0.25 it is refused. A different configuration (render size, output size, quality) drops the calibration. The scaled pair is written once and nothing puts it back, so super resolution, frame generation, the DLSS-NR path, the `Jitter Count` value in the menu and the FSR and XeSS backends all see it. Only the input named `Upscaler` reads the scaled pair from the parameter block. Test with frame generation (and NR) off first, then on.

`[FFXIV] JitterScaleOverride` (0 = off; `auto` means 0) is an experiment key and may be removed once the correction is validated. A value from 0.25 to 1.0, used while `JitterCorrection` is true, takes precedence over the calibration. Values to try with the same scene: `1.0` (the baseline), `0.8`, `0.6` (what the probe measured) and `0.5`.

**Status.** Experimental, off by default. The correction ran in game and scaled the told jitter (2026-10-20 and 2026-10-23); its earlier version showed no visible gain at the Quality mode (2026-10-19); the look of the current version is not recorded. Test with frame generation off first. An earlier version replaced the pair only after proving for every evaluate that the object belonged to it; in the author's session that proof held for 11% of 9418 evaluates and the correction flapped, which is why this design replaced it. Quality (1.5x) and Balanced are not measured. Other limits: the notes file.

**Config.** `[FFXIV] JitterCorrection` (false), `JitterScaleOverride` (0). **Menu.** Checkbox for `JitterCorrection` and the slider "Manual jitter scale (0 = learn it)" in the card "Game jitter (FFXIV)" (steps of 0.05, below 0.25 snaps to 0, greyed out while the correction switch is off).

**Check.** A status line comes about every 10 seconds for the first 60 lines, then once a minute: `Jitter correction: on; totals since the start of the session: N evaluates seen, N scaled, ...; state: calibrated ratio 0.600 for render 1920x1080, ...`. In a good session a `calibrated ratio` line comes within a second or two, `scaled` stays close to the number of evaluates, and `disagreed` and `ratio changes` stay near zero. **Code and seams.** `ext/ffxiv/jitter/` (`FfxivJitterCalibration.h`, `FfxivJitterCore.h`).

### Jitter source

**Origin.** Follows the approach of SirenBrink's v6.0 `JitterSource`, committed there first (2026-10-19). Hook scope, return-address filters, the DLSS gate, the strength range, the normalise and projection checks and the ring criteria are the same, and constants and names (`Generator`, `Getter`, `NormalizeHalton`, a ring of 32 with 1e-7 and 1000 ms) are shared. The logic was ported by re-typing it. The phase-count rule is v6.0's `TemporalSampling::PhaseCount`, and the guard table shares block starts and one fingerprint. The controller, world-camera tie, verification, watchdogs, fallback, stand-down, opt-in key and menu are fork code. How NGX is told differs: v6.0's getter returns a thread-local packet and a scope restores it; this fork writes once and never restores.

**What it does.** In DLSS mode the game draws the scene with only a fraction of the sub-pixel jitter its generator produces (native strength, measured 0.6, so +-0.3 px instead of +-0.5 px) and calls the generator with an unbounded phase count. `JitterCorrection` cannot recover samples that were never drawn. With `JitterSource=true` a hook on the generator divides its output by the native strength, so the game's multiplication leaves the full +-0.5 px lattice, and replaces the phase count by NVIDIA's `ceil(8 * output pixel area / render pixel area)` (8 at DLAA, 18 Quality, 24 Balanced, 32 Performance, 72 Ultra Performance). It only touches the WORLD camera's jitter object. At the DX11 evaluate boundary `Jitter.Offset.X/Y` are replaced by the offset that was drawn, so super resolution, frame generation and the Jitter Count readout get the drawn value; `JitterCorrection` stands down for every evaluate the fix tells.

Fail-open means today's behaviour: a mismatch of the executable, a failed hook install, the key off, or a generator that is not being normalised switches the hook and the told-offset write off together. Every frame is verified (tolerance 0.005 px); 90 consecutive frames outside, or 90 consecutive evaluates that match no camera sample, make the fix fall back for the session (switching the key off and on again tries once more). The character preview keeps its own 32-phase path.

**Status.** Experimental, opt-in, default off; tested in game for the lattice only. The arithmetic and the executable anchors were checked against the October 20 executable (SHA-256 46A52AB1...). In game, the log showed the full +-0.49 px lattice with 32 distinct phases at Performance and 0 frames outside tolerance. The author reported motion "less jumpy" with it on, but `[HudLess] Mode = ui_free` was active at the time, so that impression is confounded by `ui_free`. The key did not remove the faint micro-stutter seen with frame generation in that session: that came from the `ui_free` fallback (see [HUD-less frame generation](#hud-less-frame-generation)) and was gone with `recomposition` whether the key was on or off (with the DLSS-G preset on Auto or B). It supports one game executable build.

**Config.** `[FFXIV] JitterSource` (false; ini default `auto`). **Menu.** Checkbox in the card "Game jitter (FFXIV)".

**Check.** Log lines: `Jitter source: hooks installed (...)`, `Jitter source: active (strength 0.600, phases 32 for render 1920x1080 output 3840x2160)`, `Jitter source: verified N frames, drawn offset equals the generator's value (max deviation ... px, outside 0.005 px: 0), ...`, `Jitter source: inactive (<reason>)`, `Jitter source: fell back to the old behaviour, ...`. **Code and seams.** `ext/ffxiv/jitter/FfxivJitterSource*`.

## Character preview (CharaView)

**Origin.** SirenBrink's v6.0 contains the same feature (commit `fe208a59`, 2026-10-16): the isolated DLSS Super Resolution pass with 2x output, the replayed G-buffer draws, the depth and camera guides and the spatial AA with 2x upscaling. This fork's version matches it closely. The config, the target table and the guards are written here. The FXAA and guide shaders (same constants, order and names), seven geometry shader CRCs, the 18-byte code pattern with 20 entries and the 100 ms cache match v6.0. The 32-phase preview jitter was in this fork's code first (2026-10-18); v6.0 used 16 phases at `fe208a59` and moved to 32 in `5bfa6e92` (2026-10-19). Credit: [ATTRIBUTION.md](ATTRIBUTION.md); details of the behaviour: [RECONSTRUCTION-REFERENCE.md](RECONSTRUCTION-REFERENCE.md).

**What it does.** The game draws the 3D character preview (character, equipment and glamour windows) in a small separate render. CharaView gives that render its own isolated DLSS Super Resolution pass with 2x output (jittered rasterisation, replayed G-buffer draws for signed motion vectors, depth and camera guides, native alpha composed back), and offers an optional FXAA-style spatial anti-aliasing pass with 2x upscaling for the equipment preview. The jitter cycle is 32 phases (the log line "CharaView: DLSS path in that burst" ends with "jitter cycle 32 phases"). It fails open: any doubt leaves the native image. It reads the game's `.text` once, read-only, for an 18-byte code pattern that must match exactly once at the documented addresses; otherwise the feature switches itself off for the session with one log line.

**Status.** Opt-in, off by default; tested (RTX 4090) on the 2026-10-18/19 builds with one preview window: spatial AA, DLSS 2x, NR, NR before DLSS; not re-checked on this release; preview windows with more than one image open were exercised incidentally in the game logs of 2026-10-23 and 2026-10-28 (counters only): two windows ran clean, four and eight images mostly kept the native picture; the picture itself and the D3D12 debug layer were not checked. Not implemented: frame generation for previews (not needed: the preview is part of the UI, which the game's frame generation does not interpolate separately), portrait windows (it is not known which windows reach this renderer), and deferred contexts (those draws stay native).

**Config.** `[FFXIV] PreviewDLSS` (false); `PreviewAA` (false; with `PreviewDLSS` on, the DLSS pass takes the equipment preview and the AA is bypassed, but while that pass cannot run the AA is used instead); `PreviewUpscale` (true, only meaningful with the AA); the NR keys under [Preview Neural Rendering](#preview-neural-rendering). Debug: `PreviewGuideCapture` (false; capped dumps to `OptiScaler\PreviewDLSSDiagnostics\`), `PreviewDebugTint` (false), `PreviewDebugFlood` (false), `PreviewProbe` (false; logs copies of the preview, saves PNGs to `OptiScaler\PreviewDebug\`, reads live commands from `OptiScaler\chara-probe.cmd`). The probe commands, output files and caps: [notes/charaview-preview-nr.md](notes/charaview-preview-nr.md).

**Menu.** Card "Character preview" (`ffxiv_character_preview`, FFXIV tab): Preview DLSS, Preview spatial AA with its 2x upscaling option and Preview NR with "Run NR before DLSS" on top, the one-line states and the reason when the feature is off. Every counter and debug aid sits in a closed "Advanced (debug)" fold.

**Code and seams.** `ext/ffxiv/chara/` (with `shaders/`), hooks inside `ext/ffxiv/lighting/FfxivLightingCapture.h`, the per-frame callback through `dx11bridge::AfterSharedCopy` in `ext/Seams.cpp`, ini fragments `ext/ini/FFXIV.ini` and `ext/ini/HDR.ini`. No seams in upstream files.

### Preview Neural Rendering

**Origin.** Different mechanism from v6.0, which runs NR at the render size, adds the delta after DLSS and has a `PreviewNRReuse` option. This fork runs NR on the 2x output, alone on the native image, or (experimental) before DLSS. The code is the fork's.

**What it does.** `[FFXIV] PreviewNR` runs the DLSS NR model on each open character preview window. The model only runs on Direct3D 12, so the preview image is handed to the DirectX 11 on 12 bridge's device through shared textures and fences and drawn from a shared result texture. Every failure keeps the native image and switches preview NR off for the session. It needs an NVIDIA card, the bridge, `nvngx_dlssnr.dll` and `nvngx.dll_dlssnr.dll`; `[DlssNr] Enabled` is not needed. Alone (with `PreviewDLSS` off) it runs on the native preview image; with `PreviewDLSS` on it runs on the Super Resolution result (the 2x output) between the Super Resolution evaluate and the alpha pass. The cost per window is one NR pass at 2.2 megapixels.

`PreviewNRBeforeSR` (false, experimental) runs the preview NR on the render-size picture before the DLSS evaluate, with `PreviewDLSS` and `PreviewNR` both on. The model works at a quarter of the pixels, so each window is expected to use less GPU time and video memory; with one window it cost about 2.8 to 3.6 ms of GPU time per frame and about 213 MB (2026-10-19), against about 4.1 ms and 739 MB for NR after DLSS on an earlier build (2026-10-18; different builds, so the comparison is rough). NR sees a jittered picture that has not been anti-aliased, so shimmer or trails on hair and cloth are possible. If the DLSS evaluate refuses the NR image, that render is evaluated again on the plain picture and NR before DLSS is switched off for the session with one log line.

**Status.** Opt-in, off by default; tested (RTX 4090) on the 2026-10-18/19 builds with one preview window: spatial AA, DLSS 2x, NR, NR before DLSS; not re-checked on this release; preview windows with more than one image open were exercised incidentally in the game logs of 2026-10-23 and 2026-10-28 (counters only): two windows ran clean, four and eight images mostly kept the native picture; the picture itself and the D3D12 debug layer were not checked. Cost of one open window with NR before DLSS (2026-10-19): the model took about 72.8 ms to create, the GPU time was about 2.8 to 3.6 ms per frame and the video memory grew by about 213 MB; an earlier build with NR after DLSS (2026-10-18) showed about 4.1 ms and +739 MB. Not checked in game: the D3D12 state tracking of the production inputs under the debug layer, whether the model accepts guides smaller than the colour, the image quality on the alpha-masked silhouette and on moving characters, and the cost with three or more windows open (two windows were measured: about 2.6 to 2.7 ms of GPU time per NR run and per window, the same per run as with one window, so a frame in which both windows render costs about twice that). Full text: [notes/charaview-preview-nr.md](notes/charaview-preview-nr.md).

**Lobby and character creation.** The lobby character does not appear to be drawn by the preview renderer: one session's log puts the lobby on the main frame, where the game calls its own DLSS and the main-frame NR runs on it (not re-observed since; the time window is placed by a render-size change, not by a login line). If that holds, this feature has nothing to add for the lobby and no lobby-specific code is planned. The one observation of the cost there was about 18 to 20 ms of NR at 4K DLAA against about 7 ms in the world; that is the main NR pass's own cost and is left to that pass's cost work, which does not need to know the scene. Character creation was not observed and is not covered by this feature either.

**Config.** `[FFXIV] PreviewNR` (false), `PreviewNRBeforeSR` (false), `PreviewNRLingerSeconds` (5; keeps a window's model after the window closed), `PreviewNRLate` (false; shows the previous frame's result and avoids the GPU wait on the DirectX 11 side at the cost of one frame of lag; bring-up only); `[HDR] PreviewNRTrace` (false; trace log lines only).

**Preview budget (experimental, unit-tested against a model of the game's feed, not tried in game).** All off or inert by default: `[FFXIV] PreviewBudget` (false) with `PreviewMaxWindows` (2, 1 to 8) limits how many preview windows get the upscaler and preview NR; a window is recognised by the camera constant buffer it draws with (the buffer, its first constant and the render size), without reading anything back from the GPU, so a render whose window cannot be recognised yet runs untouched, and the other windows keep the game's own picture and are not jittered. A window that changes to a buffer the previous window drew with is recognised from its second render on; with two windows open, one of them drawing every frame and the other only now and then, the picture can stay native far longer than a first try suggests: a buffer the occasional window showed on is left unnamed for 30 seconds after a render was attributed to the wrong window, so the window that draws every frame keeps the game's own picture for most of the time (about 90% of a minute in the offline model). That is the price of never shifting a window for an image it is not. Whether the game's windows share a buffer at all is what the `preview identity` log line answers; it is written only while `PreviewBudget` is on, so check it before reading anything into the set's behaviour and do not look for it with the budget off. A buffer that is forgotten to make room for another one also forgets its pause, so it can be mis-attributed once more before it pauses again. `[FFXIV] PreviewReplayWideShape` (false) lets the signed-motion replay take a camera block that is a view into a larger buffer; the draw must still write the preview renderer's own G-buffer. **Cost with the budget off:** nothing of the identity is asked for, because the preview path checks the key once per render; with it on, the wide-shape key is one more cached read.

**Menu.** In the "Character preview" card; the cost per open window is shown there and in the log (`CharaView NR:` lines). **Code and seams.** `ext/ffxiv/chara/CharaNr.cpp`, `CharaNr.h`, `CharaNrRules.h`. No seams in upstream files.

## Frame pacing trace

**Origin.** Follows the approach of SirenBrink's frame pacing trace and hidden-present `DO_NOT_WAIT` switch, both committed there first (2026-10-16). The code is written for this fork; the trace accumulator and the log line format match.

**What it does.** With `[FramePacing] Trace=true` (or file logging at Debug or Trace with the key left on `auto`), FFXIV logs every 10 seconds and per thread one line per timed place of the present path (native present, hidden DX11 present, FG dispatch, Reflex sleep, output present, scene NR recording, preview NR): `Frame pacing CPU [<name>] tid <n>: calls N, mean x ms, max x ms, >=8ms a, >=16ms b, >=33ms c`. With DLSS-G active the phases nest, so compare each on its own. The lines are CPU time only; queued GPU work is not counted. One line at the start says whether the trace runs: `Frame pacing trace: on (key true)`, `on (Debug log)`, `off (key unset, log level 2)`, `off (key false)` or `off (not FFXIV)`. `[FramePacing] HiddenPresentDoNotWait=true` adds `DXGI_PRESENT_DO_NOT_WAIT` to the bridge's present of the hidden swapchain; a busy chain skips that present instead of blocking (counted as `skipped k` on the hidden-present line). If DXGI answers a flagged present with an invalid-argument or invalid-call result, the flag is switched off for the rest of the session (one WARN line, `hidden DX11 present: DXGI rejected DO_NOT_WAIT`).

**Status.** new. The core, the policy, the seam body (against a fake swapchain) and the DXGI flag handling (against a real WARP swapchain) are unit-tested; nothing of it has run in game.

**Config.** `[FramePacing] Trace` (default off), `HiddenPresentDoNotWait` (default off), `GpuTimers` (`auto`, see the GPU stage timers below). All are ini only. **Menu.** None.

**Code and seams.** `ext/present/` (`FramePacingCore.h`, `FramePacingTrace.cpp`, `HiddenPresentPolicy.h`). Seam: present (`PacingScope`, `HiddenPresent`, `RecordSample` and the begin/end pairs); upstream lines: 3 (`wrapped/wrapped_swapchain.cpp`, `hooks/FG_Hooks.cpp`, `with_dx12/dx11_with_dx12_sc.cpp`).

### Frame-pacing GPU stage timers

**Origin.** Fork code. The corrected `Bridge excl. NR` row fixes a known gap: upstream's `Interop` row in "Per shader GPU times" also counts the time of NR, which runs inside the bracketed evaluate and has its own row.

**What it does.** With the timers on, 4 of every 16 frames carry timestamps: the present copy-in (D3D11, `BeforeSharedCopy` .. `AfterSharedCopy`), ReShade's own end-of-frame pass (D3D11, `begin_effects` .. `finish_effects`; the fork's own ReShade passes, the diagnostic probe and the in-place preset pass, are left out; the first ReShade runtime of a frame is timed, and a span left open from an earlier frame is closed and dropped), and the D3D12 interop copy (`ConvertCopySource` .. `PrepareScreenshot`, on the existing copy list). Every 10 s each timed stage logs `Frame pacing GPU [<stage>]: samples N, mean x ms, p95 y ms, max z ms`. `Bridge excl. NR` shows upstream `Interop` minus NR's own time (the latest values of both, clamped at 0) while frame generation is active and NR is running; it is a menu row only and has no log line. D3D11 annotations and D3D12 list markers name the timed ranges in a GPU capture while the timers run. A timer never waits on the GPU (D3D11 pairs are read only at the present with `DONOTFLUSH`; a D3D12 pair is reported once the copy queue's fence shows its work finished, and exactly once); the D3D12 readback is mapped once when the timer is created; no timer changes submission order; a creation failure turns that timer off with one warning; a new device restarts the timers; durations are never mixed across APIs. With the timers off nothing is timed and no row or log line appears; what still runs on every present is small CPU bookkeeping (a frame counter, the same trace decision the frame-pacing trace makes, and a short timer lock at the present exit and around the copy seams), and at load the built-in ReShade add-on subscribes to ReShade's begin/finish-effects events (one log line), whose handlers return at once while the timers are off.

**Status.** new; unit-tested (sampling, statistics, the slot bookkeeping of the D3D12 pairs, the effects span rule, the key resolution, the `cpu offset` pairing) and pinned against the wiring; not tried in game.

**Config.** `[FramePacing] GpuTimers` (`auto` = on only together with the frame-pacing trace above; `true` forces the timers on, `false` forces them off; FFXIV only; ini only). **Menu.** Four rows under "Per shader GPU times" while frame generation is active: `present copy-in`, `ReShade effects`, `interop copy`, `Bridge excl. NR`; the upstream `Interop` row is unchanged.

**Code and seams.** `ext/present/GpuBridgeTimers.cpp` (capture, reads, rows) and `ext/present/GpuTimerStats.h` (the pure rules). Seams: present (`PresentScope` begin and end, `BeforeSharedCopy` / `AfterSharedCopy`, `ConvertCopySource` / `PrepareScreenshot`), the ReShade begin/finish-effects events from the built-in add-on, and a call guard around the fork's live preset pass (`ext/reshade/ReShadeBoundaryCore`). `kMaxTimeRows` (`ext/core/MenuRegistry.h`) rises from 4 to 10.

The interop line adds `, cpu offset <x> ms` once the stage is calibrated: the same samples placed on the CPU clock, measured against the CPU read taken when each copy was submitted (a negative value means the GPU began before that read). The two counters are paired with `ID3D12CommandQueue::GetClockCalibration`, resampled once per ten-second line, so it costs nothing per frame. D3D11 has no such call, so the two D3D11 stages log no offset.

### Simulation tick probe

**What it does.** With `[FramePacing] TickProbe = true` the fork leases one vtable slot of the game's `Framework` object (its `Tick` function) and timestamps every tick, every DX11 bridge present and every Reflex sleep on the thread that ran it. Once every 10 seconds one line reports the window: the tick period and body time, the age from tick start to the present of the same frame, `W` (the time the game thread spends inside the native present when the present runs inside the tick), `queue` (when the present runs outside the tick), the slack, the thread ids and how many presents found the tick their frame number named. Reading the line: [notes/tick-probe.md](notes/tick-probe.md).

**How it is installed.** The slot is replaced, not the code: one compare-exchange on the pointer inside the vtable after four checks (the vtable lies in read-only memory of the game image, the slot already holds exactly the function this build's anchors found, the instance offsets the tick updates have the layout the tick's own instructions encode, and the page can be made writable). Any failure writes nothing and logs one line. An inline hook over the function's entry from another tool is composed with, in either order. Nothing is installed with the key off.

**Origin.** The slot and the anchor family follow SirenBrink's FFXIVRender; the slot number, the function's name and the instance counters are the ones FFXIVClientStructs documents for `System/Framework/Framework.cs`. The anchors, the install checks and the probe are written here from the pattern; no source was copied.

**Status.** The first version of the probe ran in a played session on 2026-10-30 (RTX 4090, DLSS-G): the lease installed, and the tick and the bridge present ran on one thread in all 126 ten-second windows, which that version could not pair (it reported `paired 0.0 %`). The current version pairs a present that runs inside the tick and reports `W` as the time inside the native present; it is unit-tested and has not been tried in game. A controller that would sleep before the tick was an experiment and is not shipped.

**Config.** `[FramePacing] TickProbe` (`auto` = off, `true` = lease and record, `false` = off; applies live; FFXIV only; ini only). **Menu.** None. **Code and seams.** `ext/latency/`, anchors in `ext/ffxiv/resolve/AnchorsLatency.h`; seams on the first D3D11 device hook, the fork's own unhook, `NativeBegin`/`NativeEnd` of the bridge present and the Reflex-sleep `PacingScope`.

## Bridge flush after signal

**Origin.** Fork code. The call site is upstream OptiScaler's own, where the flush after the fence signal sits commented out ("Games flush should be enough, so disabled for now").

**What it does.** Every frame the D3D11 side copies the frame into a shared texture and signals a fence; the D3D12 side waits for that signal before it runs the upscaler and NR. The D3D11 context hands its recorded commands to the driver at the game's own flush, so the D3D12 wait can start before any of that work was submitted. With `[Bridge] FlushAfterSignal=true` the fork flushes the D3D11 context itself, right after the signal was accepted and before the D3D12 wait is recorded. With the key off, the hand-over is exactly upstream's call sequence: the seam costs one relaxed atomic load per frame (the key is cached, the config load publishes it) and the branch is not taken. One log line at startup says the key is on: `Bridge FlushAfterSignal on: the D3D11 context is flushed after each D3D11 -> D3D12 fence Signal (experiment, off in the ini by default)`; nothing is logged when it is off.

**Status.** experiment, off by default; not measured yet. The config key, the cached seam and the source pin on the hand-over are unit-tested; whether the flush shortens or lengthens the frame has to be measured with the frame-pacing GPU stage timers or a GPU capture (key on versus off, same scene, display pacing known). Expected cost: a driver flush and less command batching per frame.

**Config.** `[Bridge] FlushAfterSignal` (ini only, default false; fragment `ext/ini/Bridge.ini`). **Menu.** None: an experiment switch, read from the ini.

**Code and seams.** `ext/bridge/` (`BridgeSeams.h` is the cached key and the seam, `BridgeConfig.h` the config key, `BridgeSeams.cpp` the startup line). Seam: `ext::bridge::FlushAfterSignal()`, one upstream line in `with_dx12/dx11_with_dx12.cpp` (`SyncDx11ToDx12`, right after the accepted fence signal). Tests: `tests/ext/bridge/bridge_config`, `bridge_upstream_pin`.

## Automatic mipmap bias

Two modes. In FFXIV the bias is applied when the game binds a sampler (the bind-time mode). In other games, or if the sampler hooks cannot be attached, the older create-time mode is used; it stands down while the bind-time hooks are attached. Design discussion and the full text of both modes: [notes/mipmap-bias-design.md](notes/mipmap-bias-design.md).

**Origin.** The bind-time mode follows the approach of SirenBrink's v6.0 bind-time mip bias, committed there first (2026-10-19): six shader stages, an immutable sampler copy, and `GetSamplers` returning the game's sampler. The table cap of 256, a comment text and the `AutomaticFFXIV` alias may echo v6.0. v6.0 replaces the game's bias, while this fork adds to it by default and detects add or replace; the bind path here has no lock and a manual override works live. The create-time mode, `MipmapBiasAuto`, the offset and the add or replace detector are fork-original (committed 2026-10-18); the formula is upstream's mip bias calculator.

**Config.** `[Mipmap] MipmapBiasAuto` (default on for FFXIV, off for other games; `AutomaticFFXIV` is accepted as another name, the main key wins), `MipmapBiasAutoOffset` (-3 to 3, default 0), `MipmapBiasObserve` (debug, off: logs every distinct original sampler bias seen at each ratio); fragment `ext/ini/Mipmap.ini`. A value set by hand (`MipmapBiasOverride`, also the "Mipmap Bias" card) always wins: the bind-time mode applies nothing while it is set (log `Bind-time mip bias: not applied because MipmapBiasOverride is set by hand`); set it to `auto` and the feature resumes at the next evaluate. A live ini that carries a number in `MipmapBiasOverride` gets none of this until that key is `auto`. **Menu.** Card "Automatic Mipmap Bias" (`mipmap_auto`, Textures tab, after Anisotropic Filtering).

### Bind-time mode (FFXIV)

**What it does.** Keeps the texture sharpening matched to the upscaling ratio with no number to work out by hand and no restart after a quality change. The target is `log2(render width / output width)` of each DX11 upscaler evaluate (DLAA 0, Quality 1.5x -0.585, Performance 2x -1.0) plus `MipmapBiasAutoOffset`. FFXIV caches its sampler states, so the fork hooks `SetSamplers` and `GetSamplers` of the six shader stages on the game's immediate context and binds an immutable copy with the current target for samplers the game made with a negative bias; `GetSamplers` still returns the game's own sampler, and at most 256 samplers take part. The target is ADDED to the game's own bias until the fork sees that the game follows the mode; it then switches to REPLACE, provisional first. The decision is logged (`Bind-time mip bias: ... REPLACE mode ...` or `... staying in ADD mode ...`).

**Status.** Ran in game (RTX 4090) on 2026-10-20, 21 and 23; no fps loss measured (comparison across sessions, not a same-session A/B); look not compared. The pure rules, the sampler table, the bind path, the six stages through real Detours hooks on a software D3D11 device, the settings and the install order are tested offline (`tests/ext/upscaler/mip_bind_*`). The older create-time mode ran in sessions with the manual value. Known limits: the notes file.

**Check.** Remove or set to `auto` any `MipmapBiasOverride` in the ini, start the game with default settings and read `OptiScaler.log`: `Bind-time mip bias: sampler hooks installed ...`, `CreateSamplerState hook installed` at the first upscaler create, then one `Bind-time mip bias: render width W, output width O, ratio bias B, offset X -> target T (add mode, first measurement)` line and one line per later change of the quality preset (targets 0.0000 at DLAA, -0.5850 at Quality 1.5x, -1.0000 at Performance 2x), and after the first change one `REPLACE` or `ADD` decision line. The textures must keep their sharpness after each change without a restart and the frame time must not change. With `MipmapBiasAuto=false` there are no `Bind-time` lines.

**Code and seams.** `ext/upscaler/MipBind*.h`, `MipBindHooks.cpp`. No new seam: `OnD3D11DeviceHooked`, `OnD3D11Unhook` and `OnUpscaleBoundary` also reach the bind-time module, and the first upscaler create reaches it through `mipbias::OnFeatureCreate`.

### Create-time mode

**What it does.** For other games, or when the sampler hooks cannot be attached. While `MipmapBiasAuto` is on, the value is `log2(render width / display width)` of the newest upscaler the game created plus the optional offset. It is applied the way upstream applies `MipmapBiasOverride` to the samplers the game creates: added to the game's own bias, only for samplers that already have a negative bias unless "MB Override All Textures" is ticked, and replacing those biases by the single value with the upstream "MB Fixed Override" option. 3840x2160 gives 0, a forced Quality preset (2560x1440) -0.585, Balanced (2258x1270) -0.766. A create that is not a game scene (size missing or outside 20 to 16384, display narrower than 640 pixels, portrait display) is ignored. It only reaches samplers created after a change.

The automatic bias does not engage while "MB Scale Override" is on (one warning, `Automatic mipmap bias: not applied while MB Scale Override is on ...`, a red line in the card, your manual value stays in force). Ticking or unticking Scale while the option is on takes effect at once while the Automatic Mipmap Bias card is on screen, and otherwise at the next quality change (the next time the upscaler feature is created).

**Status.** Opt-in, off by default; ran in game on 2026-10-19; the bind-time mode replaced it as the default. The sampler path is the manual value's, which runs in every tested session; the automatic part (which create to follow) was also replayed offline on the logged sessions.

**Check.** Set `MipmapBiasAuto = true`, start the game and read `OptiScaler.log`: every accepted create logs a line (on FFXIV every line comes twice in a row and the second says `unchanged`): `Automatic mipmap bias: create render 3840x2160, display 3840x2160, ratio 1.000 -> bias 0.0000 ...` at the login screen and `... create render 2560x1440, display 3840x2160, ratio 1.500 -> bias -0.5850 (was 0.0000 ...)` after the quality switch. An ignored create logs `ignored create ...` with the reason. With `MipmapBiasScaleOverride = true` the first create logs the warning above instead.

**Code and seams.** `ext/upscaler/MipBias.h`, `MipBias.cpp`, `ext/upscaler/menu/MipBiasMenu.cpp` (tests `tests/ext/upscaler/mip_bias_*`). No seam added: the existing upscaler seam `ApplyForcedQuality` also hands every feature create to the automatic mip bias.

## VFX mask probe (FFXIV, developer)

**Origin.** Fork-original. The upscaler's mask input is still documented (NVIDIA calls it the bias current colour mask, AMD's reactive and transparency-and-composition masks and Intel's responsive pixel mask are the same idea, and the DirectX 11 bridge already converts the same slot for all three backends), but the current programming guide adds that the buffer was not introduced for the latest models and should not be used, and names only the older preset F as supporting it. The game itself hands the upscaler no mask of any kind. This probe is the cheap question that has to be answered before anything produces a mask.

**What it does.** `[FFXIV] VfxMaskProbe` (ini only, `off` by default; `off`, `left` or `right`) puts a constant R8_UNORM mask the size of the colour input into the mask input of every DirectX 11 upscaler evaluate: one half at 1.0 (masked) and one half at 0.0, `left` or `right` choosing which half. The texture is built once and refilled only when the render size or the half changes. Two frames of a still scene never match bit for bit (the jitter phase keeps moving), so the unmasked half is the noise floor of an on-versus-off comparison: a clearly larger difference in the masked half means the backend reads a mask, an equal difference means it ignores it. One log line per change of the situation names the backend that received the mask and whether the parameter block reported it back (`Set` of an NGX parameter returns nothing, so the key is read again; the line says `reports the mask back` or `does not report the mask back`). With the key off the cost is one relaxed load per evaluate. On a frame the probe cannot build a mask - no colour input, a size it cannot split, a device that refuses the texture, a description that is not what was created - nothing is written at all, and the game's own value for that key reaches the upscaler exactly as before. The probe never clears the key.

**Status.** Developer probe, off by default. Result (closed): on the official benchmark client with DLSS 310.9.16 at the title's default preset, a constant half-screen mask in the upscaler's mask input changed nothing measurable: the masked half differed from the unmasked baseline by 7.55 against 8.51 mean absolute levels (two pairs), with no change in aliasing and at most 2 % spread across three runs. The upscaler does not read the mask in that setup, so nothing here will build a mask. Limits: no positive control was run (a runtime or preset that the guide says supports the mask), six screenshot pairs instead of ten, and no second baseline run, so strictly it is a null without a control. Not tried in a played session. Unit-tested: the rules and the log text (`tests/ext/ffxiv/vfxmask/vfxmask_core`), the texture and both halves read back on a software adapter, including 3840x2160 (`vfxmask_texture_warp`), the write path against a stand-in parameter block with the mask key only while the probe is armed (`vfxmask_apply_warp`), and the wiring read from the sources (`vfxmask_seam_test`).

**Check.** Set `[FFXIV] VfxMaskProbe = left`, start the game and read `OptiScaler.log`: one line appears the first time an evaluate carries a mask, for example `VFX mask probe: left half masked in a 3840x2160 R8_UNORM mask, given to the DLSS bias-mask input; the parameter block reports the mask back`. Switch to `right` and one more line appears. Then take the screenshot pairs and follow the protocol in [notes/vfx-mask-probe.md](notes/vfx-mask-probe.md): at least ten pairs per half, three seconds after each switch, the difference measured separately inside the masked and the unmasked half, and the threshold taken from the unmasked half's spread before looking at the masked half. A null result only counts with the positive control described there (an older runtime, or a preset the guide says supports the buffer).

**Config.** `[FFXIV] VfxMaskProbe` (`off`; `off`, `left` or `right`, anything else reads as off). **Menu.** None: ini only, a developer probe rather than a player setting. **Code and seams.** `ext/ffxiv/vfxmask/` (`VfxMaskProbe.cpp`, `VfxMaskCore.h`, `VfxMaskTexture.cpp`, `VfxMaskApply.h`). No seam added: it runs from the existing bridge boundary `ext::dx11bridge::OnUpscaleBoundary`, and nothing upstream was touched. Protocol, benchmark use and limits: [notes/vfx-mask-probe.md](notes/vfx-mask-probe.md).

## Contact shadows (FFXIV)

**Origin.** Fork code. The idea and the placement come from the fork's own lighting notes (the engine already runs its own AO, so contact shadows are the part of the screen-space lighting set that is missing; the sun light draw samples a screen-space mask the fork can multiply into); the measurement it needed, the shaders, the pass, the rules and the tests are written here. The engine's shaders are identified by their reflected names, the technique the draw diagnostic and the character preview already use, so no shader CRC is compared.

**What it does.** `[FFXIV] ContactShadows` adds the short-range shadow the engine's cascade map cannot resolve - a character's feet, a crate's edge, a pole on the ground - to the sun's light. The engine builds a screen-space sun visibility mask (a full-resolution `B8G8R8A8_UNORM` texture, 0..1, accumulated with `MIN`) and its sun light draw samples it as `g_SamplerShadow`; for the sun light draw the frame makes, the fork reconstructs the view position from the draw's own depth and marches over it at half the render window (12 steps by default, exponential growth, first hit wins, a fixed per-pixel pattern and no frame-to-frame dither, because DLSS Super Resolution is not a denoiser), multiplies the result into a private copy of that mask and binds the copy for that one draw. Pixels outside the render window keep the engine's value, and the mask itself is never written. It happens before the light pass, so before DLSS, before the tone map and before the UI: the ambient term, the engine's AO buffer and the light targets are untouched, and cloud shadow (which is inside the same mask) is applied to a contact-shadowed pixel as well.

**Which light draws.** Only a directional light draw is a sun light draw: its pixel shader declares the mask, `g_SamplerDepth`, `g_LightParam`, `g_CameraParameter` AND the cascade parameters `g_DirectionalShadowParameter` (the sun by day, the moon-like light by night). The shadowed point and spot lights declare the first four names too; since 2026-11-07 they are not indexed (one log line names the first one), so the pass never runs on them and their light colours never reach shadow mapping's night curve. The game draws two directional lights a frame, the main view's and the character view's; the main view's also declares `g_FakeSpecularParam` on this game build, and only that one feeds the night curve's colour (a build that declares it nowhere, such as the 2024 benchmark, keeps every directional draw as the source).

Normals come from the pixel's own depth neighbourhood - a neighbour is used only if its depth belongs to the same surface, so a silhouette does not borrow the other surface's normal - of the position reconstructed from the draw's depth (the light draw binds no view-position buffer), so no G-buffer encoding and no near plane is assumed. The march starts off the surface (along the normal and a few pixels along the ray), gives a hit only when the ray point is behind the sampled surface by more than a bias AND within a thickness of it in 3D AND that surface faces the receiver AND the ray point is at least the start's distance from the receiver, fades the term out over the last part of its length and fades it in from the terminator, and scales the thickness with the view depth through the world size of one depth texel there. The bound pixel shader is tracked by a `PSSetShader` seam (one integer load per draw instead of a per-draw state query: the query cost 0.65 ms a frame), and the two draws' GPU time is measured with a timestamp query pair read a run later, never waited for. The sun direction is read from `g_LightParam` and the view matrices from `g_CameraParameter` of the same draw, both copied GPU side (nothing is read back to the CPU while the pass runs; the vector is read once per session for the classification line and the unit-length guard). It is off by default, and it fails open: a draw whose shader does not declare all four names, a mask that is not the display allocation's size and 8-bit colour format (the cascade atlas carries the same reflected name, so size and format are what tell them apart), a multisampled, array or volume binding, a depth or view-position binding of another size, a degenerate or out-of-range render window, a sun vector that is not a unit vector, a mask copy the device refuses, a pass that threw, or a call from the scene HDR replay - every one of those leaves the game's draw exactly as it was, with the game's own shader resource bound, and writes one log line for the reason (32 lines a session, one per change of state). After sixteen refused light draws in a row the module switches itself off for the session with one line, so a game build whose shaders it does not recognise costs one line and no per-draw work; a refusal about the draw's *shape* is not that kind - the cascade atlas writer declares the same four names and binds the atlas instead of the screen mask - so those are logged once and the draw's shader is skipped for the rest of the session instead of being counted.

**Status.** New; experimental; off by default; checked on the benchmark and tried in one game session, where it never ran, and the contact term itself is still **not verified**: the rule indexed the 16 shaders that declare `g_SamplerShadow` (every one of them a cascade-atlas reader, refused for its `R8_TYPELESS` 2048x8192 binding) and never recognised the light draw, whose binding is named `g_SamplerShadowMask` in the view names and bound as `R8_UNORM`; both names and both formats are accepted now, and the atlas is still refused by its format and its size; and the mask's own meaning is an *assumption* for this build - 1 = sunlit is the benchmark build's convention, the mask's texels and the light shader's bytecode were never captured, and an inverted mask would put the term on the sun's own shadows, which is plausible enough to survive a casual A/B because nothing is missing for the fail-open path to catch. The one-frame dump now writes the mask's texels under a file name that says their format and keeps the bytecode of every mask-declaring shader from creation, so one session settles it. The second one-frame dump (a march with a bias, a depth-scaled thickness, a 3D distance test, a receiver-facing test and the neighbourhood normal) darkens 1.77 % of the render window and only 3.0 % of those texels sit on a depth edge (1.1 % on an object's own side, 95.9 % with no edge in their 3x3 neighbourhood), so on that frame the term still does not read as the contact shadow this entry describes; the hits trace to 4 to 25 mm of depth on lit mid-distance surfaces, where the thickness still accepts a smooth surface's own screen neighbourhood (see [notes/contact-shadows.md](notes/contact-shadows.md)). The march itself is proven on synthetic geometry: a wall's base 512 of 512 darkened texels with none on the wall, a box on a floor 19 with none on the box, a sphere on a floor 31 with none on the sphere's silhouette, a flat floor and a quantised one 0, and the CPU reference of both shaders agrees with the GPU to the level. The plumbing is proven frame-exactly. On the benchmark the reflection index recognises the engine's sun light draw and the pass runs for the whole session: `Contact shadows: sun light draw found, mask 2560x1440 format 87, sun (0.000, 0.800, 0.600) read as view space`, then `Contact shadows: multiplying the sun mask (2560x1440) by a 0.50 m march over the 2560x1440 render window, strength 1.00, 12 step(s)`. Reaching that took three fixes, all in this branch: the engine's effect compiler writes the mask and the depth with a `.T` suffix (`diag::ResourceBaseName`), the draw diagnostic's fixture bound filled with the session's ambient-occlusion shaders before the light draw arrived (`AdmitFixture`, a reserve for the light draw's shape), and the cascade atlas writer's refusals were switching the module off a minute into a session (`IsShapeDecline`). Two blobs the game handed to `CreatePixelShader` are fixtures now, so `contact_reflection` pins the engine's own bytecode. The screenshot pair does not settle where the term lands: the benchmark's camera path is time based, so two runs are never the same frame, and the difference between a key-on and a key-off run (1.8 to 16.2 mean |luma| levels per screenshot) is no larger than between two runs of the same build with the pass inert (1.9 to 22.5). The tests: the rules (`tests/ext/ffxiv/relight/contact_rules`), the reflection index on shaders compiled in the test, on the engine's effect-style name table and on the two real blobs (`contact_reflection`), the pass and its shaders on a software adapter over synthetic buffers - a wall within reach darkens the ground beside it, a wall two metres away does not, open ground and a NaN pixel stay lit, the sign key and a quarter-turn camera behave (`contact_pass_warp`), the injection (the copy bound for one draw, the game's own resource back afterwards also when the draw throws, the switch-off after sixteen refusals that are not shape refusals, the log budget: `contact_apply_warp`), and the wiring pins (`contact_pins`). Not measured: the GPU cost in a real session, the look at 4K and at other resolutions, night scenes and interiors, and frame generation with the pass running.

**Check.** Set `[FFXIV] ContactShadows = true` and look at a character's feet in sunlight: a soft dark gradient within half a metre, away from the sun, that the engine's own shadow does not draw. `OptiScaler.log` writes one line per change of state: the card's state line carries the counters a session reads first (`N pass(es), one per light draw served, M left alone (K of them of another shape); the last classified light draw's mask is 3840x2160 in format 57 at slot 8 (run)` means the rule found this build's mask and the pass is applying the term, and `2048x8192 in format 56` means it is still looking at the atlas writer), then `Contact shadows: sun light draw found, mask ...x... format ..., sun (...) read as view space`, then `Contact shadows: multiplying the sun mask ... by a 0.50 m march over the ... render window, strength 0.50, 12 step(s), sun in view space toward the sun`, and one line per session with the measured cost: `Contact shadows: on cost: N draws seen, 64 sampled, the draw's lookup ... ms per draw (... ms at 9250 draws a frame; the budget is 0.02 ms); N pixel-shader binds seen, 64 sampled, ... ms per bind (... ms a frame at that rate)`, and the run line gains `its two draws ... ms on the GPU` once the timestamp queries have landed. A `Contact shadows: the draw was left alone (...)` line names the reason; sixteen in a row of the kind that counts (not the cascade atlas writer's, which is logged once) and the module says it is off for the session. Turning `ContactShadowsStrength` to 0.2 makes the term faint in an 8-bit mask; turn it to 1.0 to see where it lands before settling on a value.

**Config.** `[FFXIV] ContactShadows` (false), `ContactShadowsLength` (0.5 m, 0.05 to 2.0), `ContactShadowsStrength` (0.5, 0 to 1; 0 runs nothing), `ContactShadowsSteps` (32, 4 to 64). Two ini-only keys exist for a game build where the sun vector has to be measured again: `ContactShadowsSunSpace` (`auto`, `world` or `view`; `auto` reads as view, the space this build was measured to report) and `ContactShadowsSunSign` (`auto`, `toward` or `from`; `auto` reads as toward the sun). **Menu.** Card "Contact shadows (FFXIV)" (`ffxiv_contact_shadows`, FFXIV tab, after the FFXIV HDR10 card): the switch, the three tuning sliders and the state line. **Code and seams.** `ext/ffxiv/relight/` (`ContactShadowsRules.h` for the pure rules, `ContactShadowsPass.{h,cpp}` for the two draws, `ContactShadowsApply.cpp` for the classification and the bind/restore, `Inject.{h,cpp}` for the reflection index, the config side and the seam's wrapper, `shaders/ContactShadows.hlsl`, `RelightMenu.cpp`). Seams: one guarded call in the existing FFXIV draw hook (`ext/ffxiv/lighting/FfxivLightingCapture.h`, `Around`) and one in its `CreateShader`, plus a Detours hook on `ID3D11DeviceContext::PSSetShader` (`LIGHT_ATTACH(setPs, OnSetPs)`) that is attached with the other FFXIV lighting hooks and is installed whether the key is on or not; no upstream line, no game address. **Cost with the key off:** the per-bind trampoline and one out-of-line call (the author measured 1.0 ns a bind, 0.007 ms a frame at 6,300 binds), one relaxed load of the key a draw, and the mask-name scan of every pixel shader's bytecode when the game creates it (0.43 ns a byte; about 58 ms over a session's ~33,000 shaders, at load time only; the scan is deliberate with the key off). Measurement protocol, benchmark result and limits: [notes/contact-shadows.md](notes/contact-shadows.md).

## Engine pass overrides (FFXIV, experimental)

**Origin.** Fork code. The mechanism comes from the fork's own analysis of the engine's passes: FFXIV hands its own parameters to its own passes in named constant buffers, and the fork can copy one, scale it and bind the copy for a single draw without touching the game's memory, its shaders or any address of its executable. The draw is recognised the way the contact-shadow pass recognises the sun light draw (the reflected names in the shader's bytecode), so no shader CRC is compared.

**What it does.** `[FFXIV] EnginePassOverrides` arms a primitive that patches one of the engine's own constant buffers for exactly one draw: the buffer the draw bound is copied on the GPU into a fork-owned constant buffer, one compute shader copies every float4 into a fork-owned raw buffer and multiplies or replaces the components a small table addresses, the result is copied into a second fork-owned constant buffer and bound for that draw, and the game's own buffer is put back before the hook returns (a scope guard, so a draw that throws still gets its binding back). Two knobs ship:

- **Ambient sky visibility** (`AmbientSkyVisibilityScale`, 1.0, 0 to 2; 1.0 runs nothing): the level of the sky light the ambient probes contribute, written as two multipliers on the ambient probe table (64 probes of 192 bytes) in one patch: the probe's own `skyVisibilityScale` (probe offset `0xB0`, multiplier `{scale, 1, 1, 1}`, so the `ssaoMask` beside it keeps its bits) and the probe's `shRecipScale` (the `.w` of the float4 at probe offset `0x30`, multiplier `{1, 1, 1, scale}`, so the probe's colour keeps its bits). The second field is the one the deferred composite applies to every probe it ends up using, on the ambient and on the indirect specular; the first is read only inside the shader's probe loop (`index < paramNum - 1`) and only for a probe whose `(1 - bakeLightRate) * skyVisibility` is below 0.5, which a table holding one probe never reaches. Lower values darken the flat sky-lit fill of a night without touching the baked probe values, the direct light or the shadows, and they dim the probe's share of the indirect specular as well. Both offsets, the stride and the probe count come from the shader's own reflection: the first entry ends exactly at the declared 12,352 bytes, the second at 12,224. Two draws a frame are patched (the composite draws whose shader declares both `g_AmbientParamArray` and `g_SamplerLightDiffuse` and that write one render target at the main-scene size); each costs two 16 KB copies and one dispatch.
- **Wetness** (`WetnessOverride`, -1.0, -1 to 1; below 0 runs nothing): the wetness amount the engine hands every material draw in `g_WetnessParameter`, a 32-byte buffer bound at the slot each shader declares (4 on almost every draw, 5 and 1 on a few; about 1,500 draws a frame). `0.0` forces dry ground and `1.0` full wetness whatever the weather is, and the engine's own dryness blend (`.y = 1 - .x/2`) follows it; the angles and tuning constants beside those two floats keep the game's bits, and so does the second float4. The game binds one such buffer for a whole frame, so the patch runs once a frame and that frame's later draws bind the cached copy; the frame boundary is an output-frame counter both present paths tick. The engine's rain-exposure mask is untouched, so the gloss appears under open sky and not under cover, and grass has no gloss response: judge it on stone.

The scale shader reads the buffer as raw bits and converts only a component whose multiplier is not 1, so every byte beside a knob comes out bit-identical; a set entry replaces a masked component with a bit pattern computed on the CPU, so a replacement passes through no conversion either. A second mode writes a small owned buffer from the CPU at most once per frame, for the knobs whose target is a handful of floats.

The draws are recognised by the parameter names their pixel shaders declare, reflected once at shader creation into a 64-bit anchors word that carries each knob's flag bit and the slot its name sits at: one flag bit and one 8-bit slot field per knob, fixed and checked at compile time so no two fields can share a bit. The word also carries the texture passes' anchors, because they share this module's draw seam: ambient occlusion's reader bit and slot, the light shafts' light-draw, composite and tone-map bits with their slot, and the puddles reader bit. The stored shaders live in this module's own open-addressing table (65,536 slots over a 20,000-shader cap, linear probing of at most 16 slots at a bind, 1.5 MiB allocated on first use; insertions at shader creation under the index's one lock, a bind that takes no lock), so a draw costs one hash, a short probe and a pointer compare instead of a `PSGetShader` (0.65 ms a frame in the contact-shadow measurement); a recycled shader address is caught by the id the object itself carries, and a shader whose 16 probes are all taken is passed on with one line for the session.

The draw seam is entered while any of the module's features wants a draw. The two constant-buffer knobs' own master switch arms them; each texture pass's own card arms its pass, so the ambient occlusion, light shafts, puddles and screen-space reflection cards run with `EnginePassOverrides` off and are not switched off by it. The feature bit is cleared only when every one of those features has stood down, and the master changes nothing but its two knobs.

It fails open: a draw whose shader does not declare a knob's names is another pass of the frame and is passed on at one integer load, before any state is queried, and it is not counted as a refusal; an ambient buffer that is neither 16,384 nor 12,352 bytes, a draw that does not write exactly one render target at least a minimum scene size, a render window that does not fit inside it, a wetness buffer that is not 32 bytes, a character-preview replay, an allocation or dispatch that failed, or a call that threw - every one of them draws the game's original call with the game's own buffer bound and writes one log line for the reason (32 lines a session, one per change of state). Each knob keeps its own sixty-four-refusal streak, and a draw a knob never asked for is neither its run nor its refusal, so a build whose composite changed shape stands the module down even while 1,500 material draws a frame keep working; the fifth distinct wetness buffer of one frame is passed on rather than patched. A master left on with both knobs at the engine's own values costs one relaxed load per draw and one per pixel-shader bind. The patch is applied by the draw-once rule the contact-shadow pass uses, so it does nothing on a frame the scene HDR path replays: while scene HDR is requested, the composite draws that would be patched are the plain ones and the ambient knob has no effect.

**Status.** New; experimental; off by default. The primitive is proven: the rules and the index on the host (`engine_rules`, `engine_index`), the three-buffer scale and the CPU-written mode on a software adapter (`cbpatch_warp`, `cbpatch_set_warp`, `cbpatch_write_warp` - the addressed values scaled or replaced, every other byte bit-identical including denormals and NaN payloads seeded beside the knob, a DYNAMIC source too, the game's buffer unread and unwritten, the game's binding back also when the draw threw), and the wiring (`engine_pins`). The field's effect on the picture is **unproven and under analysis**: it ran in one game session on 2026-10-31, night outdoors, master on with `AmbientSkyVisibilityScale` at 0.70 - no crash, no visible artefact and no fps change noticed, but no visible change from the knob either. The capture taken in that session holds the table the knob scales with a single probe at `skyVisibilityScale` 1.0 and `skyVisibility` 1.0, night, day and interior alike, which may be a default or fallback table rather than the one the composite reads; the log was not enabled for that session, so three explanations remain - the sampled table is a fallback and the composite reads another buffer, the module refused the composite draws, or the patched slot is not the one the composite reads - and the next capture carries the composite shader's bytecode so the slot can be read offline. Not verified: the visible effect, the GPU cost in a real session, and whether `skyVisibilityScale` or `shRecipScale` is ~1.0 in the shipped build (the pass reads them on the GPU only; a capture's `cbdump.csv` shows the game's own values, never the patch, because the dump is taken before the module swaps its copy in). The knob now writes both per-probe fields the composite weights its ambient with, so a one-probe table - the 2026-10-31 session's - is no longer a spot where it can be silent; it does cost the probe's share of the indirect specular too. The wetness knob has not run in a game at all: its layout comes from a live capture (32 bytes, the wetness amount in the first float and the engine's own dryness blend in the second, about 1,500 draws a frame), its patch is proven on a software adapter on a static and on a dynamic game buffer with every byte beside the two replaced bit-identical, and its acceptance is the dry-plaza pair in Check.

**Check.** Set `[FFXIV] EnginePassOverrides = true`, move `AmbientSkyVisibilityScale` off 1.0 and compare two screenshots at the same camera at night, slider 1.0 against 0.7 (that is the acceptance test; in the 2026-10-31 session it gave no visible difference, and the 2026-11-01 analysis found why: that session's table held one probe, so the sky-visibility field could not show - a spot for the new A/B must have more than one probe, and the second field now moves in every spot). `OptiScaler.log` says what the module did: `Engine pass overrides: scaling the ambient table's sky visibility and SH reciprocal scale by 0.700 over 16384 bytes for the 2560x1440 composite ...` when a composite was patched, `Engine pass overrides: the draw was left alone (...)` with the reason when one was not, and `Engine pass overrides: 64 of one knob's draws in a row were left alone, so the module is off for this session` when it stood down. **Config.** `[FFXIV] EnginePassOverrides` (false), `AmbientSkyVisibilityScale` (1.0, 0 to 2; 1.0 runs nothing; scales the probe's sky visibility and its SH reciprocal scale), `WetnessOverride` (-1.0, -1 to 1; below 0 runs nothing). **Menu.** Card "Engine pass overrides (FFXIV)" (`ffxiv_engine_passes`, FFXIV tab, after the contact shadow card): the master switch, the ambient slider, the wetness slider and a state line. **Code and seams.** `ext/ffxiv/engine/` (`EnginePassRules.h` for the pure rules and the anchors map, `PassIndex.{h,cpp}` for the open-addressing index, `CbPatch.{h,cpp}` and `shaders/CbScale.hlsl` for the primitive, `EnginePass.{h,cpp}` for the draw path and the per-frame wetness cache, `EngineMenu.cpp` for the card), plus the output-frame counter in `ext/present`; the texture passes that share the seam keep their own files (`AoApply.{h,cpp}`, `ShaftsDraw.cpp`, `GlossPuddlesApply.{h,cpp}`, `SsrApply.{h,cpp}`). ## Shadow mapping (FFXIV, experimental)

**What it does.** Retunes the game's own deferred light at two seams the fork already reads, so a night scene's shadowed regions and its ambient floor lift without moving the sky, the highlights or the tone map. Lever 1 (the mask lift): the engine's screen-space sun/shadow mask - the R8 texture `g_SamplerShadowMask`, which the game's sun light draw *squares* before it multiplies the diffuse term (the shading's own shadow visibility term is the mask squared) - is copied GPU-side, the remap is applied to the value the square shares (`m'² = m² + (1−m²)·lift`, the design-doc correction: applying the lift to the square makes the key read linearly in the picture, and a lift of 0 is the engine's own mask byte for byte), the copy carries the square root of the remapped square so the shader's own square lands back on it, and the copy is bound at the mask slot for exactly that draw with the game's binding restored afterwards. An optional tent (0-2 mask pixels of reach over the 5×5 kernel) feathers the lifted mask's edges; it feathers the lift itself, so a lift of 0 remains the byte-exact passthrough whatever the softness says. Lever 2 (the night ambient lift): ONE CbPatch dispatch on the deferred composite scales the ambient probe table's *global* sky-SH scale (the header's `skyShRecipScale` at byte 4 - the night's dominant term, which the shipped ambient knob never touches - through multiplier[1] of the table's first float4, the corrected shape: `byteOffset 4, stride 0` is not addressable, `AddressFits` refuses both) and every probe's SH reciprocal scale (byte 112+192k, `.w`, the engine's own `AmbientSkyRecipEntry` shape with this module's multiplier). When `AmbientSkyVisibilityScale` is armed the two entries go into the SAME dispatch after the served knob's own entries, so the two levers compose multiplicatively on the field they share and stay one bind. Both levers key on the frame's own `g_LightParam.m_DiffuseColor` luminance (`NightCurveToggle`): full effect below 0.15, zero above 0.9 (a smoothstep between them) - **the thresholds are PROVISIONAL** and the report names them as settled by the capture protocol below; a toggle that is off pins the full effect for a debugging A/B at noon.

**The night curve's input** (2026-11-07) is the **visible sun's elevation**, not the shading light's colour: the fog post's own sun, `cFogParam[2].y` (the world y of its direction; 0.183 on the 2026-11-06 daylight frame, -0.109 / -0.058 / -0.012 on the three evening frames), published by the god rays module's fog-post capture (see God rays, "The fog sun"). `night = smoothstep(sin(-1 degree), sin(-7 degree), y)`: no lift while the sun is above 1 degree below the horizon, full by the end of civil twilight (0, 0.96, 0.34 and 0 on the four frames; the colour curve said 1 on the fourth, a frame the player saw as daylight, because the main view's shading light there is the dim moon-like light). The ONE curve drives both levers (the mask lift and the night ambient table). It does not depend on the god rays being on: shadow mapping asks the fog-post capture for the sun row whenever the curve can act (the master key on, the lift or the night ambient key off their identity, `NightCurveToggle` on), and the fog state failing to land several times in a session does not matter (the sun row needs no height profile). A fog sun counts as current for 120 rendered frames (shadow mapping's own clock - frames with a served light draw - not the present counter that frame generation steps two to four times per game frame); past that, or when none has landed, the curve falls back to the main view's light colour (the main view's sun light draw only: the character view's light and the point lights no longer flip it between day and night colours within seconds). `OptiScaler.log` writes one line per change of source: `Shadow mapping: the night curve reads the fog sun (its world elevation sine is -0.109), curve 0.956` or `Shadow mapping: no fog sun has landed recently, so the night curve reads the main view's light colour (luminance 0.109), curve 1.000`. The character ambient (CharaAmbient) keeps reading the light colour through the same curve function: it is not switched here.

**Status.** New; experimental; off by default, and every default is the engine's own picture (nothing copies, nothing patches, nothing draws). The code is pinned: the rules on the host (the clamps, the curve, the remap identity, the merged-table order), the mask remap and the combined contact-combine stage on D3D11 WARP against the CPU reference (byte-exact at the identity, the lift's bytes, the tent on a real step edge, the light-draw fixture reading the lifted copy from the bound slot with the restore putting the game's mask back), and the ambient entries on the device in the ONE CbPatch dispatch with the shipped knob's entries (the composed probe field answers the product, the header field answers the lift alone, every other byte bit-identical, the game's buffer never written, ONE `Scale()` per patched draw). The visible effect is **not verified in game**: the thresholds, the lift's perceptual default and the ambient lift's own strength all wait for the capture session (see [notes](notes/engine-pass-overrides.md)' engine-pass-overrides report's shadow-mapping brief for the five-stop protocol).

**Check.** At night with the character's shadow visible: set `[FFXIV] ShadowMapping = true`, `ShadowLift = 0.5` and `NightAmbientLift = 2.0`, screenshot; set them to 0 / 1.0, screenshot; the difference is the report's own two levers. At day (or with `NightCurveToggle` on and a bright scene), both settings at 0 / 1.0 are the engine's own picture. `OptiScaler.log` writes once per state change: `Shadow mapping: lifting the sun mask (3840x2160 format 61), lift 0.500, softness 0.00 px, curve 1.000` when the mask lift ran (the contact shadows path's combine carries it with one line: `Shadow mapping: the sun mask lift rides the contact combine (lift ..., softness ..., curve ...)`), and `Shadow mapping: lifting the ambient table (g_AmbientParamArray at cb2, 12352 bytes, 2560x1440 composite) by 2.500, curve 1.000 (header skyShRecipScale and 64 probe shRecipScale fields, one dispatch)` when the ambient arm patched. A refusal (a composite or light draw the module cannot serve) is one `Shadow mapping: the light draw was left alone (...)` line, and `Shadow mapping: 64 light draws in a row were left alone, so the shadow mapping module is off for this session` stands the mask route down for the session; the light colour it had read is forgotten at that moment (nothing could refresh it any more), so a ticked night curve falls back to the engine's own ambient until the module is re-armed. A served draw on the colour-only path (the game's own mask) ends the run of declines, as a lifted draw does.

**With Contact shadows off.** The module does not need `[FFXIV] ContactShadows`: the draw hook hands the sun light draw to the module's own route whenever the lift key is off 0, or the night ambient key is off 1.0 on the ticked curve (that arm needs the frame's light colour, and the route is where it is captured). With both keys at their defaults nothing is entered, tracked or copied. A retest reads the log, because the picture may not change visibly (the ambient lift once showed no visible change, undiagnosed): `Shadow mapping: the mask route is serving the sun light draw (mask ..., g_LightParam at cb...)` when the route first follows a light draw, `Shadow mapping: the first light colour landed (r, g, b), luminance ..., curve ...` when the capture ring's first read lands, then the two run lines above. A module that stays idle says why, once per state: `the mask route was asked 4096 times and none of the draws was a sun light draw the light-draw index knows`, `the bound g_LightParam is N bytes and the curve reads the first 48`, `the capture ring's staging buffer could not be created`, `the night curve has no light colour after 240 asks (... route draws, ... copies staged, ... reads landed, ... not ready)`, `the ambient entries do not fit the composite's table sizes`, and `N sun light draws were served and the night ambient lift (x...) was never asked for entries` (after 600 served light draws; the engine seam has not classified the deferred composite, which tells that apart from a curve that stayed at 0). The once-per-state lines of the route are written again only after the master switch was turned off and on. The engine seam names the composite it patches once (`Engine pass overrides: composite indexed (g_AmbientParamArray at cb..., g_SamplerLightDiffuse at t...)`). The card's state line shows the module's own counters: route draws, copies staged, reads landed, composite dispatches that carried the entries.

**Config.** `[FFXIV] ShadowMapping` (false), `ShadowLift` (0.0, 0 to 0.9; 0 is the engine's own mask and runs nothing), `ShadowEdgeSoftness` (0.0, 0 to 2; feathers the lift), `NightAmbientLift` (1.0, 1.0 to 4.0; 1.0 is the engine's own table and runs nothing), `NightCurveToggle` (true). **Menu.** Card "Shadow mapping (FFXIV)" (`ffxiv_shadow_mapping`, FFXIV tab, right after the engine pass overrides card): the switch, the two sliders of the mask lever, the ambient lift slider, the curve toggle and a state line. **Code and seams.** `ext/ffxiv/shadows/` (`ShadowsRules.h` for the pure rules and the entry tables, `ShadowsHooks.h` for the six sink hooks the two seams read, `ShadowsPass.{h,cpp}` and `shaders/ShadowLift.hlsl` for the module's own copy/remap/bind, `ShadowsDispatch.cpp` for the state, the capture ring and the sinks, `ShadowsMenu.cpp` for the card); the mask lift rides the contact shadows pass's own combine when contact shadows is armed (one copy per frame per light draw, its values travel through the ext-internal sink the combine reads) and runs its own one-copy one-draw remap at the light draws when contact shadows is not armed (the same seam, `relight::Inject`, hands the draw across on the same terms); the ambient entries ride the engine pass overrides module's ONE CbPatch dispatch on the composite draw through an ext-internal entry provider. Seams: none new (the relight module's own draw route, tracker and shader hooks, and the engine module's own `ApplyFeatureBit`/`OnGameDraw`/`Release` chain carry the module's arming and its entries); no upstream line, no new detour, no game address, and the light-colour capture is a staging-ring read with `D3D11_MAP_FLAG_DO_NOT_WAIT` (never a wait, never a flush: the go-through is the readback ring the light shafts' sun reader models). **Costs with the keys at their defaults:** one relaxed read per draw and per bind (the relight seam's own), nothing else.

## Ambient occlusion (FFXIV, experimental)

**Origin.** Fork code. The same mechanism as the engine pass overrides above, applied to a texture instead of a buffer: the engine samples its own screen-space occlusion from a texture whose name its pixel shaders declare, and this fork computes its own occlusion, binds it in place of the engine's for the draws that sample it, and puts the engine's binding back. Nothing is written into the game's memory, no shader of the game is replaced and no address of its executable is used; a reader is recognised by the reflected name, never by a CRC.

**What it does.** `[FFXIV] AmbientOcclusion` arms a pass that runs once a frame, at the reader of that frame that completes the pass's three inputs, and computes this fork's occlusion from the game's depth and the G-buffer target that holds the world-space normal (`g_SamplerGBuffer4`). Two draws in a private device-context state write an owned texture of the engine's own size and format: a horizon search of two slices and 4, 8 or 16 taps a direction in the tangent plane of each pixel's normal, rotated per pixel by a 4x4 pattern, then a 4x4 denoise, the strength, the blend with the engine's own value and the 8-bit encoding. The engine's occlusion texture is the render size, but its own producer fills only a quarter of it (960x540 of a 1920x1080 texture in a captured 3840x2160 session), and its readers sample it by the same allocation-relative coordinate they use for the G-buffer and the lighting: a texel of this pass therefore stands for the depth texels at the same fraction of the depth allocation, and the pass computes exactly that quadrant. The rest of the texture starts as a copy of the engine's own texels, so a reader that samples outside the quadrant sees the picture it saw before. A frame's readers do not all declare the pass's three inputs, and which of them comes first changes from frame to frame: in a captured frame a material draw declares the camera table at constant-buffer slot 3 and neither texture, the deferred composite the G-buffer normal at texture slot 9 and the camera table at slot 1, and a sun light draw the depth at texture slot 0, the G-buffer normal at slot 7 and the camera table at slot 1 - and at least two captured light families declare that depth and camera but not the normal. So each reader contributes the depth, the normal and the camera table it declares, the frame keeps the first usable binding of each together with the camera table's own device object - which is the view's identity, so a reader that binds another view's table (a reflection, a preview camera) refuses the frame instead of being mixed into it, and a texture whose reader binds no usable camera table is not taken at all - and the pass runs at the first reader for which all three are in hand, bounded to 64 readers of a frame. **Serving starts at the completing reader**: the texture is swapped only after the pass has run, so a reader of that frame before the completing one keeps the engine's occlusion. In the captured order (the sun light draws, then the composite, then the materials) the light draws come first and declare the normal, so a frame that starts on one of them is completed at its first reader and served whole; a frame that starts on the light family without the normal is completed at the next light draw that has it, so its first light draws keep the engine's mask - the tear a capture shows - and a frame whose first reader is the composite or a material draw has no later depth supplier and is never completed, so it keeps the engine's occlusion all frame. Every draw from the completing reader onward that binds the engine's occlusion texture - about 50 sun light draws, the two deferred composite draws and about 250 forward/material draws in a captured frame - binds this one for that single call, and the game's binding is put back before the hook returns. The engine's occlusion texture alternates between two objects from one frame to the next, so the frame records which one its completing reader bound, and nothing is carried across a frame.

The captured readers sample the texture's red channel and use it as `1 + (x - 1) * k`, so 1 is unoccluded; the pass writes red and returns the engine's own green, blue and alpha untouched, because a channel whose meaning has not been measured cannot be corrupted by it. The light and composite shaders were not in the capture, so a session still confirms that they read that channel.

It fails open. A draw whose shader does not declare the name is passed on at one integer load; a binding that is not the engine's render-size texture (the engine also binds a 4x4 placeholder under the same name on a few dozen draws) is another draw of the frame and is not counted as a refusal; a reader without a single-sample depth, without the normal at the same allocation, without a camera table of at least 0x160 bytes, or with a render window that does not fit its depth, draws the game's original call, with one log line that names the reason and what that frame has collected. A frame whose readers never supply all three, or whose readers span two views, keeps the engine's texture for the whole frame; after 64 such frames in a row the module pauses, inspects every reader of one frame about 2.7 seconds later (120 frames at the measured session's 45 frames a second) and re-arms at the first frame it can serve, so a menu or a loading screen costs the effect for a few seconds rather than for the session. The feature bit is set only while this card's switch is on and the strength and the blend are both above 0, so a master left on at 0 costs one relaxed load per draw.

**Cost.** Expected, not measured on a real card. Once a frame: one shader read, two resource reads, one copy of the camera table (0x160 bytes), one 64-byte parameter write, one copy of the engine's occlusion texture (8 MB in the captured session), two draws over the quadrant only, and a timestamp pair that is read a run or two later and never waited for. Per reader draw: one relaxed load, one resource read for its slot, the swap and its restore, about 300 draws a frame. The search dominates: 16 depth loads a pixel at the medium quality over the quadrant. The log's GPU line reports the measured pair once it has landed.

**Status.** New; experimental; off by default. Proven on a software adapter (WARP): the pass reproduces a CPU reference of the same search to within two thousandths of a level on a synthetic floor-and-wall scene (`ao_warp`), a flat floor stays fully lit, a wall's foot darkens, a strength of 0 leaves the engine's texel at every blend, and two runs of one scene are byte-identical; the quadrant is byte-exact the engine's outside and identical to the same scene rendered as its own allocation inside; the other three channels come back byte-identical at every texel; the slot swap and its restore are proven on a real device (`ao_apply_warp`); the rules, the frame's merged inputs and the pause on the host (`ao_rules`). **Tried in game, and the user confirmed it works**: a session served frames with about 610 to 640 of their reader draws bound to this module's texture, and also showed frames no reader could complete (24 logged refusals in three reader shapes, with served frames between them and a frame served at 17:49:04) and, at the end, 64 such frames in a row that stood that build's module down for the rest of the session. That build had no pause; this one collects a frame's three inputs across its readers and, after 64 frames in a row left alone (one count a frame, at its first wait or its refusal), pauses and inspects one whole frame's readers about 2.7 seconds later (120 frames at that session's 45 frames a second), re-arming at the first frame it can serve. Neither the torn frame that follows from serving a later reader nor that pause has been judged again. How the fixed picture looks, the GPU cost on a real card, the channel the light and composite shaders read and how the pause behaves in a menu or a loading screen are still unmeasured. A session checks the A/B screenshots in a corner-rich scene (off, on and blend 0.5), the served count against the roughly 300 occlusion bindings a captured frame makes (202 to 299 is the expected range; below about 150 is a classification problem), the refusal line's own shape, and the GPU figure; the darkening must sit at the wall's foot, not magnified in the middle of the screen and not absent, and corners getting brighter mean the 1 = open convention is inverted.

**Check.** Turn `[FFXIV] AmbientOcclusion` on in a corner-rich scene (a stone wall meeting a floor, a pillar's foot), keep `[Log] LogToFile` on, and compare two screenshots at the same camera, off against on; lower `AmbientOcclusionBlend` to 0.5 first if the picture is too dark. `OptiScaler.log` says what the pass did: `Ambient occlusion: 1920x1080 at 8 steps a direction, radius 1.00 m, ...` when it ran, `Ambient occlusion: the frame waits for another reader (…)` (one reader supplied only part of the pass's inputs) or `Ambient occlusion: the frame could not be served (…)` (a size, another view's camera table), followed by what the frame has collected (the occlusion texture's size and format, the depth's and the normal's sizes and slots, the camera table's size and slot, the window), `Ambient occlusion: N reader draws of the last frame bound this module's texture` once a session, and `Ambient occlusion: 64 frames in a row were left alone, so the module pauses and looks at a frame's readers again 120 frames later (about 2.7 seconds at 45 frames a second)` when it paused - the scene coming back then re-arms it at once.

**Config.** `[FFXIV] AmbientOcclusion` (false), `AmbientOcclusionRadius` (1.0 m, 0.1 to 4.0), `AmbientOcclusionStrength` (1.0, 0 to 2), `AmbientOcclusionBlend` (0.5, 0 to 1; 0 runs nothing), `AmbientOcclusionQuality` (`medium` = 8 taps a direction, `low` = 4, `high` = 16). **Menu.** Card "Ambient occlusion (FFXIV)" (`ffxiv_ambient_occlusion`, FFXIV tab, with the other engine pass cards): the switch, three sliders, the quality combo and a state line. **Code and seams.** `ext/ffxiv/engine/` (`AoRules.h` for the pure rules, `AoPass.{h,cpp}` and `shaders/Ao.hlsl` for the pass, `AoApply.{h,cpp}` for the seam, `AoSwap.cpp` for the one slot swap and its restore, `AoMenu.cpp` for the card). It hangs on the shared engine module's draw seam and feature bit (one anchor bit with its slot field, one swap line, one stamp call in the shader-creation hook) and adds no upstream line. Design and the measurement: [notes/ambient-occlusion.md](notes/ambient-occlusion.md).

## Light shafts (FFXIV, experimental)

**Origin.** Fork code. The engine renders the frame's lighting into an FP16 scene texture and its tone map reads that texture once; this fork builds a sky mask from the frame's own depth, blurs it toward the sun (taken from the frame's light pass), adds it to its own copy of the scene, and binds that copy for the tone map's one draw. The game's scene is only read, never written; no shader of the game is replaced, no address of its executable is used, and the draws are recognised by the parameter names their pixel shaders declare plus their own shape, never by a shader CRC.

**What it does.** `[FFXIV] LightShafts` runs before the engine's tone map reads the lit scene: a half-resolution sky mask from the depth (1 where the depth is the far plane, 0 on every surface; the engine's depth is reversed-Z, so the far plane is 0, and a NaN or a negative depth reads as a surface), a radial blur toward the sun's screen position (`Samples` taps, each `Decay` times fainter, the reach scaled by `Density`), the sun's colour into one texel (the engine's own colour for that light when it reports one, otherwise the sky's colour around the sun's screen position, sampling sky pixels only, so what stands in front of the sun cannot tint the shafts), and a composite of the scene copy plus `mask * intensity * colour` over the render window. The copy is what the tone map's `t0` holds for that one draw, and the game's own view is put back afterwards, also when the draw throws. The sky itself keeps its own value: the shafts land on the surfaces the light crosses, never on the sky they come from.

The tone map's own parameter buffer is read too: its second float is the engine's exposure multiplier, and the scene value at which the picture reaches display-white is its reciprocal - the bound the shafts' light is measured against, so the same intensity key is the same share of the white in a bright frame and a dusk one.

The sun is the frame's light draw that writes the engine's pair of light buffers without blending into them and whose light reports no world position, a unit direction and a direction above the horizon (the same vector negated is a second directional light's draw - the sun's mirror - and is refused). Both halves are needed: the local lights accumulate into the same pair, and the wetness volumes that come first in the frame write one R8 target and blend. From that same draw the pass takes the frame's depth and a camera buffer it validates by the projection's own rows, and out of that buffer the view-projection the sun's world direction is projected through. The deferred composite declares the ambient probe table, and its single render target is the lit scene, which is what makes the scene recognisable without a hash; the tone map is the draw that reads that scene as `t0` into a single FP16 target of the same size. The light's bytes and the camera's view, view-projection and projection are read back through small staging copies issued at the light draw and mapped at a later frame without waiting: a ring of four staging pairs, the newest copy first and an older one when the newest has not landed, on the module's own count of rendered frames (the light pass, the composite and the tone map are one frame, whatever the output-present counter does under frame generation), so no frame ever waits on the GPU and a stale sun is never composited; a read that has not landed for ninety frames skips the frame with one line.

A frame with no sun draw, a light whose bytes have not arrived, a sun behind the camera, a sun further outside the window than a quarter of it, or a sky too dark to be a sun adds nothing at all and is not counted as a refusal - each has its own line once. Sixty-four counted refusals in a row switch the pass off for the session with one line. It is inactive while the engine's scene HDR is on, because that path replaces the tone chain this pass draws before; the HDR key is read where the module decides, so HDR off starts the pass on that frame, and the log and the card say so.

**Cost.** Expected, not measured on a real card: four draws (the half-resolution mask, the half-resolution blur, one texel for the sun's colour and the full-screen composite) and one copy of the whole scene allocation per frame (66 MB at 4K), with a timestamp pair around the four draws that is read a run or two later and never waited for. The log's GPU line reports the pair once it has landed.

**Status.** New; experimental; off by default. ## Puddles (FFXIV, experimental)

**Origin.** Fork code. Rain makes the ground glossy and the engine does that itself: its material shaders read `g_WetnessParameter` and write the five G-buffer targets, which the light passes, the deferred composite and the forward draws then read. What the engine does not have is the shape of standing water. This feature replaces one of those G-buffer targets for one draw at a time, the way the ambient occlusion pass replaces the engine's occlusion texture. A first design shaped the engine's R8 screen-space mask, which turned out to be the sun's shadow mask; it was parked and replaced by this one.

**What it does.** `[FFXIV] Puddles` copies one of the engine's own G-buffer targets (key `PuddlesGlossTarget`, default 1, the material pack) into a texture of the engine's own size and format, once a frame, at the frame's first draw that reads that target and also declares the G-buffer normal, the depth and the camera table. A full-screen triangle over the part of the copy inside the render window reconstructs each texel's world position from the depth and the camera, reads a world-anchored two-octave noise field at its world x and z, and replaces one channel of the copy (key `PuddlesGlossChannel`, default `a`, the material pack's gloss) with a wet value where the surface faces up and a puddle is; a surface steeper than sixty degrees, a texel with no surface, a texel whose normal is not a unit vector and every texel outside the render window keep the engine's own bits. The threshold is `1 - coverage * wetness`, where `wetness` is the amount the engine's own draws read: the engine's weather amount, or the amount the engine pass's wetness knob forces while that knob is armed. The puddles ramp up as the rain builds and down as it stops - there is no timer of this fork's own - and a dry frame is a byte-for-byte copy of the engine's target. Every draw of the frame that binds the same target object as the frame's first reader binds the copy for that one call and the game's own binding comes back afterwards; a replay of a game draw by another module is not served at all. Ground the engine itself renders dry (a roofed hall in rain) gets no pool from this stage: the pool weight is scaled by the engine's own gloss alpha at the texel against what exposed ground shows at the frame's wetness, over a soft band, and the log says once per change of state how much of the pool field that removed. The tone-map stage reads the same gloss (the engine's material pack of the same frame, at a sixth shader-resource slot) and applies the same function, so its darkening, mirror and rings leave ground the engine renders dry alone; with no material pack to read it draws no pool, and says why once. `PuddlesGlossTarget` = 2 carries no engine gloss, so it draws no pool in either stage.
At the frame's tone-map draw, before the tone map reads the scene, a second stage of the same card shades the pool itself. The draw is recognised without a shader CRC: `t0` is a single-sample view of the scene the frame's composite wrote, and the draw writes one other FP16 target. The five inputs it needs are measured once per frame at the deferred composite, which is the one draw that binds `g_SamplerViewPosition`: the frame's view-space positions, its G-buffer normal (`g_SamplerGBuffer4`), the camera table and the render target it writes. Inside the same noise field, at the same wetness - the frame's amount is copied for this stage whether or not the gloss stage's target and channel keys give it anything to shape - the stage darkens the pool's lit colour by `PuddlesDarkening` (`scene * (1 - mask * darkening)`) and adds a reflection of the scene marched from the frame's own view positions, with water's Fresnel (`F0 = 0.02`, Schlick: 2 % straight on, most of it at a grazing angle) and the key's strength. The mirror's normal is the floor's (the world's up) tilted by a static gradient of the same noise field, scaled by `PuddlesRipple`: static on purpose, because an animated perturbed direction is what a temporal upscaler turns into noise. The march is the screen-space reflections' own (`shaders/SceneMarch.hlsl`, one implementation for both), 24 taps by default (`PuddlesReflectionSteps`). A ray that leaves the picture or finds nothing adds nothing: the darkened scene already carries the engine's own probe reflection of that ground, so a miss is never black and never a hole. Outside the pool, on a wall, on a texel with no surface and on every texel outside the render window the scene's own bytes come back unchanged; a frame with no wetness is skipped before the copy, with one log line that says so.
One module owns that tone map. The light shafts add their air light at the same draw, so their branch is the owner: after their own pass has run and before they bind `t0`, they run this stage on their air-lit output, and what the tone map reads is the pool's colour over the shafts' light - the mirror reflects the air light too. The draw seam's own call to this stage is the fallback for a frame the shafts left alone, and it answers nothing for a tone map the chain already answered. While the engine's scene HDR path is on, that path replays its own tone chain in its own branch, so the fallback leaves the frame alone with one log line and counts nothing against the module; the shafts' branch never sees the draw at all.
The pool field is the one these defaults were measured at, with the shader's own noise ported to a host program: over one full 64-cell period of it, at the defaults (`PuddlesCoverage` 0.42, `PuddlesScale` 6.0 m, `PuddlesSoftness` 0.03), about a third of the up-facing ground is pool (32.9 %), and on a 60 m patch the blobs' median is 4.3 m across (the largest tenth 11.5 m) with a 0.81 m edge. `PuddlesReflection = false` is the darkening alone, which is the A/B a session needs to judge the pool's shape before the mirror, and the darkening at 0 with the reflection off is the stage's identity, so nothing is copied and nothing is drawn. The stage is before the upscaler and before the tone map: super resolution takes the pool as scene colour, ray reconstruction sees the flat floor under it, and frame generation interpolates finished frames. Nothing is remembered between frames, so the pass cannot ghost on its own - but the mirror is one sample of the scene per texel, with no edge fade and no jitter, so expect it to shimmer under NR/SR and to smear along the floor's motion vectors under frame generation.

The channel is measured from the engine's own shaders and from two G-buffer dumps of the same stone plaza: the gloss is the material pack's (target 1) alpha, which the composite remaps as `gloss = sat((a - 0.2) * 1.25)` and lerps the material's green towards. Its red is not a gloss but a selector the composite and the frame's wetness pass compare against 1.0 to choose the surface encoding, so the pair target 1 / `r` is refused: the pass binds the engine's own target unchanged and says so once in the log. Only the engine's 8-bit targets can be shaped: target 3 is a 16-bit target and target 4 is the world-space normal the up-facing test reads, so an ini value of either binds the engine's own target unchanged and says so once in the log. Target 3's blue channel is the engine's per-texel wetness and would be the faithful input, but the 8-bit copy this pass makes cannot answer a 16-bit target today.

A frame the pass cannot serve is skipped with one line in the log, with the slots and sizes that draw bound, and the skip does not count towards anything. Only a frame the pass cannot do the work for - an owned texture or a draw that could not run, a call that threw, a target of a format or size it cannot copy - counts, and sixty-four of those in a row switch the feature off for the session with one log line. A camera table that is not the layout the shaders read is refused, looked at again after five seconds, and does not count either; the check reads a copy taken on an earlier frame, without waiting for the GPU, so it never drains the pipeline inside one of the game's draws. The card's own switch is what arms the pass: the engine pass overrides' master is not needed, and that master neither starts nor stops the puddles.

**Cost.** Expected, not measured on a real card. The gloss stage: one copy of the G-buffer target (33.2 MB at 3840x2160), one full-screen triangle over the render window and, per reader draw, one slot read, one resource read, the swap and its restore. The tone stage: one small copy of the camera table, the render window's one-texel ring out of the scene (the draw writes every texel inside the window, so only the ring the tone map's filter reads is copied), and one full-screen triangle with a 24-tap march - about 690,000 pool texels times 24 taps is 16.6 M scattered reads a frame, which is expected to be 0.4 to 1.3 ms at 1080p, plus the ring, and the chained order adds no full copy of its own because the shafts' is the frame's. The pass reports its own GPU time (a timestamp pair read a run or two later, never waited for) and the run line prints it, so a session reads the figure instead of trusting the estimate. A draw-diagnostics capture additionally allocates a per-texel statistics target (33 MB) while it is armed, to report the pool's share of the frame and the march's hit share. The risky half of the look is the darkening at night: a night stone sits near 0.10 in linear terms, a full pool at 0.45 lands near 0.05, and a pool reads as a hole where the mirror misses.

**Status.** New; experimental; off by default. **Not tried in game: no session has seen the look**, and the GPU cost is unmeasured. ## Screen-space reflections (FFXIV, experimental)

**Origin.** Fork code. The engine writes its own planar reflection map for the water surfaces (`g_SamplerReflectionMap`, a `B8G8R8A8` texture at the picture's size, filled by its own water reflection chain at half the picture's resolution) and the water material samples it. This fork computes its own reflection from the game's view-position buffer and the scene the frame has already rendered, and binds it for the water draws only. Nothing of the game is written and no shader of the game is replaced; the draw is recognised by the reflected names, not by a CRC.

**What it does.** `[FFXIV] ScreenSpaceReflections` arms the pass. Once a frame, before the first water draw (a shader that samples `g_SamplerReflectionMap`, the engine's `g_SamplerVPosition` and `g_CameraParameter` and one of the two water anchors), the pass copies the render window's texels out of that draw's own render target, marches the view-position buffer along the mirrored direction about the water plane (48 taps by default, geometric, out to 100 m), refines the crossing to the surface's own texel and rejects a surface deeper behind the crossing than the thickness key, all inside the quadrant the engine's own producer fills. The reflecting surface is the water plane: the normal is the world's up turned into view space by the view matrix's own second column, not a depth or a G-buffer normal, because the captured water shaders declare neither. The result replaces the engine's texels where the march found something, and the engine's own texels stay everywhere else - including every texel whose ray leaves the picture - because the owned target starts as a copy of the engine's map. The confidence stays inside the pass and only scales the RGB blend; alpha is the engine's own byte in every texel. Every water draw of that frame binds this texture for its one call, and the game's own map is bound again afterwards.

The quadrant mapping is the ambient occlusion pass's own rule, fed this pass's three numbers (the map's size, the scene allocation's size and the render window), so the two passes cannot disagree about where a texel goes. Draws are recognised by names and by the stamp the module writes on each shader at creation, so nothing is looked up per draw and no table can lose a shader.

A water draw is left alone, with one log line the first time its reason appears, when nothing is bound under the reflection name or the texture is not the engine's map, when there is no single-sample scene target it can copy, no usable view-position buffer (or one at another allocation), no camera table or one smaller than the matrices, a render window of a few texels or one that does not fit its scene, a character-preview replay, an owned texture or a shader it could not create, or an exception. Sixty-four refused water draws in a row switch the module off for the session with one line, and its switch-off is its own: the engine pass overrides and the ambient occlusion pass keep their arming. A frame whose water draws use two different scene targets copies the first one and the second keeps the engine's map.

**Cost.** Expected, not measured on a real card: one partial copy of the render window out of the scene target (16.6 MB for a 1920x1080 window in FP16), one copy of the engine's map (8.3 MB), a 0.35 KB camera copy, one parameter write, one full-screen draw over the 960x540 quadrant and a timestamp pair read a run or two later. The march dominates - 518,400 texels at 48 steps is about 25 million iterations - so 0.2 to 0.6 ms on a mid-range GPU is the estimate and `ScreenSpaceReflectionsSteps` scales it linearly; the owned copy of the scene is an FP16 texture at the display allocation's size (63 MB at 4K), created once per size.

**Status.** New; experimental; off by default. Proven on a software adapter against a CPU reference of the same march (`ssr_warp`): the floor below a bright square on a wall shows the square's colour with a confidence of 0.998, the whole written region matches the reference to 0.0019 worst and 0.00041 mean per channel, a texel whose ray leaves the picture keeps the engine's own bytes, a floor with nothing above it keeps 1024 of 1024 region texels byte-exact, every texel outside the quadrant keeps all four of the engine's channels, no texel differs in alpha, and the same scene rolled 20 degrees matches its own reference and differs from the unrolled one. The parse of a water shader is checked on a compiled shader and on the effect compiler's `.T` suffix, a typeless map or scene is accepted as its typed sibling, and the run line's gate and the card's arming are covered (`ssr_rules`). The reader rows come from a captured frame: two water shader families, 11 and 27 draws, sampling the map at slots 8 and 4 of a 1920x1080 `B8G8R8A8` texture the engine's own chain writes at 960x540. **Never tried in a game, the visible effect is not verified**: the GPU cost, the look on real water (the engine's own map is half resolution and blurred, this one is a hard mirror ray) and whether the view-position buffer really is view space are unmeasured. A session checks a shore with water in view and the camera low over it, the key off, on, blend 0.5 and 16 steps at one camera, the card's passes and served water draws against the 38 map bindings a captured water frame makes, the log's GPU figure and no refusal line, calm water first, a bright reflection at blend 0 (the map is 8-bit with no exposure or tone map, so it may clip), the character preview (it must not show the main scene's reflection) and a scene-HDR session.

**Check.** Stand on a shore with water in view and the camera low over the surface, keep `[Log] LogToFile` on, and compare two screenshots at the same camera with the key off and on; a third with `ScreenSpaceReflectionsBlend = 0.5` mixes the two. `OptiScaler.log` writes the run line once the timestamp pair has landed (`Screen-space reflections: 1920x1080 at 48 steps, thickness 0.30 m, blend 1.00, fade 0.10, the pass ... ms on the GPU`), one line per session with the number of water draws a frame served, and a refusal line that names the reason and what the draw bound. The key arms the pass on its own: the draw seam is entered while any of the module's features wants a draw, so the engine pass overrides' master switch neither has to be on for the reflections nor switches them off when it is. With `[Log] LogToFile` on, a water draw the module passes on for the texture under its reflection slot writes the stamp the shader carries and the view it read there (`stamp 0x..., map slot N, read slot N, view ..., array ..., format ..., WxH, texture ...`), and `engine.txt` carries the same as `ssr last water draw:`, so a capture says which slot the module read instead of leaving it to be inferred. Every slot the module reads is looked up by the kind it binds (`diag::BindPointOf`), because the effect compiler writes a texture and its sampler under one name and writes the sampler first at a register of its own.

**Config.** `[FFXIV] ScreenSpaceReflections` (false), `ScreenSpaceReflectionsSteps` (48, 16 to 128), `ScreenSpaceReflectionsThickness` (0.3 m, 0.05 to 2), `ScreenSpaceReflectionsBlend` (0.5, 0 to 1; 0 runs nothing), `ScreenSpaceReflectionsFade` (0.15, 0 to 0.5). **Menu.** Card "Screen-space reflections (FFXIV)" (`ffxiv_screen_space_reflections`, FFXIV tab): the switch, the four tuning sliders and the state line. **Code and seams.** `ext/ffxiv/engine/` (`SsrRules.h` for the pure rules, `SsrPass.{h,cpp}` for the draw, `SsrApply.{h,cpp}` for the classification, the stamp, the per-frame memory and the swap, `SsrSwap.cpp` for the stamp and the guard, `shaders/Ssr.hlsl`, `SsrMenu.cpp` for the card). Mechanism and measurements: [notes/screen-space-reflections.md](notes/screen-space-reflections.md).

## God rays: volumetric (FFXIV, experimental)

**Origin.** Fork code, built on the engine's own measured state. The engine renders a cascade shadow atlas every frame (a plain `R16_TYPELESS` 2048x8192 plane its own mask-assembly draws sample as `R16_UNORM`), binds a per-cascade light-space matrix beside it, and runs its own fog post (`Fog_GU`) once a frame after the composite and before the tone map, with an analytic two-exponential density profile and a sky-consistent colour rule over `cFogParam` and `cExpHeightFogParam`. The march reads those - the atlas, the cascades, the fog state, the engine's sky texture and fog weight LUT - instead of inventing keys, and adds its beams to a copy of the scene through the same white-bounded addition the radial light shafts use.

**What it does.** `[FFXIV] GodraysVolumetric` is the last stage of the tone-map chain the light shafts own: the shafts (owner when on) hand their air-lit output to the puddles' tone stage, which hands the chain's output to this march; when neither earlier stage answered, the march is the fallback owner and makes its own scene copy. At a quarter (or half) of the render window it reconstructs each pixel's view ray through the engine's own inverse projection (a sky pixel has no surface: the ray is a direction, bounded by the atlas' reach) and marches `GodraysSteps` samples (48, 16 to 96) through the air in front of it. At each sample it reads the shadow from the engine's own cascade atlas the way the engine's own mask writer blends it: **every one of the four cascades, each only inside its own atlas slice** (the slice is read from the cascade's own matrix and fade row: the projected v of the middle of its distance band along the view axis, `floor(4 v)`), the compare being the writer's (`shadowed when the sample's depth is at or beyond the gathered texel`, plus a 0.002 bias an air sample needs and the writer's normal offset gives a surface; the disc taps and their depth correction scaled by the shared map row's own constant), the writer's own edge fades and distance ramp on the sample's view z, and the **minimum** over the cascades. The first version took the first cascade whose uv was inside the whole atlas, which handed far samples to the near cascade and its band fade said "lit": the beams the far cascades cast were hidden (on the 2026-11-06 frame the pick agreed with the engine's own sun mask on 77 % of surface pixels, the minimum over the slices on 94 %). The medium is the engine's own density profile `rho(y) = d1*exp(f1*(h1-y)*0.545968) + d2*exp(f2*(h2-y)*0.545968)` from the captured constants, normalised by the density at the camera's own height (`GodraysFogBoost` multiplies it, `GodraysHeightLift` scales the height falloffs) and boosted by `GodraysDensity` (20, in units of 0.001 per metre: the engine's own density is about 0.0009 per metre there, far too thin to make a beam visible, so the boost is an artistic constant), scattered with a Henyey-Greenstein lobe around the shadow light (`GodraysAnisotropy`, g 0.8: 10 % of the peak at 24.6 degrees; `GodraysPhaseBoost` narrows or widens it) and summed as an in-scatter integral with extinction, `S = sum sigma * phase * V * T * dt` - not the first version's average lit-air fraction under a `pow(cos, 16)` lobe, which removed 92 % of the term and carried no optical depth. The quarter-resolution term is upsampled depth-aware (a pixel keeps the term of its side of a depth edge), shaped to what stands above its own local level, `min(max(term - lowpass, 0) * 0.75 + 0.10 * term, 4)`, the low-pass being the mean of a 9 x 9 grid of march texels 48 window pixels per side (the unshadowed in-scatter is the engine's own fog post's, and adding all of it on top read as a haze: +3.95 % on the castle and +4.72 % on the sea of the 2026-11-06 coast frame, +0.47 % and +0.79 % now; the replay lab's no-shadow control through the same composite still lifts them +0.53 % and +0.91 %, so what is left is the kept share and the unshadowed integral's own silhouette structure, and the added light is a soft glow against the tree and castle silhouettes rather than a second fan of streaks next to the light shafts'), and added to a copy of the scene through the radial's own `ShaftAdded` bound against the frame's own white point (composite gain 0.7), with the tint from `GodraysColor`: `auto` is the radial's scan-and-sky rule (the light's own colour, else the sky's colour around the sun's screen position), `white` is a neutral beam, and `enginefog` is the engine's own fog colour rule - `max(0, LUT.y * (sky(pixelUV) - fogColor) + fogColor)` from the engine's own sky texture and weight LUT, secured at the fog post's draw. The sky is lit too (the air in front of it is where beams are seen), but each of its channels is capped at the scene's own sky 99th percentile: a compute pass samples every fourth pixel each way of the scene's sky pixels (the engine's `sSky` texture is not used: it does not correlate with the scene's sky), builds a 128-bin histogram per channel and writes 0.98 of the interpolated percentile; with fewer than 64 sky samples the sky is left alone. A sample the march cannot read is a shadowed sample, never a lit one: a broken atlas takes beams away instead of filling the frame with glow.

**Which light, and the limits.** The march's light is the **shadow light**: the frame's first sun-shaped light draw (the main view's directional light), accepted only when its direction agrees with the finest cascade's axis (`-normalize` of its matrix's third row) to 3 degrees, and the phase is centred on that axis. It is the light the atlas was cast along and nothing else, which on the one daylight frame measured (2026-11-06, a low sun over the coast) sits 15 degrees above the visible disc, at the same azimuth: **the beams converge on the shadow light's vanishing point, not on the disc** (the atlas has no shadow of the disc's own direction). Two gates say when there are no beams: the light's luminance gain (0 at a luminance of 0.05, 1 at 0.6, a smoothstep: a moon-like light never runs at sun strength; the dim blue light of the evening frames is 0.26 and 0.11) and the aside gate (the nearest pixel ray to the light farther than 72.5 degrees: a light behind or beside the camera casts none; the daylight frame's nearest ray is 8 degrees, the evening frame with the light behind the camera 118). The range is the atlas' (150 to 190 metres), and the frame's beams are as noisy as a quarter-resolution, hash-jittered march is: the jitter is screen-locked and may crawl when the camera moves (an in-game check, not one a single frame can show).

The captures are the shafts' own machinery, the march's own instances: the light and camera at the frame's sun draw (the same draws the radial captures; the march instantiates its own readers, so it works with the radial off), the fog constants, the uv mapping row, the frame's depth and the sky/LUT views at the engine's fog post (recognised by `cFogParam` and the absence of the material family's `g_FogParameter`), and the four per-cascade shadow parameter instances pointer-keyed per frame at the assembly draws (they declare `g_LightParam`, so they arrive as light draws). The atlas, the sky and the LUT are secured once: an own SRV on the game's resource after its description is checked for the shader-resource bind flag, else an owned copy. The reads land through rings of staging copies one or more frames late, never waiting for the GPU; the last accepted state (the light, the fog constants and the cascades ride one accept) is held for at most six frames with the radial's own fade weights, and a camera cut drops it.

A frame the march cannot measure is left exactly as the chain left it: a chained decline leaves the chain's last good picture at t0 (the hold stands - the march does not fall through to the engine's texel and does not bind an unlit scene), and an owner decline leaves the game's own binding. The march's decline paths never touch the chain's shared state - the composite's capture stamp is the puddle stage's own file-local state - and the march's own answered-tracking is its own rendered-frame counter. Skips (no atlas, no fog state, no shadow light yet) are not refusals; a camera buffer that is not this build's camera is, and sixty-four counted refusals in a row switch the march off for the session with one line. It is inactive while the engine's scene HDR is on, and it refuses a character-preview replay of a game draw.

**Cost.** Expected, not measured on a real card: at quarter res and 48 steps about 6.2 M atlas taps a frame at 1080p (four cascades, most of them rejected by the slice test before a tap), the stats pass (one group of 256 threads over about 130 thousand sky samples and the term, a 32-byte copy to the staging ring), plus one copy of the scene allocation per frame when the march owns the draw (the chained case adds one more copy after an earlier stage's), one quarter-res R16F target (0.2 MB at 480x270) and a timestamp pair read a run or two later, never waited for. `GodraysSteps`, `GodraysResolution` and `GodraysShadowSoftness` scale the taps linearly.

**Status.** Second version (the first was measured on the 2026-11-06 session's frames: it added about 0.6 % of the frame's white on the daylight frame, a smooth haze with no stripes). Experimental; off by default. **Measured in the replay lab on the 2026-11-06 frames** (the pass on the game's own inputs; the fog table of the evening frame's dump stands in for the three frames whose dumps lack one): on the daylight frame the light added inside the 30-degree cone around the shadow light is 2.3 % of the frame's white (the first version: 1.8 %), the ring structure around the light is 0.74 against 0.20 for the same pass with every shadow texel lit (the first version: 0.46), the lift outside the cone is 1.4 %, and no sky pixel passes the scene's own sky 99th percentile. The quarter-resolution term correlates 0.999 with the numpy prototype's; the full-resolution light correlates 0.99 with the plain bilinear upsample and 0.92 with the depth-aware one, which keeps a pixel's term on its own side of a depth edge on purpose. The evening frame whose nearest pixel ray is 66 degrees from the light, the frame with the light behind the camera and the indoor frame add nothing (5e-9, 3e-5 % and exactly 0 of the frame's white). The lab runs the pass without the draw path, so no gate acted in those runs: the 66-degree frame is inside the aside gate's 72.5 degrees (it would run, at the luminance gain's 0.33) and is dark because the phase lobe keeps under 1 % of its peak there; the behind frame's gate is covered by the host rules; the indoor frame is shadowed everywhere in the atlas. With the lobe centred on the visible disc instead of the shadow light (a lab run, not a key), the light added over the daylight frame is 1.9 % of its white instead of 1.0 %, the ring structure around the disc 0.60 instead of 0.74 and the lift outside the cone about the same; the default stays on the shadow light because the shadows and the scattering must be the same light, and the beams' vanishing point is the shadow light's. What this leaves open: if the brightest part of the glow looks displaced from the disc in game (15 degrees on that frame), the disc's direction is already read (`cFogParam[2]`) and a phase-centre key is a small change. GPU time on the RTX 4090 at 1920x1080, a single lab run each: 0.76 ms for the whole pass on the daylight frame (the one that marches; a second run of the same process, bit-identical output; the first run of a fresh process measured 91 ms, a cold start) and 0.71 to 0.72 ms on the others, against 0.42 ms for the first version. **Not tried in game: no session has seen the look.** The rules are covered on the host (`godrays_march_rules`: the Henyey-Greenstein lobe, the in-scatter integral against its closed discrete form with extinction through shadow, the cascade slice on all sixteen matrices of the four 2026-11-06 frames, the sky ceiling's histogram, the light gates against the nearest-ray angles of the four frames, the cascade axis to 0.05 degrees, the stage values string; `godrays_rules` for the earlier ones), the march and the composite against a CPU reference on a software adapter (`godrays_warp`: the term per pixel at three softness settings, each rule seen by a fixture that separates it from its broken form - first cascade wins, no slice test, no bias, no extinction, the cos^16 lobe - the sectors fixture's ring structure, the bilateral edge, the sky ceiling with and without the cap, the stats read-back, the graphics and compute state restored) and the wiring by text pins (`godrays_pins`).

**Check.** Set `[FFXIV] GodraysVolumetric = true` with the sun low behind trees or a roof edge, keep `[Log] LogToFile` on, and compare two screenshots at one camera, off against on; `GodraysColor = enginefog` is the second pair (the beams take the game's own fog colour), `GodraysShadowSoftness = 2` the third (the banding knob). `OptiScaler.log` writes the secured views once per session (`God rays: the cascade shadow atlas secured as an own view on the game's resource (2048x8192, format 56)`), the run line once per window size (`God rays: the march ran at 480x270 of the 1920x1080 window, direction (...), fade 1.00, white 0.838, ...`), one line per change of reason for a frame left alone - `God rays: the march declined (the pass could not build its textures, shaders or draws), so the chain's hold stands` when chained and `... so the frame is the engine's own` when the march owned the draw - the card's counts line about once a minute of rendered frames, and the cost line with the measured GPU figure once the timestamp pair has landed.

**Config.** `[FFXIV] GodraysVolumetric` (false), `GodraysSteps` (48, 16 to 96), `GodraysResolution` (`quarter` or `half`), `GodraysFogBoost` (1.0, 0 to 2; a multiplier on the density the engine's profile gives), `GodraysHeightLift` (1.0, 0 to 2; 1.0 is the engine's own height falloff), `GodraysIntensity` (1.0, 0 to 2; 0 runs nothing), `GodraysColor` (`auto`, `white` or `enginefog`), `GodraysShadowSoftness` (0, 0 to 2 taps), `GodraysJitter` (true), `GodraysPhaseBoost` (1.0, 0 to 2; 1.0 is neutral: it divides the lobe's narrowness 1 - g), `GodraysDensity` (20, 0 to 200, units of 0.001 per metre) and `GodraysAnisotropy` (0.8, 0 to 0.95, the Henyey-Greenstein g). **Menu.** Card "God rays: volumetric (FFXIV)" (`ffxiv_godrays`, FFXIV tab, with the other engine pass cards): the switch, seven sliders, two combos, the jitter switch and a state line with the skip decomposition. **Code and seams.** `ext/ffxiv/engine/` (`GodraysRules.h` for the pure rules, `GodraysPass.{h,cpp}` and `shaders/Godrays.hlsl` for the three draws and the stats dispatch, `GodraysDraw.cpp` for the draw path and the chain, `GodraysSun.{h,cpp}` for the captures, `FogSun.h` for the fog sun the night curve reads, `ChainHooks.h` for the chain's stage hooks, `Godrays.h`, `GodraysMenu.cpp` for the card). The stats dispatch is the one place the module touches the compute stage; it saves and restores its own compute state (the explicit-state guard does not cover that stage).

The read needs neither the height profile nor a usable march state, so it works on the frames the profile is refused (`the buffer at cb2 is not a height profile`). With shadow mapping off, nothing is asked and the draw path costs what it did.

## Light bounce (FFXIV, experimental)

**Origin.** Fork code, built on the engine's own measured state. The engine's deferred composite reads a G-buffer (world normals and a material byte, the material pack, an albedo carrier that it squares on read) and a per-pixel view-position buffer, composes in a squared-light domain and writes the square root of the sum; the engine's tone map squares the scene back on read. That makes the finished scene's stored texel, squared, the linear radiance a surface sends toward the camera, and equally toward any other surface that sees it.

**What it does.** `[FFXIV] Gi` is a stage on the tone-map chain, right behind the volumetric march: it answers when the march answered (it composes on the march's picture), when the march declined, and when the march is off, which is its default. At half (or a quarter) of the render window, K cosine-distributed rays leave every pixel along the G-buffer normal, rotated per pixel by a fixed hash (no frame number, no history; the upscaler's temporal accumulation is the denoiser). Each ray steps on a quadratic ramp up to a range key through the engine's own view-position buffer; a hit is a ray point behind the visible surface at its texel, measured along the camera's own line, by more than a small bias that grows with the surface's distance and by no more than a fixed thickness, so a flat surface cannot light itself. A hit sends back its own linear scene value, the scene's stored texel squared per channel, with the surface's own colour left in (a warm floor sends warm light, a dark one little, a lamp its own light; a value over 8 is refused). A ray that finds no hit adds zero. The hits' sum is scaled by the cosine pdf (pi over the rays asked for, not over the rays that hit), by the pixel's own camera-facing cosine and by 1/pi (the Lambertian normalisation: a surface under a uniform environment reflects it whole). The irradiance store marks every origin the pass traced, whether or not a ray hit it, and a traced texel with no hit is a valid zero; the smooth is a dense 5x5 binomial stencil (the 1-4-6-4-1 outer product, 25 taps on exact integer positions) that averages every traced texel, zeros included, and skips only the origins that could not be traced (the sky, a texel with no view position or no usable normal). The result is multiplied by the pixel's own albedo square and its material pack's diffuse weight, and added in the engine's squared-light domain (the stored value becomes the square root of the scene square plus the light) through the same white-bounded addition the light shafts use: no key pushes a channel past the frame's white point. The engine's special material rows (the character shaders' band) and its special-colour class get nothing in this first version. The game's textures are only read; the stage draws into its own scene copy and binds it at the tone map's `t0` for the one draw, putting the game's own binding back afterwards.

A frame the stage cannot measure is left exactly as the chain left it, with one log line for the reason: a chained decline leaves the chain's last good picture at `t0`, and a fallback-owner decline leaves the game's own binding. It is inactive while the engine's scene HDR path is on, refuses a character-preview replay of a game draw, and stands down for the session after 64 counted declines in a row.

**Night and the leak.** The faithful alternative source, the diffuse light buffer multiplied by the albedo, is zero on about four fifths of the texels of a night frame, so it would bias the bounce toward black; the scene-reading form used here covers the whole frame. What a hit sends back is the finished scene's value, so it carries the specular and emissive terms along with the diffuse light and the pass cannot separate them (measured at about 1% of the direct radiance on the kept frames, 2 to 3% at the 99th percentile); the engine's special-colour pixels (about 6% of a frame) are excluded as origins, but their light can still be read as a hit. A lamp bounces its own light, which is physically right, and the clamp keeps it bounded: on the four 11/05 captures a hit is refused for being over 8 linear in 0.0013% of surface pixels (the day exterior), none of the two night frames and 0.07% of the inn's, where the lamps are.

**First version, and what the replay showed.** The first version divided each hit's squared scene value by the albedo carrier's square, which read every hit as a white reflector (2x to 5x too bright indoors, the colour pushed toward the neutral light), and it skipped the traced texels whose rays all missed, which carried a lone hit at full strength over its whole 5x5 neighbourhood. Replayed on the four 11/05 captures on the RTX 4090 at strength 0.5, it added 19% to the inn's stored luminance on average (76% at the 95th percentile of surface pixels, a whole-frame ratio of 1.10), leaning blue in a warm room (a developer harness that runs the pass on dumped frames; it is not part of the repository). Both are fixed, and the default strength was re-picked from the same replay: at 0.55 the inn's whole-frame stored luminance ratio is 1.014 (the added light is 2.8% of the scene on average and 15% at the 95th percentile of surface pixels), the two night frames 1.010 (15% at the 95th percentile), and the day exterior 1.001. The added light is warmer than the room (the bounce of warm surfaces is warm), not bluer.

**Status.** New; experimental; off by default. **The first game run (2026-11-06) showed a diamond lattice and a grey-blue veil; the lattice was fixed in the smooth and the veil in the radiance and the data marker above, and the new look is checked on a replay of the captures, not yet in game.** The GPU cost on the replay is about 0.4 ms at 1920x1080 on the RTX 4090. The rules, the shaders (against a CPU reference march on a synthetic scene on the software adapter, lamp and clamp included) and the wiring are covered by tests. The bias share, the thickness and the strength default are provisional until a capture session.

**Check.** Set `[FFXIV] Gi = true`, keep `[Log] LogToFile` on, and look where geometry meets under bright light: the bounce reads as colour carried onto a wall no direct light reaches. The card's state line counts runs, declines and the three skip reasons; the log says why a frame was left alone.

**Config.** `[FFXIV] Gi` (false), `GiRays` (4, 1 to 8), `GiSteps` (16, 8 to 32), `GiRange` (5.0 m, 1 to 20), `GiStrength` (0.55, 0 to 1; 0 runs nothing, 1 is the full diffuse bounce) and `GiResolution` (`half` or `quarter`). **Menu.** Card "Light bounce (FFXIV)" (`ffxiv_gi`, FFXIV tab, after the god rays card): the switch, four sliders, one combo and a state line. **Code and seams.** `ext/ffxiv/engine/` (`GiRules.h` for the pure rules, `GiPass.{h,cpp}` and `shaders/Gi.hlsl` with its own `shaders/GiMarch.hlsl` for the three draws, `GiDraw.cpp` for the captures and the chain entries, `ChainHooks.h` for the two hooks `chainGiScene` and `toneMapGiOwner`, `Gi.h`, `GiMenu.cpp` for the card). It shares the engine pass module's draw seam and feature bit (bit 20), adds one composite-shader stamp, one call in the draw path and one card, and no upstream line. The stage hangs inside the volumetric march's own chain entries, so it is reached with the march off; a stage that follows it takes the hook's texture first and the owner hook second.

## Depth of field (FFXIV, experimental)

**Origin.** Fork code. The game ships its own depth-of-field family (a weight and circle-of-confusion pack, a quarter-size downscale, a near blur, a far blur and a merge, then the tone map right after it) and runs it on the benchmark client; a live play session was never seen running it, so this stage does not shape the game's own chain. It is the fork's own blur, chained at the tone map.

**What it does.** `[FFXIV] DepthOfField` is the last stage of the tone-map chain (shafts, puddles, volumetric march, light bounce, depth of field, then the game's own draw). It makes its own copy of the scene it is handed and runs three draws on it. The pack, at the render window, keeps the scene colour capped at 10 (the game's own weight shader does the same) and writes a signed circle of confusion into the alpha: `(focus - z) / (z + focus)` from the pixel's view depth, positive in front of the focus plane, negative behind it, zero on it, shaped before it is written. A **focus band** (a raw circle of 0.12 or less, which is about 0.79 to 1.27 times the focus distance) is exactly zero, so it stays sharp. Above the band the magnitude is remapped linearly, `(|c| - 0.12) / (1 - 0.12)`, so the blur starts from nothing at the band's edge (the far blur is a little weaker in the middle of its range than the raw circle: 55 % less at a raw 0.2, 32 % at 0.3, 14 % at 0.5, none at 1). The **near side** (toward the camera) is capped at 0.25 of the full circle, and the far side is not capped. The blur, at a quarter of the window, gathers a golden-angle disc of `DofSteps` taps and keeps the near side and the far side apart, each tap weighted by its own defocus. The merge mixes the near or the far blur over the scene by the pixel's own circle of confusion times `DofStrength`; outside the render window the copy is the scene byte for byte, and the game's textures are only read. The focus is the view depth under the screen centre by default (`auto`), or `DofFocusDistance` metres (`manual`). The view depth comes from the engine's own depth through the camera's inverse projection, and a camera whose derived near and far planes are outside what the engine can produce is refused.

A frame the stage cannot measure is left exactly as the chain left it, with one log line for the reason: a chained decline leaves the chain's last good picture at `t0`, and a fallback-owner decline leaves the game's own binding for the caller to draw once. It is inactive while the engine's scene HDR path is on, refuses a character-preview replay of a game draw, and stands down for the session after 64 counted declines in a row.

**The two looks (`DofMode`).** `distance` is the gameplay look and the default; `cinematic` is the first release's look, kept exactly as it was (its output on the four rc6 captures is bit-identical to rc6's in the replay lab). The distance look blurs the far side only: nothing nearer than the *start* distance is touched, the start being the larger of twice the focus distance and 20 m (a character at 8 m gives 20 m); beyond it the circle of confusion follows the thin lens, `(1 - start/z) / (1 - start/far)`, which is 0 at the start, grows quickly and saturates at 1 at the far limit, eight times the start (160 m for a character at 8 m). The blur radius at the full circle is 0.75 % of the window height (8 px at 1080p), and the merge mixes at most 25 % of the blurred picture (`DofStrength` 1.0; the default 0.8 mixes 20 %): the blur runs at a quarter of the window, so a tile keeps about (1 - mix) squared of its detail, which leaves the far background visibly softer and not destroyed. The near side never blurs. The auto focus is smoothed in time on the GPU (a one-texel state, no readback): each run takes a cross of five depth taps around the window's centre (1.5 % of the window height apart), drops the taps that read no depth (the sky), takes the lower median of the rest and moves the focus toward it exponentially in seconds (time constant 0.4 s; 1.6 s for a sample more than three times the focus, a glance past the character; a run after a gap of one second or more adopts the sample whole). `DofAperture` applies to the cinematic look only.

**The game's own depth of field.** The game's classic depth-of-field chain (the weight pass, the downscale, the blurs and the merge) writes its result back into the scene texture the tone map reads, so this stage would blur an already blurred picture (on the benchmark's cutscenes the two together took the high frequencies to x0.32 to x0.70). The weight pass is recognised by its reflected names (a pixel shader that declares `cWeightSamplingParam` and reads an `sInput`; the 256x1 CoC LUT update declares the buffer alone and never counts) and by drawing to a scene-sized target; a frame it drew in is left to the engine in both looks (a log line once per state, `Depth of field: the draw was left alone ... (the engine's own depth of field drew in this frame)`; not counted toward the stand-down).

**Capture numbers.** On the capture frame the `# stage 10 dof` line of the draw diagnostic's dump carries `mode=`, `focusM=` (the focus the frame used, read from the one-texel state by a single staging copy made on the capture frame only), `centreM=` (the raw sample), `start=`, `farM=`, `maxPx=` (the radius at the full circle in pixels), `engineDof=`, and `white=` / `fade=` (depth of field has no white point of its own: it names the one an earlier stage of the chain noted this frame, `n/a` when none ran). Stages 06 and 09 carry `white=` and `fade=` (stage 06 also `sunPx=` and `tint=`) the same way. The dump also writes the fog post's scene depth as `depth.bin` (cropped to the draw's window, with a `# depth-image` line), always keeps the fog weight LUT and the sky next to the scene, and says `# skipped <name>.bin: over the dump's places` when its twenty-four engine places are full (the stage images have places of their own and no longer use them up).

**Known limit.** The auto focus is the view depth under the centre of the window (a median of five taps): with the camera looking at a far subject (a focus at 100 m) the start moves out to 200 m and nothing nearer is blurred, by design. The camera's own distance to the player (the third-person zoom, `Client::Game::Camera` +0x124) would be the ideal focus; the fork's resolver does not resolve it offline for the installed build, so it is not used.

**Status.** Experimental; off by default. ## Developer draw diagnostic

**Origin.** Fork code.

**What it does.** `[FFXIV] DrawDiagnostics = capture` (ini only) writes what the game asks the GPU to draw, for the first few complete frames of the session, to `OptiScaler\draw-diag\<run>\` next to the DLL (the eight newest runs are kept):

- `draws.csv` (format 3), one row per draw in draw order: ordinal, draw call, whether the draw came from the game's own context, the vertex/index counts, the pixel shader's bytecode CRC32 and its stage in the frame (tone map, the post stages, UI), the reflected names and slots of the textures and constant buffers that shader binds, every render target's format and size, the depth view, the viewport, the blend state and the depth state. Every texture, target and depth entry ends with the resource pointer in lowercase hex, and every constant-buffer entry with the buffer pointer, so a target and the draws that read it can be joined without a symbol table. One `#` comment line closes each frame with the ordinals of the tone-map draw when it was seen, the first UI draw and the upscale boundary when it was seen (`upscale_after` = the draw it followed).
- `cb.csv`, the sun position, direction and diffuse colour of the `g_LightParam` constant buffer of the lighting passes (fixed offsets 0x00, 0x10 and 0x20) and the view matrix of the `g_CameraParameter` buffer of the same draw (offset 0x00, sixteen columns), read back at most once a second while the diagnostic is armed. The pair is what tells the space of the sun direction apart: a direction in world space stays the same while the view matrix turns.
- `cbdump.csv`, one row per (sample, named buffer) while a capture runs: frame, time, shader, the buffer's reflected name, slot, size, pointer and the first 16 KiB of its bytes in hex. The list is the wetness parameter, the ambient array, the directional shadow and reflection parameters, the camera table, the engine's flare family (`cHaloParam`, `cSunParam`, `cRadialBlurParam`) and the glare, tone-map, fog and filter buffers; each is read at most once a second, and only while a capture collects. This is what turns the flat float arrays of the post passes into a usable offset map.
- `views.txt`, the SRV description of the four identifying textures - `g_SamplerReflectionArray`, `g_SamplerReflectionMap`, `g_SamplerHierarchicalZ` and `g_SamplerShadow` - written at the first draw of the capture that binds each: the view dimension, mip count, format, array size or cube count, and the size, array size, mip count and format of the texture behind it. That tells a real reflection array from a 1x1 dummy.
- `engine.txt`, the engine pass overrides module's counters as they stood when the capture was written; its `sun:` line carries the diagnostic's own projection of the frame's sun - the light pass's direction through the same draw's camera - and whether it was in the window, with the light shafts card off as well, so a reader knows whether a capture could show the engine's flare.
- Every file ends with a `# rows` trailer (`draws.csv`: `# rows <n> frames <m> omitted <k>`) and the log line at the end of the capture prints the same numbers, so a copy that was cut off is caught by its reader instead of being read as a short capture.

The reflected names are the engine's own (`g_SamplerOcclusion`, `g_SamplerShadowMask`, `g_LightParam`, `g_AmbientParamArray`, ...), read from the bytecode the game hands to `CreatePixelShader`, so a draw is described by what it reads instead of by a fingerprint alone. Frames with fewer than 32 draws (loading screens, the title) are not counted, so `DrawDiagnosticsFrames` counts rendered frames. Any other value than `capture` reads as `off`, which is today's behaviour.

The captured window is one game frame: the tone map runs exactly once per frame, so a window runs from just after one tone map to just after the next, and the tone map that closes a window is the boundary of the next one. The first tone map also drops the partial frame the capture started in, so the first window is a whole frame. A session that has the DX11-on-DX12 bridge still closes a frame at its Present as well; the rows after a Present are a whole frame already, so its next tone map only arms the window.

Nothing in the frame changes: the diagnostic binds nothing, draws nothing, writes no game resource and restores nothing, because it only reads D3D11 state. The GPU work it adds is one staging copy and one map of two constant buffers (and of the named `cbdump.csv` buffers) per second while it is armed, and the files are written once, at the end of the capture, from the render thread. With the key off the draw hook pays one relaxed atomic load per draw.

Two keys decide when a capture starts, because the opening frames of a session are the loading ones: `DrawDiagnosticsDelaySeconds` waits that many seconds after the game starts, and `DrawDiagnosticsKey` waits for a key press instead (a letter, a digit or F1 to F24, read only while the diagnostic is armed; the key wins when both are set). Either way the capture lands on a frame the player chose, which is where particles, effects and the character are actually drawn; while it waits, the constant buffers are still sampled once a second, so a delayed capture also carries a series of sun and camera samples. A key-started capture re-arms after it is written: the key has to be released first, so the press that started one capture does not start the next, and a session starts at most eight captures, each in its own folder (the run id with the capture index appended when two land in the same second). That is what makes one in-game session answer several questions - rain, then dry after a zone change, then an interior - without a restart. The no-key path still writes one capture and then stops.

`[FFXIV] DrawDiagnosticsDump = frame` (ini only, off by default) writes the targets of one captured frame to `OptiScaler\draw-diag\<run>\dump\`: the wetness pass target, the five G-buffer targets, the two light buffers, the target of the hierarchical-Z (screen-space reflection) draw, the scene the tone map reads, the view-position buffer the water and composite draws sample, the tone map's target and the post-tone-map FP16 copy. Each is a raw `.bin` named after what it is, with a line in `facts.txt` carrying the format, size, bytes, the readback's row pitch, the draw that identified the resource and its pointer; a texture the dump cannot take (multisampled, a format it cannot write, over the bound, displaced by a higher-priority texture) says so once in the same file, and so does a G-buffer target no draw sampled. The readbacks are staged after the draw that identified a resource, never at it, because the hook runs before the draw; the five G-buffer targets wait one step longer, for the first later draw that samples one of them, because their pass is not over when the five-target draw returns. "Later" is the capture's own draw counter, which a frame close does not restart, so a target identified at a window's last draw is still copied in the next one. At most 24 files and 256 MiB are taken (`[FFXIV] DrawDiagnosticsDumpBudgetMiB`; a 4K frame's whole set is about 514 MiB with the view position (451 MiB without it, about 546 MiB when the SSR target is written too), so a session that wants all of it sets 1024), and the bound is enforced when a texture is identified as well, so the staging copies stay inside it: a texture that does not fit releases the holds of a lower priority (the G-buffer, then the light buffers, the SSR target and the rest), so the wetness target is never displaced by one that was merely identified first, and only a set of equal or higher priorities refuses it. The dump is written once the frame that identified its tone map is over, with the game's context: a later frame ended, or that frame itself ended at a bridge Present, so a two-frame capture in a session with a bridge writes its dump at the Present that closes the second frame. It needs a capture of at least two frames. A key-started session writes up to four dumps, one per capture (`DrawDiagnosticsKey`), each into its own run folder; each dump is bounded by the byte budget on its own, so mind the disk.


**Per-stage pictures (stage A/B).** The same `DrawDiagnosticsDump = frame` capture (the F9 press) also writes, for that frame only, what every stage of this fork did to it, so the effects can be judged on the frame the player saw instead of by flipping ten of them by eye. For each stage that makes a picture there are two files next to the dump's others: `stage-<NN>-<name>-in.bin`, the picture the stage received, and `stage-<NN>-<name>-out.bin`, the picture it produced, each cropped to the stage's render window in the texture's own format and listed in `facts.txt` with the same seven columns as every other file, followed by one comment line (`# stage-image ...`) with the stage, the port, the format the stage sampled it in (a mask is a typeless texture read through a typed view), the window and the box that was copied. The numbers follow the stages in the order of the frame: 01 contact shadows (the engine's sun mask and the copy the light draw sampled instead), 02 shadow-mapping lift (the same pair on its own route; when contact shadows is serving, the lift rides on its combine and the line says so), 03 ambient occlusion (the engine's texture and this pass's), 04 puddles' gloss (G-buffer 1 and its rewritten copy), 05 screen-space reflections (the engine's planar map and this pass's), then the tone-map chain in the order its stages hand the picture on: 06 light shafts, 07 the puddles' tone stage, 08 the god-rays march, 09 the light bounce and 10 depth of field, and 11 the lens-flare card, which patches the engine's own constants and makes no picture (status only). A stage whose input is the stage before's output has no second file: the comment line says `same_as=` the file it is again, and the chain's first stage carries the chain's input. Every stage, whether or not it ran, has one line in `facts.txt`: `# stage 06 shafts: ran | frame position 5123 | images in+out | values ...`, or `declined: <its own reason>`, `held` (the puddles' tone stage binding its last whole answer, an earlier frame's picture), `combined`, `not armed`, or `not reached this frame`. A later "answered already" never overwrites a run, and the first run of the frame is the one that is shown. The copies are made after a stage's pass has returned and its own guards are gone, with one `CopySubresourceRegion` into the dump's staging (no pipeline state is set and nothing is drawn), and before the stage after it is handed the answer, so no stage renders differently; with no capture open each stage pays one relaxed load. There is no new key: the pictures ride on `DrawDiagnosticsDump = frame` and its byte budget, they take the tone map's rank (the atlas, the sun mask, the water files, the material table and the fog post's two textures give their places away to them, the engine's own targets do not), and they have places of their own beside the dump's 24. A picture that does not fit is skipped with a `# skipped` line and the log says how much the frame's pictures want in all, so set `DrawDiagnosticsDumpBudgetMiB` to that. Measured on the four captures of 2026-11-05 (a 3840x2160 window, an FP16 scene): the pictures of every stage with its key on are about 506 MiB - the six FP16 pictures of the tone-map chain (its input and five outputs) are 63 MiB each, the G-buffer 1 pair 63 MiB, the sun-mask pair and the lift pair 16 MiB each, the half-size occlusion and planar-map pairs 16 MiB each - on top of the dump's own 566 to 645 MiB, so one press that keeps everything needs a budget of 2048 (1024 holds all of it but the last picture or two). They scale with the window's pixel count: about 127 MiB on top of about 160 MiB at 1920x1080, where 512 holds everything. `tools/diag/stage_ab.py <capture folder>` turns them into a PNG triptych per stage (input | output | amplified change) and a `stage-ab.json` with the status line and, per stage, the mean and 95th-percentile absolute change, the share of pixels changed by more than 1/255 and 4/255, the luminance ratio out/in (the veil), the high-frequency energy ratio out/in (the blur) and the local deviation of the change over the input's flat 16x16 tiles (the blotch).

`[FFXIV] DrawDiagnosticsDump = ssr-pair` selects a separate SSR module pair capture. With DrawDiagnostics armed (including its F8/key capture), it stages inputs before the SSR pass and the pass output after dispatch for two adjacent successful SSR executions. It records the actual scene, view-position, planar source, camera buffer and result at each module run, with frame token, run counter, dimensions, format and row bytes in `manifest.csv`. Native row-packed bytes are written as `.raw` files under `OptiScaler\PreviewDebug\SsrFramePair\<run>\`; staging drains on ordinary draw callbacks after the draw-row capture completes. The pair has a shared 128 MiB staging cap; unsupported, multisampled or oversized resources are reported in the log. The existing `frame` value keeps the one-frame dump behavior.
**Status.** New; unit-tested (the file formats, the marker ordering rule, the frame split, the reflection reader on a shader compiled in the test, and wiring pins). Ran on the official FFXIV benchmark client: one run with frame generation on wrote a capture (three frames); one run without frame generation wrote none before the tone-map split was added. Ran in a played session on 2026-10-31, seven captures in one launch from the key: format 3 with its pointer columns, `cbdump.csv`, `views.txt` (the reflection array turned out to be a real five-cube array, 256x256 with 8 mips, not a 1x1 dummy), the re-arm and every capture's `# rows` trailer all behaved as described, and the one-frame dump worked at 3840x2160 - seven textures (the wetness target, the five G-buffer targets and the diffuse light buffer, 240 MB), then the 256 MiB bound, so the specular light, scene, tone-map and copy textures were skipped with a line each; the readers in `tools/diag/` then answered the session's checklist from the copied folders. The run folder naming, the caps and the `#` comment rows follow the existing developer probes. Limits: at 4K the bound is too small for the whole set of targets (making it a key is the next step), and the dump's G-buffer and wetness shapes are measured shapes, so a build with a different one takes nothing for those files and says so only by their absence.

**Config.** `[FFXIV] DrawDiagnostics` (`off` | `capture`, ini only, default `off`), `[FFXIV] DrawDiagnosticsFrames` (how many complete frames one capture writes, 1 to 16, default 3, ini only), `[FFXIV] DrawDiagnosticsDelaySeconds` (seconds after the game starts before the capture begins, 0 to 3600, default 0 = the first draw), `[FFXIV] DrawDiagnosticsKey` (a key that starts the capture instead of the delay, default `off`) and `[FFXIV] DrawDiagnosticsDump` (`off` | `frame`, default `off`). All are read once at start: the shader reflection is recorded when the game creates its shaders, so a capture has to be armed before that. **Menu.** None (developer key, listed in `kIniOnlyKeys`).

**Reading a capture.** `tools/diag/` holds the readers for the capture files and needs only Python 3.14 with numpy: `drawdiag.py` (the loader and the format notes), `cbdump_report.py` (the sampled constant buffers, member by member and over time, with the ambient probe table and the wetness buffer's pointer question), `dump_to_png.py` (the one-frame texture dump as PNG previews and raw float arrays), `session_answers.py` (a fixed list of questions answered from a set of captures, written as `session-answers.md`) and `selftest.py`. `tools/diag/README.md` has the one-session workflow.

**Code and seams.** `ext/ffxiv/diag/` (`DrawDiag.h` for the hook side, `FfxivDrawDiag.cpp` for the state reads, the reflection table and the files, `DrawDiagFormat.h` and `ShaderBindings.h` for the pure parts). It hangs on the existing FFXIV draw hooks (`ext/ffxiv/lighting/FfxivLightingCapture.h`: `Around()` and `CreateShader`), on the upscaler evaluate seam (`ext/Seams.cpp`) and on the Present entry of the UI boundary detector (`ext/ffxiv/ui/FfxivUiBoundary.cpp`). Upstream lines: none. The column-by-column reference of the files is [notes/draw-diagnostic-format-3.md](notes/draw-diagnostic-format-3.md).

## What runs with every key at its default

Some of this release's additions run with no key at all. None of them was measured against v0.4.0 end to end: the figures are the authors' microbenchmarks and code reading, and there is no A/B at defaults.

- **`PSSetShader` hook** (FFXIV): the lighting provider attaches one Detours hook on `ID3D11DeviceContext::PSSetShader` whether contact shadows are on or not. 1.0 ns a bind, about 0.007 ms a frame at 6,300 binds (author).
- **Shader-creation mask-name scan** (FFXIV): every pixel shader's bytecode is scanned once when the game creates it, key or no key. 0.43 ns a byte, about 58 ms over a session's ~33,000 shaders, at load time only (author).
- **About three relaxed loads a draw** in the existing FFXIV draw hooks (contact shadows, the draw diagnostic, nameplates), at about 9,250 draws a frame: about 0.01 to 0.03 ms a frame by reading.
- **Hook-gate prologue on the FSR FG and XeFG hooks** (the live switch's safety): two seq_cst loads and one locked add and sub per hooked call, at most the present call (and `GetFrameLatencyWaitableObject` for XeFG) a frame. Well under 100 ns a frame by reading.
- **A clock read every present** in `OutputSwitch::OnPresent` (the bridge only): `steady_clock::now()` (QueryPerformanceCounter) and one configuration read before the key check, tens of nanoseconds a present; v0.4.0 had no such read.
- **Loader-lock and skip-window fixes**: one `thread_local` access on the library-load path, no new per-call work; the already-loaded catch-up now skips a busy mutex instead of waiting.
- **Rate-limited frame-count warning**: runs only when the game's frame count jumps, one mutex and `GetTickCount64` then; at default it logs fewer lines than v0.4.0 did.

Summed by reading: the present path about 0.1 to 0.3 us, the draw and bind path about 0.02 to 0.04 ms a frame, about 0.2 % of a 16.7 ms frame. Plausibly negligible, but no v0.4.0-vs-v0.5.0 A/B at defaults exists, and the trampoline's instruction-cache effect on the game's `PSSetShader` was not measured beyond the 1.0 ns a bind figure.
